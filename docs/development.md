# 개발 절차

작업마다 만들 동작을 정하고, 구현한 뒤 검사 결과를 남깁니다. 이 저장소의 하네스는 개발 절차, 작업 규칙, QA 절차와 이슈 처리 기준으로 구성합니다. QA는 앱을 직접 조작해 기대한 동작인지 확인하는 검증입니다.

이 문서는 모든 앱에 공통인 절차입니다. 앱별 현재 상태, 검사 명령과 기기 검증 순서는 각 앱의 README에 둡니다.

## 저장소 구성

```text
for-me/
├── apps/
│   └── video/              동영상 앱
│       ├── README.md       앱 개요, 검사 명령, 기기 검증
│       ├── docs/           범위, 기술 조사, 검증 기록, QA 이슈
│       └── android/        Android 모듈(Gradle 프로젝트 :video-android)
├── docs/                   모든 앱에 공통인 개발 절차와 QA 절차
├── build.gradle.kts        모든 앱이 함께 쓰는 Gradle 플러그인 버전
├── settings.gradle.kts     앱 모듈 등록
└── gradlew, gradlew.bat    Gradle 실행 스크립트
```

모든 앱은 루트의 Gradle 빌드 하나를 함께 씁니다. 플러그인 버전은 루트 `build.gradle.kts`에서 관리하고, 라이브러리 버전은 각 모듈에서 정합니다.

### 앱 추가

1. `apps/<앱>/` 폴더를 만들고 `README.md`와 `docs/`에 범위(`scope.md`), 기술 조사(`research.md`), 검증 기록(`verification.md`), QA 이슈(`qa-issues.md`)를 둡니다.
2. 플랫폼 모듈은 `apps/<앱>/<플랫폼>/`에 둡니다. 예: `apps/music/android/`.
3. `settings.gradle.kts`에 Gradle 프로젝트 `:<앱>-<플랫폼>`을 등록하고 폴더를 연결합니다. 폴더 이름 `android`가 앱끼리 겹치므로 프로젝트 이름으로 구분합니다.
4. 앱 식별자는 앱마다 다르게 정하고, 출시한 뒤에는 바꾸지 않습니다. 바꾸면 기존 설치본과 다른 앱이 되어 저장 기록을 이어받지 못합니다.
5. 루트 [README](../README.md)의 앱 목록에 추가합니다.

## 개발 환경

- JDK 17
- Android SDK Platform 36
- Android SDK Build-Tools 36.0.0
- Gradle 8.14.3: 저장소의 `gradlew` 사용

Android Studio에서 저장소 루트를 엽니다. 앱 폴더를 따로 열지 않습니다. Gradle 실행에 JDK 17을 사용합니다. `gradle/gradle-daemon-jvm.properties`도 17로 고정하며 JDK 자동 설치는 사용하지 않습니다.

SDK 위치는 `ANDROID_HOME` 또는 Git에서 제외한 `local.properties`의 `sdk.dir`로 지정합니다. 전역 Gradle 설치는 필요하지 않습니다.

### Windows와 macOS

같은 저장소를 Windows와 macOS에서 번갈아 사용합니다. 운영체제마다 다른 값은 저장소에 넣지 않고 각 사본에 둡니다.

| 항목 | macOS | Windows |
|---|---|---|
| Gradle 실행 | `./gradlew` | PowerShell은 `.\gradlew.bat`, Git Bash는 `./gradlew` |
| SDK 기본 경로 | `~/Library/Android/sdk` | `%LOCALAPPDATA%\Android\Sdk` |
| ADB | `$ANDROID_HOME/platform-tools/adb` | `%ANDROID_HOME%\platform-tools\adb.exe` |

- `local.properties`는 Android Studio가 머신마다 만들고 Git에서 제외합니다. 다른 운영체제의 사본에 복사하지 않습니다.
- `JAVA_HOME`이 JDK 17을 가리켜야 합니다. Android Studio에 포함된 JDK를 쓰면 터미널의 `JAVA_HOME`도 그 경로로 지정합니다.
- 줄바꿈은 `.gitattributes`가 정합니다. 텍스트 파일은 LF로, `.bat`과 `.cmd`는 CRLF로 받습니다. 각 머신의 `core.autocrlf` 값에 기대지 않습니다. 편집기 저장 형식은 `.editorconfig`가 정합니다.
- 파일 이름에는 영문, 숫자, `-`, `_`, `.`만 씁니다. macOS와 Windows의 기본 파일 시스템은 대소문자를 구분하지 않으므로 대소문자만 다른 이름을 나란히 두지 않고, 대소문자만 바꾸는 이름 변경은 다른 사본에서 경로가 바뀌었는지 확인합니다.
- Windows에서 이 문서와 [QA 절차](qa.md)의 셸 예시는 Git Bash에서 실행합니다. PowerShell 5.1의 `>` 리디렉션은 출력을 텍스트로 바꾸므로 `screencap` 같은 바이너리 출력이 깨집니다.

빌드 설정이나 줄바꿈 정책을 바꾸면 양쪽 사본에서 영향받는 앱의 자동 검사를 실행하고, 확인한 운영체제와 확인하지 못한 운영체제를 그 앱의 검증 기록에 구분해 남깁니다.

## 문서별 역할

공통 문서:

- [QA 절차](qa.md): 가상 기기와 실제 기기에서 조작하고 증거를 수집하는 방법
- [작업 규칙](../AGENTS.md): 데이터 보존과 검증 기준
- [Git 규칙](../.docs/git-convention.md): 커밋을 나누고 명령을 제안하는 방식

앱별 문서(`apps/<앱>/docs/`):

- `scope.md`: 만들 기능과 완료 기준
- `research.md`: 기술 선택의 근거와 조사 결과
- `qa.md`: 그 앱의 QA에서 확인할 항목
- `verification.md`: 검사할 항목과 실행 결과
- `qa-issues.md`: 발견한 문제의 우선순위, 현재 상태와 다음 조치

## 작업 순서

1. 이번에 만들 동작과 완료 기준을 정합니다. 범위가 바뀌면 해당 앱의 범위 문서를 먼저 고칩니다.
2. 해당 동작을 구현합니다. 기술 선택이 바뀌면 이유를 해당 앱의 기술 조사 문서에 남깁니다.
3. 변경한 동작에 필요한 자동 검사를 실행합니다. 공통 설정을 바꾸면 영향받는 모든 앱의 검사를 실행합니다.
4. 실제 재생이나 파일 접근, 데이터 보존에 영향을 주면 [QA 절차](qa.md)에 따라 앱을 조작합니다. 가상 기기 결과와 실제 기기 결과를 구분합니다.
5. 해당 앱의 검증 기록에 결과와 미검증 항목을 남기고, 발견한 문제는 그 앱의 QA 이슈 문서에 있는 처리 기준에 따라 분류합니다.
6. 승인된 작업 범위의 결함은 수정 후 같은 조건에서 다시 확인합니다. 수정 권한이 없거나 검증 환경이 없으면 이슈와 남은 조치를 기록하고 완료 범위를 제한합니다.

필요한 검사가 통과하면 작업을 마칩니다. 새 변경이나 실패, 구체적인 우려가 생겼을 때만 검사 범위를 넓힙니다.

## 자동 검사

저장소 루트에서 실행하며, 앱별 명령은 각 앱의 README에 있습니다.

- 코드 검사: Android Lint로 오류와 플랫폼 사용 문제를 확인합니다.
- 테스트: 변경한 동작을 확인합니다.
- 앱 빌드: 디버그 APK와 서명하지 않은 릴리스 APK를 만듭니다. APK는 Android 앱 설치 파일입니다.

Lint 경고는 오류로 처리합니다. 새 라이브러리나 빌드 도구 버전이 나왔다는 알림 3종은 정보로 표시하며, 업데이트는 호환성을 확인한 뒤 반영합니다.

테스트는 입력과 기대하는 결과를 기준으로 작성합니다. 외부 라이브러리를 흉내 낸 테스트는 앱의 상태 처리를 확인하는 데 쓰고, 실제 동작은 기기에서 확인합니다.

빌드나 CI, 릴리스 구성을 바꾸면 기존 생성물이 없는 임시 사본에서 같은 명령과 순서로 검증합니다. CI는 변경 시 검사를 자동 실행하는 환경입니다. 릴리스 명령이 있으면 외부 게시 없이 모의 실행하고, 실행하지 못한 단계는 남깁니다.

## 기기 검증

가상 기기에서는 기본 사용 흐름을 먼저 확인합니다. 정확한 모델명과 Android 버전은 실행할 때 기록합니다. 실제 기기 연결을 미룬 작업에서는 해당 검증을 미검증으로 남깁니다.

- 업데이트는 이전 앱을 지우지 않고 같은 앱 식별자와 서명으로 설치합니다.
- 업데이트 전 버전에서 저장한 기록과 파일 접근이 유지되는지 확인합니다.
- 설치한 APK와 검사에 사용한 파일을 식별할 수 있게 기록합니다.

앱별 기기와 검증 순서는 각 앱의 README에 있습니다. 조작과 증거 수집은 [QA 절차](qa.md)를 따릅니다. 수정한 이슈는 새 APK를 설치해 재현 조건과 영향받는 동작을 다시 확인한 뒤 완료합니다.

## 구성을 늘리는 기준

처음에는 한 작업씩 구현하고 기존 빌드 도구로 검사합니다. 같은 실패나 수작업이 반복될 때 추가 자동화를 검토합니다. 별도 하네스 프로그램, 자동 훅, 상시 다중 에이전트 구성은 현재 도입하지 않습니다.
