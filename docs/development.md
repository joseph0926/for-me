# 개발 절차

작업마다 만들 동작을 정하고, 구현한 뒤 검사 결과를 남깁니다. 이 저장소의 하네스는 개발 절차, 작업 규칙, QA 절차와 이슈 처리 기준으로 구성합니다. QA는 앱을 직접 조작해 기대한 동작인지 확인하는 검증입니다.

이 문서는 모든 앱에 공통인 절차입니다. 앱별 개발 환경, 검사 명령과 기기 검증 순서는 각 앱의 README에 둡니다.

## 저장소 구성

```text
for-me/
├── apps/
│   ├── video/              동영상 앱(Kotlin, Gradle)
│   │   ├── README.md       개발 환경, 검사 명령, 기기 검증
│   │   ├── docs/           범위, 기술 조사, QA, 검증 기록, QA 이슈
│   │   ├── android/        Android 모듈
│   │   └── gradlew 등      이 앱의 Gradle 빌드
│   ├── music/              음악 앱(착수 전, 문서만)
│   ├── gallery/            갤러리 앱(착수 전, 문서만)
│   ├── screen-gif/         화면 녹화 GIF 생성기(Tauri 2, Rust, React)
│   ├── termkeys/           터미널 줄 이동 단축키 도구(Swift, macOS)
│   ├── screen-note/        개인용 이미지 편집기(Tauri 2, Rust, React, Konva)
│   ├── journal/            사용과 개발 기록 로컬 웹과 CLI(Node, 외부 패키지 없음)
│   └── today-ref/          주제별 UI 레퍼런스 수집과 조합 구현(React, Vite, pnpm 작업 공간)
├── scripts/                여러 앱을 함께 점검하는 스크립트(Node, 외부 패키지 없음)
├── docs/                   모든 앱에 공통인 개발 절차와 QA 절차
├── .docs/                  Git 규칙
├── AGENTS.md               작업 규칙
└── .gitattributes 등       모든 앱에 공통인 줄바꿈과 편집기 설정
```

앱마다 언어와 빌드 도구가 다를 수 있습니다. 앱의 빌드 도구, 의존성 설정과 코드는 모두 그 앱의 폴더 안에 두고, 저장소 루트에는 어느 앱의 빌드 파일도 두지 않습니다. 앱을 빌드하거나 IDE에서 열 때는 그 앱의 폴더를 기준으로 합니다.

### 앱 추가

1. `apps/<앱>/` 폴더를 만들고 `README.md`와 `docs/`에 범위(`scope.md`), 기술 조사(`research.md`), QA(`qa.md`), 검증 기록(`verification.md`), QA 이슈(`qa-issues.md`)를 둡니다. 아직 내용이 없는 문서는 필요해질 때 만듭니다.
2. 기술을 정하면 빌드 도구와 코드를 `apps/<앱>/` 안에 둡니다. 플랫폼마다 코드가 나뉘면 `apps/<앱>/<플랫폼>/`처럼 하위 폴더로 나눕니다.
3. 앱 식별자는 앱마다 다르게 정하고, 출시한 뒤에는 바꾸지 않습니다. 바꾸면 기존 설치본과 다른 앱이 되어 저장 기록을 이어받지 못합니다.
4. 루트 [README](../README.md)의 앱 목록에 추가합니다.
5. 루트나 앱 README의 표지는 실제 화면이나 명령 출력을 중심에 둡니다. 기능을 사물에 비유한 그림으로 대신하지 않고, 생성 이미지는 그 바깥을 꾸미는 데만 씁니다.

## Windows와 macOS

같은 저장소를 Windows와 macOS에서 번갈아 사용합니다. 운영체제마다 다른 값은 저장소에 넣지 않고 각 사본에 둡니다. 앱별 도구 경로는 각 앱의 README에 있습니다.

- SDK 경로처럼 머신마다 다른 값을 담는 로컬 설정 파일은 Git에서 제외하고, 다른 운영체제의 사본에 복사하지 않습니다.
- 줄바꿈은 `.gitattributes`가 정합니다. 텍스트 파일은 LF로, `.bat`과 `.cmd`는 CRLF로 받습니다. 각 머신의 `core.autocrlf` 값에 기대지 않습니다. 편집기 저장 형식은 `.editorconfig`가 정합니다.
- 파일 이름에는 영문, 숫자, `-`, `_`, `.`만 씁니다. macOS와 Windows의 기본 파일 시스템은 대소문자를 구분하지 않으므로 대소문자만 다른 이름을 나란히 두지 않고, 대소문자만 바꾸는 이름 변경은 다른 사본에서 경로가 바뀌었는지 확인합니다.
- 실행 스크립트를 추가하면 macOS에서도 실행되도록 Git에 실행 권한을 기록합니다. Windows 사본은 실행 권한을 기록하지 못하므로 `git add --chmod=+x <파일>`을 사용합니다.
- Windows에서 셸 예시는 Git Bash에서 실행합니다. PowerShell 5.1의 `>` 리디렉션은 출력을 텍스트로 바꾸므로 화면 캡처 같은 바이너리 출력이 깨집니다.

빌드 설정이나 줄바꿈 정책을 바꾸면 양쪽 사본에서 영향받는 앱의 자동 검사를 실행하고, 확인한 운영체제와 확인하지 못한 운영체제를 그 앱의 검증 기록에 구분해 남깁니다.

### macOS 앱 설치본 관리

Mac에 설치해 사용하는 제품은 기존 설치 경로를 기준으로 관리합니다. 빌드 폴더의 `.app`도 Spotlight에 나타날 수 있습니다.

1. 설치본의 경로, `Info.plist`의 `CFBundleIdentifier`와 실행 파일의 SHA-256을 확인합니다. QA를 시작하면 같은 경로에 검증할 빌드를 설치하고 그 경로에서 검사합니다. 이전 완료본이 복구에 필요하면 앱으로 검색되지 않는 압축 파일이나 `.app-backup`으로 보관합니다. 설정과 사용자 데이터는 유지합니다.
2. QA가 끝나면 검증을 마친 최신 완료본을 같은 경로에 둡니다. 검사한 빌드가 그대로 완료본이 되면 해시를 대조해 그대로 사용합니다. 실패한 빌드를 폐기하고 QA를 종료할 때는 직전 완료본을 복원합니다.
3. 빌드만 할 때도 제품이 이미 설치돼 있으면 임시 번들은 Spotlight 검색 대상 밖(예: `.noindex` 작업 폴더)에서 만듭니다. 설치본의 서명과 실행 파일을 확인한 뒤 중복된 개발용 `.app`은 휴지통에 옮기거나 백업 형식으로 보관합니다. QA 로그와 캡처는 보존합니다.
4. 일반 사용자 세션에서 아래 명령의 식별자를 실제 값으로 바꿔 실행합니다. 결과가 의도한 설치 경로 한 곳인지, 그 실행 파일의 SHA-256이 QA 중에는 검사 대상과, 완료 후에는 최신 완료본과 같은지 확인합니다. 빌드 및 QA 폴더도 직접 확인해 색인 반영 전의 사본을 찾습니다. Spotlight를 조회할 수 없으면 앱 검색은 미검증으로 남깁니다.

   ```sh
   mdfind 'kMDItemCFBundleIdentifier == "제품의 번들 식별자"'
   ```

### 빌드와 설치본 점검

제품마다 소스 버전을 빌드 산출물, 이 머신의 설치본, 의존성 설치 상태와 한 번에 대조합니다. 읽기만 하고 빌드, 설치, 삭제는 하지 않습니다. 저장소 루트에서 실행합니다.

```sh
node scripts/build-status.mjs
node scripts/build-status.mjs --json
```

| 표시 | 뜻 |
|---|---|
| 최신 | 소스 버전과 같고, 빌드 뒤 바뀐 소스가 없음 |
| 오래됨 | 버전이 다르거나, 빌드 뒤 소스가 바뀌었거나, 설치본이 최신 빌드와 다른 파일이거나, 마지막 `pnpm install` 뒤 lockfile이 바뀜 |
| 없음 | 산출물이나 설치본이 없음 |
| 미확인 | 기기가 없거나 이 운영체제에서 볼 수 없음 |

오래됨이나 없음이 하나라도 있으면 종료 코드 1, 모두 최신이거나 미확인이면 0입니다.

- 대조 대상과 경로는 스크립트 위쪽의 `products`가 정합니다. 제품, 산출물 경로나 설치 위치가 바뀌면 그 표를 함께 고칩니다.
- 빌드 뒤 소스 변경은 파일 수정 시각으로 판정합니다. `git pull`이나 브랜치 이동처럼 내용 없이 수정 시각만 바뀐 경우에도 오래됨으로 나옵니다.
- 의존성은 pnpm이 설치할 때 남기는 `node_modules/.pnpm/lock.yaml`과 `pnpm-lock.yaml`의 수정 시각을 비교합니다. Cargo와 Gradle 의존성은 빌드할 때 받으므로 따로 보지 않습니다.
- Windows 설치본은 실행 파일의 제품 버전과 SHA-256을 릴리스 빌드와 비교합니다. Screen Note는 설치 프로그램의 기본 경로, screen-gif는 실행 파일을 복사해 둔 `%LOCALAPPDATA%\Programs\screen-gif`를 봅니다.
- Android는 `adb devices`로 연결된 기기와 가상 기기마다 설치된 `versionName`을 읽습니다. adb 서버가 꺼져 있으면 이 명령이 서버를 켭니다. 기기가 없으면 미확인으로 남깁니다.
- macOS 설치본 대조는 아직 없습니다. macOS에서는 앞 절의 절차로 확인하고, TermKeys는 Windows에서 점검하지 않습니다.
- 테스트는 `node --test scripts/*.test.mjs`입니다.

### 할 일

남은 일의 상태는 Git으로 나뉘는 앱 문서가 소유합니다. [기록 도구](../apps/journal/README.md)의 데이터는 Git에서 빠져 머신마다 따로이므로, 한 머신에서 끝낸 일이 다른 머신 기록에는 열린 채 남습니다. 그래서 기록 도구를 할 일 목록으로 쓰지 않습니다.

- 할 일은 앱의 `scope.md`(또는 그 일을 다루는 문서)에 `- [ ] **제목.** 설명` 한 줄로 둡니다. 끝나면 `- [x]`로 바꾸고 같은 줄 아래에 날짜와 확인한 범위를 적습니다. 진행 상황도 그 줄 아래에 덧붙이고, 같은 일을 다른 절의 "남은 것" 목록에 따로 적지 않습니다.
- 기록 도구에 같은 일을 요청으로 남길 때는 제목을 `할 일: <제목>`으로 씁니다. 사용자 결정을 기다리는 일은 `결정 대기: <제목>`을 기록 제목과 문서 제목에 똑같이 씁니다.
- 일을 마치거나 다른 머신에서 끝냈다는 말을 들으면 문서 줄과 이 머신의 기록을 함께 고친 뒤 대조합니다.

```sh
node scripts/todos.mjs
node scripts/todos.mjs --all
```

열린 할 일을 파일과 줄 번호로 보여 주고, 이 머신 기록과 어긋나면 종료 코드 1을 냅니다. 읽기만 합니다.

| 어긋남 | 뜻 |
|---|---|
| 문서에 없음 | 이 머신 기록에 시작 전(`open`)이거나 `결정 대기:` 요청이 있는데 같은 제목의 문서 할 일이 없음 |
| 기록이 뒤처짐 | 문서는 완료인데 이 머신 기록은 열림. 다른 머신에서 끝낸 경우가 많습니다 |
| 문서가 뒤처짐 | 이 머신 기록은 완료인데 문서 할 일은 열림 |

- 진행 중(`in_progress`)과 다른 대기 요청, QA 이슈의 상태는 대조하지 않습니다. QA 이슈는 각 앱의 `qa-issues.md`가 소유합니다.
- 기록 도구 데이터가 없는 머신에서는 문서의 할 일만 보여 줍니다.
- 테스트는 `node --test scripts/*.test.mjs`입니다.

### Node와 pnpm 버전

- Node.js 버전은 `.node-version`이 정합니다. 저장소 루트와 Node를 쓰는 앱 폴더(`screen-gif`, `journal`, `today-ref`)에 같은 값을 둡니다.
- `engines.node`는 최소 버전 기준으로만 둡니다.
- pnpm 버전은 각 앱 `package.json`의 `packageManager`가 정합니다. 어떤 도구로 pnpm을 실행하든 이 버전이 실행되어야 합니다.
- 버전을 올릴 때는 `.node-version` 네 개와 `packageManager` 두 개를 한 변경에서 함께 바꾸고, pnpm을 쓰는 앱마다 설치와 자동 검사를 실행합니다. lockfile에서는 pnpm 버전 부분만 바뀌어야 합니다.
- 새 Node 버전은 개발 머신마다 직접 설치합니다.

Node와 pnpm을 실행하는 도구는 머신마다 다릅니다. 그 머신이 쓰는 도구의 항목을 따릅니다.

- fnm과 전역 pnpm: 새 버전은 `fnm install <버전>`으로 설치하고 pnpm은 `pnpm <명령>`으로 실행합니다. fnm은 앱 폴더의 `package.json`에 `engines.node`가 있으면 상위 폴더의 `.node-version`보다 그 범위를 먼저 쓰므로, 루트 파일 하나로 대신하지 않습니다. 설치하지 않은 버전을 가리키는 `.node-version`이 있으면 fnm이 오류를 내고 기존 버전을 계속 씁니다.
- asdf와 Corepack: 새 버전은 `asdf install nodejs <버전>`으로 설치하고 pnpm은 `corepack pnpm <명령>`으로 실행합니다. 전역 pnpm과 섞어 쓰지 않습니다.
- 버전 관리자가 없는 머신(Windows): `.node-version`이 자동으로 적용되지 않으므로 `node -v`가 같은 값인지 직접 확인합니다.

## 문서별 역할

공통 문서:

- [QA 절차](qa.md): 기기와 컴퓨터에서 조작하고 증거를 수집하는 방법
- [작업 규칙](../AGENTS.md): 데이터 보존과 검증 기준
- [Git 규칙](../.docs/git-convention.md): 커밋을 나누고 명령을 제안하는 방식

앱별 문서(`apps/<앱>/docs/`):

- `scope.md`: 만들 기능과 완료 기준
- `research.md`: 기술 선택의 근거와 조사 결과
- `ui.md`: 화면 흐름, 화면 값과 움직임. 화면 설계가 필요한 앱만
- `qa.md`: 그 앱의 조작 도구와 QA 확인 항목
- `verification.md`: 검사할 항목과 실행 결과
- `qa-issues.md`: 발견한 문제의 우선순위, 현재 상태와 다음 조치

## 작업 순서

앱의 사용자 개발 요청은 [기록 도구 절차](../apps/journal/docs/agent.md)에 따라 기존 요청을 확인하고 원문과 요약을 남깁니다. 작업 중 변경과 검증, 확인한 버전을 연결하며, 상세 결함과 검사 근거는 아래 기존 문서에 유지합니다. 기록 장애가 있으면 그 사실을 보고하고 승인된 개발을 계속합니다.

1. 이번에 만들 동작과 완료 기준을 정합니다. 범위가 바뀌면 해당 앱의 범위 문서를 먼저 고칩니다. 화면과 조작은 직접 쓰는 데 필요한 기능을 하나씩 쌓으며 정하고, 대체하려는 기존 앱에 대한 불만은 만들게 된 배경으로만 다룹니다.
2. 해당 동작을 구현합니다. 기술 선택이 바뀌면 이유를 해당 앱의 기술 조사 문서에 남깁니다.
3. 변경한 동작에 필요한 자동 검사를 실행합니다. 공통 설정을 바꾸면 영향받는 모든 앱의 검사를 실행합니다.
4. 파일 접근이나 데이터 보존, 사용자가 직접 확인해야 하는 동작에 영향을 주면 [QA 절차](qa.md)에 따라 앱을 조작합니다. 가상 환경 결과와 실제 기기 결과를 구분합니다.
5. 해당 앱의 검증 기록에 결과와 미검증 항목을 남기고, 발견한 문제는 그 앱의 QA 이슈 문서에 있는 처리 기준에 따라 분류합니다.
6. 승인된 작업 범위의 결함은 수정 후 같은 조건에서 다시 확인합니다. 수정 권한이 없거나 검증 환경이 없으면 이슈와 남은 조치를 기록하고 완료 범위를 제한합니다.

필요한 검사가 통과하면 작업을 마칩니다. 새 변경이나 실패, 구체적인 우려가 생겼을 때만 검사 범위를 넓힙니다.

## 자동 검사

앱마다 코드 검사, 테스트와 앱 빌드 명령을 README에 둡니다.

테스트는 입력과 기대하는 결과를 기준으로 작성합니다. 외부 라이브러리나 운영체제 기능을 흉내 낸 테스트는 앱의 상태 처리를 확인하는 데 쓰고, 실제 동작은 기기에서 확인합니다.

빌드나 CI, 릴리스 구성을 바꾸면 기존 생성물이 없는 임시 사본에서 같은 명령과 순서로 검증합니다. CI는 변경 시 검사를 자동 실행하는 환경입니다. 릴리스 명령이 있으면 외부 게시 없이 모의 실행하고, 실행하지 못한 단계는 남깁니다.

## 기기 검증

가상 환경에서는 기본 사용 흐름을 먼저 확인합니다. 정확한 모델명과 운영체제 버전은 실행할 때 기록합니다. 실제 기기 확인을 미룬 작업에서는 해당 검증을 미검증으로 남깁니다.

- 업데이트는 이전 앱을 지우지 않고 같은 앱 식별자와 서명으로 설치합니다.
- 업데이트 전 버전에서 저장한 기록과 설정, 파일 접근이 유지되는지 확인합니다.
- 설치 파일과 검사에 사용한 파일을 식별할 수 있게 기록합니다.

앱별 기기와 검증 순서는 각 앱의 README에 있습니다. 조작과 증거 수집은 [QA 절차](qa.md)를 따릅니다. 수정한 이슈는 새 설치 파일로 재현 조건과 영향받는 동작을 다시 확인한 뒤 완료합니다.

## 구성을 늘리는 기준

처음에는 한 작업씩 구현하고 기존 빌드 도구로 검사합니다. 같은 실패나 수작업이 반복될 때 추가 자동화를 검토합니다. 별도 하네스 프로그램, 자동 훅, 상시 다중 에이전트 구성은 현재 도입하지 않습니다.
