# Viewgrain 폐기 기록

Viewgrain은 이미지 생성 모델로 만든 UI 시안을 고르고 보관해 AI가 구현할 때 참고하게 하던 도구입니다. 2026-11-17에 시작해 2026-11-18에 사용자 판단으로 폐기했습니다. `apps/viewgrain` 폴더는 제거했고 이 문서만 남깁니다.

## 왜 시작했나

[동영상 앱](../apps/video/README.md)을 만들면서 영상 목록과 재생 조작 화면에서 기대한 느낌을 얻지 못했습니다. 원하던 방향은 넷플릭스와 여러 영상 서비스에서 느낀 모던하고 깔끔한 화면이었습니다.

완성된 화면을 눈으로 보면서 방향을 정할 방법이 필요했습니다. 실제 앱 화면을 모으는 일은 어렵고 번거로웠고 유료 레퍼런스 서비스는 구독하지 않기로 했습니다. 그래서 GPT-Image-2.6으로 시안을 생성해 고르고, 고른 그림과 선택 이유를 쌓아 AI에 전달하는 방향을 골랐습니다.

## 어디까지 개발했나

2026-11-17에 커밋한 범위입니다.

- 레퍼런스 묶음 세 개와 PNG 다섯 장을 보관했습니다. 비디오 앱의 홈과 세로 및 가로 재생 세 장(SCENE), 영화 컬렉션의 목록형 화면 한 장(FRAME), 로그 조사 대시보드 한 장입니다. 묶음마다 사용자 선택 기록과 프롬프트 기록을 함께 두었습니다.
- 보관한 묶음과 이미지를 읽는 로컬 MCP 서버를 만들었습니다. 도구는 목록 조회, 묶음 조회와 이미지 한 장 조회 세 가지였고 원본 바이트를 변환 없이 전달했습니다.
- 다른 도구와 파일 사본으로 주고받는 내보내기와 가져오기 명령을 만들었습니다.
- 자동 검사 열두 개가 통과했고, 실제 연결에서 원본 바이트 일치와 Codex의 이미지 인식을 확인했습니다.
- SCENE과 FRAME의 네 장은 [동영상 앱의 화면 리디자인](../apps/video/docs/scope.md#2026-11-17-화면-리디자인)에 사용했습니다.

2026-11-18에 작업했지만 커밋하지 않은 범위입니다.

- 사용자 반응을 다음 프롬프트로 잇는 취향 규칙 파일을 만들었습니다. 네 규칙(색과 빛으로 고급스러움을 연출하지 않기, 조작 요소가 콘텐츠보다 무겁지 않게 하기, UI 글자에 장식 글꼴을 쓰지 않기, 많이 담으려고 글자와 간격을 줄이지 않기)을 사용자가 확정했습니다.
- 첫 생성에서 서로 다른 세 방향을 비교하는 절차를 프롬프트 가이드에 넣었습니다.
- 고르지 않은 그림을 선택작과 구분해 보관하고 조회하는 기능을 넣었고 자동 검사는 열다섯 개가 통과했습니다. 등록한 탈락작은 없었습니다.

만들지 않은 것은 웹 갤러리 화면, 검색, 생성 도구와의 직접 연결입니다.

## 왜 폐기했나

2026-11-18에 취향 규칙과 세 방향 절차의 효과를 확인하려고 로그 조사 화면을 다시 생성했습니다.

1. 세 방향의 첫 결과에서 지난번에 지적받은 색칠된 배지, 발광과 빽빽한 줄은 보이지 않았습니다. 사용자는 세 장 가운데 고르지 않았습니다.

   > B는 섹션들이 크고 뭔가 데모/목업같고, C는 엑셀이나 docs로 예쁘게 꾸미려고 노력한 느낌입니다(웹페이지, 프로덕션 느낌이 아님), Aㄱㅏ 그나마 낫지만 이것또한 vercel, apple, 넷플릭스 << 이런 프로덕션 회사 느낌이 아닙니다

2. 에이전트는 원인을 제품의 틀이 없는 것, 글자가 실제 창보다 큰 것, 데이터가 지나치게 고른 것으로 보고 수정 프롬프트를 썼습니다. 성격이 다른 화면으로도 확인하려고 숙소 예약 서비스의 숙소 상세 페이지 프롬프트도 썼습니다.

3. 로그 수정 결과 한 장과 숙소 페이지 두 장에는 프롬프트에 적은 상단 바, 실제 창 기준의 글자 크기, 고르지 않은 데이터와 가는 선이 나타났습니다. 사용자의 평가는 바뀌지 않았습니다.

   > 깨달은게있습니다.
   >
   > viewgrain은 폐기해야할듯합니다
   >
   > * gpt-image로 제작하는 레퍼런스는 프로덕션 느낌이 안납니다

4. 같은 날 사용자가 관련 내용을 모두 제거하고 이 기록만 남기도록 요청했습니다.

정리하면 이 도구의 전제는 이미지 생성으로 만든 시안이 실제 화면 수집을 대신할 수 있다는 것이었습니다. 사용자는 생성한 그림이 운영 중인 제품의 느낌을 내지 못한다고 판단했고, 프롬프트로 지시할 수 있는 항목을 채워도 그 판단이 바뀌지 않았습니다.

### 확인한 것과 확인하지 못한 것

- 전문가용 도구 화면과 소비자용 페이지 두 종류에서 같은 평가가 나왔습니다. 화면 종류마다 한두 번의 생성입니다.
- 남은 차이가 무엇인지는 사용자가 말하지 않았고 에이전트도 특정하지 못했습니다.
- 사용자가 그림을 만든 생성 모델과 실제 입력 문장은 확인하지 못했습니다. 다른 생성 모델은 시험하지 않았습니다.
- 폐기 이전에 사용자는 SCENE 세 장에 "이정도면 만족스럽스빈다"라고 했고 FRAME 목록형을 선택했습니다. 이 두 묶음에 폐기 시점의 기준을 다시 적용한 평가는 듣지 않았습니다.

## 제거한 것과 남긴 것

- `apps/viewgrain` 폴더는 휴지통으로 옮겼습니다. 커밋된 파일 서른일곱 개는 Git 이력에서 볼 수 있습니다. 첫 커밋은 `4f96202`, 마지막으로 이 폴더를 바꾼 커밋은 `7989daa`입니다.
- 2026-11-18의 미커밋 변경과 새 파일 네 개(취향 규칙, 로그 조사 화면과 숙소 상세 페이지의 프롬프트 문서, 탈락작 검사)는 커밋된 적이 없어 Git 이력에 없습니다.
- 저장소 밖에서는 이미지 생성 프롬프트를 쓰던 `ui-reference-prompt` 스킬을 제거했고, tastepin과 그 개인 자료 문서에서 Viewgrain 연결 설명을 지웠습니다.
- 남긴 것은 과거 기록입니다. [사용과 개발 기록](../apps/journal/README.md)의 Viewgrain 기록은 그대로 두고 앱 상태만 중단으로 바꿨습니다. 동영상 앱 문서의 리디자인 출처, harness의 코드 리뷰 원장과 실패 기록, tastepin Lab에서 FRAME 그림으로 만든 시안 자료도 그대로입니다.

## 비슷한 도구를 다시 만들려 할 때

- 이미지 생성 모델로 만든 UI 시안을 레퍼런스의 원천으로 삼는 도구는 이 기록의 평가를 먼저 봅니다. 프롬프트 규칙과 절차를 더하는 것으로는 사용자의 평가가 바뀌지 않았습니다.
- 금지 규칙으로 지난 지적을 없앤 것과 사용자가 결과를 받아들이는 것은 별개였습니다.
- 보관과 조회 기능을 넓히기 전에, 보관할 자료의 질을 사용자가 받아들이는지 먼저 확인합니다. 탈락작 보관은 보관할 그림이 한 장도 생기기 전에 만들었습니다.
