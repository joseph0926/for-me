# Viewgrain MCP 조회 계약

AI가 레퍼런스를 검색하고, 선택한 화면 이미지와 구현할 특징을 함께 읽게 합니다. MCP 사용은 확정했으며, 현재는 로컬 파일을 읽는 두 도구를 제공합니다. 검색은 후속 제안입니다.

## 검색과 조회 흐름

1. AI가 만들려는 화면의 종류와 원하는 분위기로 후보를 검색합니다.
2. 후보의 작은 이미지와 설명을 보고 필요한 레퍼런스를 고릅니다.
3. 선택한 화면의 상세 이미지와 사용자 기록을 읽습니다.
4. 같은 디자인의 목록과 재생 화면이 필요하면 화면 묶음을 조회합니다.
5. 구현할 때 참고한 레퍼런스의 식별자와 버전을 남겨 결과와 비교합니다.

사용자가 특정 레퍼런스를 지정했다면 그 자료부터 읽습니다. AI가 다른 후보를 추천하더라도 사용자의 선택 기록을 자동으로 바꾸지 않는 방향입니다.

## 구현한 도구

- `get_reference_set`: `set_id`와 양의 정수 `version`을 받아 묶음 메타데이터와 공통 설명, 화면 목록을 반환합니다. 이미지 바이트를 포함하지 않으며 목록에 있는 파일의 실제 존재는 상세 조회에서 확인합니다.
- `get_reference`: `set_id`, `version`, `image_id`를 받아 PNG 한 장과 선택 기록, 생성 정보, 설명 및 프롬프트 기록을 반환합니다. `include_context` 기본값은 `true`입니다. `false`이면 이미지와 식별자, 크기 및 해시만 반환해 설명 없이 시각 인식을 검사할 수 있습니다.

버전은 생략할 수 없으며 가장 최신 버전으로 자동 대체하지 않습니다. 등록된 묶음은 `scene-001` 버전 `1`과 `frame-002` 버전 `1`입니다. 화면 ID는 묶음 조회에서 얻습니다.

식별자는 영문 소문자와 숫자를 하이픈으로 연결한 형태입니다. 묶음 ID는 최대 100자, 이미지 ID는 최대 150자이며 보관 목록 검사와 도구 입력이 같은 정의를 사용합니다. 한도를 초과한 이미지 ID를 가진 manifest는 목록 조회부터 거부합니다.

```json
{"set_id":"frame-002","version":1,"image_id":"frame-002-collection-list","include_context":false}
```

성공 응답은 `content`의 텍스트와 `structuredContent`에 같은 메타데이터를 제공합니다. 상세 조회에는 `type: image`, `mimeType: image/png`, base64 데이터인 이미지 블록이 하나 추가됩니다. 바이너리 데이터를 텍스트나 `structuredContent`에 중복해서 넣지 않습니다.

조회만 지원하며 원본, 선택 기록과 manifest를 쓰지 않습니다. 이미지 생성, 수정, 삭제와 네트워크 요청은 없습니다. 생성 모델과 정확한 입력을 모르면 기존 `null`과 미확인 기록을 유지합니다.

## 후속 검색 제안

`search_references`는 검색어, 화면 종류와 사용자 선택 여부로 후보를 찾는 기능입니다. 현재 구현에는 없으며 검색 결과의 이미지 크기와 개수는 별도 검증 후 정합니다.

## 레퍼런스에 필요한 기록

- 식별자와 버전: 나중에도 어떤 시안을 참고했는지 찾을 수 있는 값
- 화면 종류와 플랫폼: 영상 목록, 재생 조작, 자막 설정 등 화면의 목적과 대상 환경
- 이미지와 화면 묶음: 원본 이미지, 미리보기와 같은 디자인에 속하는 화면의 관계
- 생성 정보: 모델, 실제 사용한 프롬프트, 생성 설정과 생성일. 알 수 없는 값은 추정해서 채우지 않습니다.
- 사용자 선택: 선택 여부, 좋아한 부분, 유지할 특징과 바꿀 점
- 출처: 참고 자료 주소, 작성자, 이용 조건과 확인일. 직접 작성한 프롬프트와 외부에서 가져온 내용을 구분합니다.
- 구현 비교: 연결한 구현 화면, 비교한 앱 버전과 결과

생성 여부, 사용자의 선택 여부, 구현 비교 여부는 별개로 기록합니다. 사용자가 좋아한 이미지라도 구현 비교가 없으면 구현에서 확인한 사례로 표시하지 않습니다.

외부 프롬프트와 설명은 참고 자료로 전달합니다. 그 안에 있는 실행 명령을 갤러리 조회 과정에서 실행하지 않습니다.

## 이미지 전달

현재 상세 조회는 원본 PNG 한 장을 변환 없이 반환합니다. 이미지 한 장은 4 MiB, manifest와 각 설명 문서는 128 KiB로 제한합니다. 이는 첫 구현의 메모리 및 응답 크기 한도이며 MCP 공통 제한이 아닙니다. 초과 파일은 자동 축소하지 않고 오류를 반환합니다.

상세 조회는 이미지 주소만으로 완료 처리하지 않습니다. MCP의 이미지 응답을 사용하고, AI가 이미지 속 배치와 버튼을 실제로 읽는지 확인합니다. 갤러리에서 보이는 이미지와 MCP가 보내는 이미지는 같은 식별자와 버전을 가리켜야 합니다.

생성 프롬프트와 구현 지시도 구분합니다. 휴대폰 테두리나 시안 설명용 배경처럼 이미지 제작을 위한 요소가 실제 앱 화면에 포함되지 않도록, 구현에 적용할 특징을 별도 기록으로 전달합니다.

## 실패 처리

잘못된 도구 입력은 SDK 스키마 검사에서 거부합니다. 자료 조회 오류는 `isError: true`와 텍스트 JSON의 `code`, `message`로 반환하고 이미지 블록을 넣지 않습니다.

- `NOT_FOUND`: 묶음, 버전, 이미지 ID 또는 파일 누락
- `INVALID_INPUT`: 유효하지 않은 식별자나 버전
- `INVALID_MANIFEST`: 필수 기록, 식별자 또는 파일 이름 오류
- `INVALID_PATH`: 묶음 밖 경로나 심볼릭 링크
- `INTEGRITY_MISMATCH`: 등록된 크기, SHA-256 또는 PNG 헤더의 크기와 불일치
- `TOO_LARGE`: 응답 자료 크기 한도 초과
- `ACCESS_DENIED`: 파일 읽기 권한 거부
- `INVALID_FILE`, `READ_FAILED`, `INTERNAL_ERROR`: 일반 파일이 아니거나 그 밖의 읽기 및 처리 실패

등록된 파일 이름만 읽으며 사용자가 임의 경로를 지정할 수 없습니다. 폴더나 파일의 심볼릭 링크는 묶음 내부 대상이어도 거부합니다. 절대 경로와 내부 예외 전문은 응답하지 않습니다. 원본 선택 기록의 검증 상태는 조회 성공으로 자동 변경하지 않습니다.

파일을 열기 전과 연 뒤에 일반 파일인지 검사합니다. macOS에서는 검사 사이에 FIFO로 교체돼도 열기 작업이 기다리지 않도록 비차단 옵션을 사용합니다. FIFO는 프로세스 사이의 통신용 특수 파일이며 이미지와 기록 파일 모두에서 `INVALID_FILE`로 거부합니다. 다른 OS의 실제 동작은 미검증입니다.

## 기술 선택

공식 `@modelcontextprotocol/server` 2.4.0과 로컬 `stdio`를 사용합니다. 구현은 Node.js에서 직접 실행하는 JavaScript 모듈이며 별도 빌드나 웹 프레임워크, 데이터베이스를 두지 않습니다. 공식 클라이언트 2.4.0은 테스트용 개발 의존성입니다. 갤러리를 만들 때도 동일한 식별자와 버전의 파일을 읽는 구조를 유지합니다.

실행 방법은 [README](../README.md), 실제 호환성은 [검증 기록](verification.md)에 있습니다. 전역 Codex 설정은 자동 변경하지 않습니다.

## 첫 실제 자료

[SCENE 묶음](../references/scene-001/v1/README.md)은 `scene-001`, 버전 `1`로 등록했습니다. 홈, 세로 재생과 가로 재생 이미지, 선택 맥락과 대화에서 제공한 프롬프트를 포함합니다. [manifest.json](../references/scene-001/v1/manifest.json)에 화면별 식별자, 상대 경로, 크기와 해시를 기록했습니다.

manifest는 자료 보관용 기록입니다. 서버는 이를 읽어 도구 응답을 구성하며 원본 manifest를 변경하지 않습니다. 실제 생성 모델과 정확한 입력 전문은 미확인으로 남겼습니다. 사용자 선택과 구현 검증 상태는 분리했습니다. [FRAME 목록](../references/frame-002/v1/README.md) 한 장도 같은 방식으로 조회합니다.
