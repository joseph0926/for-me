# 레퍼런스 생성 프롬프트 활용

먼저 원하는 앱의 모습을 넓게 탐색하고, 사용자 반응이 나온 뒤 불편한 부분을 좁혀 수정한다. 첫 사례는 [SCENE 레퍼런스 묶음](../references/scene-001/v1/README.md)이다. 당시 대화에서 제공한 다섯 프롬프트 전문은 묶음의 [프롬프트 기록](../references/scene-001/v1/prompts.md)에 보존했다.

## 공개 자료에서 가져온 작성 방식

- [Superdesign 음악 재생 예제](https://github.com/superdesigndev/superdesign-prompts/blob/main/prompts/editorial-music-player-now-playing/README.md): 전체 인상을 요약한 뒤 역할별 색상, 구역별 내용과 위치 관계를 설명한다.
- [Leonxlnx 모바일 화면 지침](https://github.com/Leonxlnx/imagegen-skills/blob/main/skills/imagegen-frontend-mobile/SKILL.md): 여러 화면에서 글자, 색상, 아이콘과 형태 표현을 공유한다.
- [ZeroLu 음악 재생 예제](https://github.com/ZeroLu/awesome-gpt-image#music-player-interface): 정확한 문구, 시간과 표시 상태를 분리해 지정한다.

원문을 통째로 가져오거나 기본 색상, 장식과 강도 점수를 채택하지 않는다. 조사 범위와 이용 조건은 [자료 조사](research.md)를 따른다. 이 자료들은 작성 방식의 근거이며 생성 품질을 보장하는 실험 결과가 아니다.

## 1. 새 방향 탐색

기존 구현의 기능, 기술, 고정 콘텐츠와 개발 난이도를 입력하지 않는다. 사용자에게 필요한 경험과 원하는 인상을 설명하고, 기능 구성과 시각적 선택은 열어둔다. 비디오 앱에서는 [탐색 방향](video-reference.md)을 따른다.

요청은 다음 순서로 작성한다.

1. 어떤 제품 경험을 원하는지 설명한다.
2. 가장 강한 디자인 방향 하나를 선택하고 일관되게 적용하도록 한다.
3. 색상, 글자, 이미지와 공간이 어떤 관계를 가져야 하는지 설명한다.
4. 기능과 콘텐츠를 스스로 구성할 범위를 알린다.
5. 읽을 수 있는 문구와 알아볼 수 있는 조작 등 완성도 기준을 정한다.
6. 한 장의 실제 앱 화면처럼 출력하도록 요청한다.

처음부터 영상 개수, 버튼 위치, 강조색과 화면 방향까지 모두 고정하지 않는다. 여러 방향을 비교하기 위해 조건을 맞추는 작업은 원하는 후보가 나온 뒤에 한다. 첫 사례의 [P01](../references/scene-001/v1/prompts.md#p01)에서 바로 시작할 수 있다.

## 2. 같은 앱의 다른 화면으로 확장

방향을 이어갈 이미지를 첨부하고 공통 디자인 규칙을 읽도록 한다. 새 화면의 사용자 과업과 보여줄 상태를 지정하되, 이전 화면의 배치를 복제하지 않는다. 홈의 글자와 색상은 재생 화면으로 이어질 수 있지만 탐색 메뉴까지 재생 화면에 반복할 필요는 없다.

첫 사례의 [P02](../references/scene-001/v1/prompts.md#p02)는 홈을 재생 경험으로 확장하는 요청이다. 첨부한 UI 이미지와 영상 장면 원본이 함께 있으면 각 이미지의 역할을 따로 설명한다.

## 3. 사용자 반응으로 수정 범위 좁히기

사용자의 표현과 수정 가설을 구분한다. 첫 사례에서 사용자는 금색 강조색이 AI가 흔히 만드는 상투적인 화면처럼 느껴진다고 말했다. 금색 광택과 발광의 반복이 원인이라는 설명은 에이전트의 해석이었다. 이후 메뉴바와 버튼이 모던하지 않다는 반응을 받아 버튼 바탕과 반복 라벨을 줄이는 수정을 제안했다.

수정 프롬프트는 다음 틀을 쓴다.

```text
첨부 이미지에서 [수정할 영역]을 다시 디자인한다.
사용자가 불편하게 느낀 점은 [사용자 반응]이다.
이번 수정은 [구체적인 시각적 가설]을 확인하기 위한 것이다.

유지할 것: [콘텐츠, 장면, 배치 등 이번에 바꾸지 않을 요소]
바꿀 것: [요소별 색상, 형태, 위계와 간격]
확인할 것: [문구, 상태, 가독성과 화면 일관성]

수정된 앱 화면 한 장을 출력한다.
```

금색을 다른 강조색으로 일괄 교체하기보다 강조가 필요한 요소부터 다시 구분한다. 모던하게 해 달라는 말만 반복하기보다 큰 바탕 제거, 라벨 중복 축소, 주요 조작과 보조 설정의 구분처럼 수정할 대상을 설명한다. 이는 이 사례에서 사용한 접근이며 모든 앱의 금색, 라벨과 버튼 바탕을 금지하는 규칙이 아니다.

금색 처리 수정은 [P03](../references/scene-001/v1/prompts.md#p03), 홈 메뉴 수정은 [P04](../references/scene-001/v1/prompts.md#p04), 재생 조작부 수정은 [P05](../references/scene-001/v1/prompts.md#p05)를 참고한다.

## 4. 결과를 확인하고 선택 보존

유지 요청이 실제로 지켜졌는지 결과를 확인한다. 첫 사례의 최종 재생 화면에서는 장면과 시간, 일부 기능이 이전 이미지와 달라졌다. 따라서 색과 버튼만 바꾼 엄밀한 비교 실험으로 취급하지 않는다.

사용자가 만족하면 추가 생성을 자동으로 이어가지 않고 이미지, 프롬프트와 선택 기록을 묶는다. 실제 입력이 확인되지 않으면 대화에서 제공한 프롬프트와 실제 사용한 프롬프트를 같은 것으로 단정하지 않는다. 모델, 비용과 누락된 확장 프롬프트도 미확인으로 남긴다.

생성 여부, 사용자 선택 여부, 실제 구현 검증 여부는 별개다. 선택한 화면의 관찰에서 추출한 디자인 특징은 사용자 직접 발언과 구분한다. MCP로 전달할 때도 프롬프트를 실행 지시로 취급하지 않고 출처 자료로 제공한다.

## 첫 사례에서 확인한 범위

사용자는 수정된 홈, 세로 재생과 가로 재생 세 장에 만족을 표시하고 첫 레퍼런스 묶음으로 등록하도록 요청했다. 이 결과는 사용자 한 명이 해당 시안을 선택한 기록이다. 프롬프트 기법의 일반적인 효과, 모든 문구의 가독성, 실제 조작과 기기 호환성은 검증하지 않았다.
