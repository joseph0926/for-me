# 장면의 홈 미리보기, 최근 영상 목록, 외부 자막 성능 비교

장면 0.6.1에 세 개선을 반영했다. 시험 영상 한 편을 기준으로 미리보기 추출은 절반으로 줄었고, 재생 중 최근 목록 조회는 사라졌고, 외부 자막 조회는 약 95% 줄었다. 홈에서 두 카드가 준비되기까지의 시간은 단축을 확인하지 못했다.

## 측정 결과

각 빌드에서 18초 영상을 세 번 재생했다. 표에서 괄호는 세 회차의 최솟값과 최댓값이다. 대사 전환 오차는 한 빌드에서 관측한 18번의 전환을 기준으로 계산했다. [회차별 측정값과 자막 전환 시각](evidence/performance-2026-11-26/measurements.csv)

| 지표 | 기존 0.6.0 중앙값 | 개선 중앙값 |
| --- | ---: | ---: |
| 홈에서 같은 영상 프레임 추출 | 2회 (2~2) | 1회 (1~1) |
| 프레임 추출 시간의 합 | 104.7ms (85.3~142.6) | 42.3ms (40.4~45.2) |
| 홈을 열어 두 카드의 이미지가 준비될 때까지 | 349ms (330~410) | 361ms (337~583) |
| 재생 중 최근 목록 조회 | 10회 (10~10) | 0회 (0~0) |
| 재생 중 0초보다 큰 위치를 저장한 횟수 | 9회 (9~9) | 9회 (9~9) |
| 외부 자막 표시 여부 조회 | 354회 (352~354) | 16회 (12~17) |
| 예정된 자막 경계에서 화면 반영 시 읽은 재생기 시각까지 | 150ms (25~276) | 109ms (25~234) |

**미리보기.** 같은 영상의 두 카드가 진행 중인 추출 작업을 공유한다. 각 카드가 사라지면 대기에서 빠지고 마지막 카드까지 사라지면 작업을 취소한다. 모든 회차에서 두 카드가 이미지를 받았다. 추출에 쓴 시간의 합은 약 60% 줄었다. 홈 전체 대기 시간에는 목록 조회와 화면 구성도 들어가므로 별도 지표로 유지한다.

**최근 영상.** 홈과 보관함에 있을 때만 목록을 구독한다. 재생기를 열 때는 선택한 영상의 제목만 넘긴다. 여섯 회차 모두 중간 위치를 9회 저장했고, 끝난 뒤 홈에는 해당 영상의 갱신된 0초 기록이 나타났다. 데이터베이스 구조와 저장 주기는 그대로 사용한다.

**외부 자막.** 현재 대사와 다음 시작 또는 종료 시각을 함께 구해 그 경계에서 재생기 시각을 다시 확인한다. 겹친 대사는 먼저 끝나는 줄도 다음 경계로 계산한다. 여섯 회차 모두 여섯 번의 전환이 예정된 순서로 나타났다. 측정 지점은 화면 구성을 마친 시점이다. 실제 휴대폰의 화면 출력 지연, 배터리 사용량, 프레임률은 측정하지 않았다.

## 측정 조건

기준은 장면 0.6.0이다. 같은 Android 가상 기기에서 기존 코드와 개선 후보에 같은 측정 코드를 넣고 실행한다. 제품 앱과 다른 앱 ID로 시험 영상을 열어 기존 재생 기록과 파일 권한을 보존한다.

| 항목 | 측정 구간 | 비교할 값 | 지켜야 할 동작 |
| --- | --- | --- | --- |
| 홈 미리보기 | 앱 프로세스를 새로 시작해 최근 영상 한 편이 홈 상단과 이어보기 카드에 함께 나타날 때 | 실제 영상 프레임 추출 횟수, 추출에 걸린 시간의 합 | 두 카드에 같은 장면이 나타난다. |

각 빌드를 세 번씩 실행하고 회차별 수치와 중앙값을 남긴다. 글꼴은 미리 준비하고 홈 미리보기의 메모리 캐시는 매회 비운다. 로그에는 시험 데이터의 시각과 횟수만 남긴다. 결과는 가상 기기에서 관측한 범위로 한정한다.

### 반복 방법

1. Android 17(API 37, arm64-v8a) 시험 기기를 4코어, 540×1200, 210dpi로 실행한다. 화면의 논리적 크기는 기존 1080×2400, 420dpi 기기와 같다. 제품 앱과 분리한 시험 앱 ID는 `dev.forme.video.perftrial`이다.
2. 360×640 H.264, 초당 24프레임, 18초 길이의 무음 시험 영상 한 편을 준비한다. SRT에는 A를 1.5~5초, B를 4~8초, C를 11~15초로 지정한다. 따라서 화면에서 관찰할 순서는 A, A와 B, B, 빈 화면, C, 빈 화면이다.
3. 같은 시험 앱에 빌드를 덮어 설치하고 프로세스를 새로 시작한다. 시험 영상의 저장 위치를 0으로 맞추고 글꼴 준비가 끝나면 홈을 연다. 두 카드의 이미지가 준비되고 0.5초 뒤에 같은 영상을 연다. 재생이 끝나면 홈으로 돌아와 갱신된 기록을 확인한다.
4. 예열 1회 뒤에 기존, 개선, 개선, 기존, 기존, 개선 순서로 실행한다. 프레임 추출은 파일을 열고 장면을 읽고 추출기를 닫기까지 잰다. 동시에 추출한 시간도 더하므로 시간의 합과 사용자가 두 카드를 기다린 시간을 따로 기록한다.
5. Room이 실제 실행하는 SQL 중 최근 20개 조회만 세고, 위치 저장은 데이터베이스 호출이 성공한 뒤에 센다. 자막은 표시 여부를 계산한 횟수를 세고, Compose가 다른 대사를 화면에 반영할 때 재생기 시각을 읽는다. 이 시각은 물리적 화면 출력 시각과 차이가 있을 수 있다.

### 예비 측정에서 제외한 회차

기존 1코어 가상 기기의 첫 집계는 로그 앞 공백을 처리하지 못해 비었다. 다음 시도에서는 앱 시작 직후 프로세스를 찾지 못하거나 오래된 로그가 이미 사라져 구간을 식별하지 못했다. 시작 전부터 로그를 수집하자 느린 회차에서 홈을 연 지 2.5초 뒤에도 미리보기 두 장이 아직 준비되지 않은 사실을 확인했다. 그 회차들은 정식 비교에서 제외했다. 시험 기기를 분리하고 두 카드의 준비 신호를 기다리는 조건을 양쪽에 똑같이 적용했다.

### 다시 측정하기

기준 소스는 저장소 커밋 `18aabd1`의 `apps/video`이고 비교 대상은 0.6.1의 같은 폴더다. 각각 별도 임시 사본을 준비한다. 공통 측정 패치는 시험 파일 제공자, 홈 준비 신호, 실제 SQL 및 위치 저장 계수를 추가한다. 자막 패치는 두 버전의 조회 위치에 같은 로그를 넣는다. [공통 측정 패치](evidence/performance-2026-11-26/measurement.patch) / [기존 자막 측정 패치](evidence/performance-2026-11-26/subtitle-before.patch) / [개선 자막 측정 패치](evidence/performance-2026-11-26/subtitle-after.patch)

각 임시 사본의 `apps/video` 위치에서 공통 패치와 해당 버전의 자막 패치를 차례로 `patch -p1 -i <패치 경로>`로 적용한다. 아래 명령으로 시험 영상을 만들고 `./gradlew --offline :android:assembleDebug`로 빌드한다.

```sh
ffmpeg -hide_banner -loglevel error -f lavfi -i testsrc2=size=360x640:rate=24 \
  -t 18 -an -c:v libx264 -threads 2 -pix_fmt yuv420p -movflags +faststart \
  android/src/main/assets/ab-video.mp4
```

시험 기기에 각 APK를 덮어 설치한다. 매회 시험 앱을 강제 종료하고 `adb logcat -T 1 -v monotonic -s SceneMeasure:I`로 수집을 시작한 뒤 `adb shell am start -W -n dev.forme.video.perftrial/dev.forme.video.MainActivity`로 연다. 기기가 여러 대면 모든 명령의 `adb` 뒤에 `-s <시험 기기 식별자>`를 넣는다. `home MARK`부터 두 `CARD_READY`까지의 시간, `home EXTRACT`의 나노초, `play RECENT_SQL`, `SAVE`, `LOOKUP`, `CUE`와 `return FIRST`를 집계한다. 완료 직후 저장하는 0초는 중간 위치 저장에서 제외한다.

정식 측정에 사용한 APK의 SHA-256은 기존 `39347b3c289a16b842f2ec52eeaf46322111a34487e45bae3130ea8a4b5c0776`, 개선 `bcbc6da00d8a772fb1bf0a5658acbb50c90052220c4974f0145cf5bb600d7f1f`이다. 두 측정용 APK의 버전 표시는 0.6.0이었다. 시험 MP4는 `8bdb4857e6e177e07f6d52889c7f7ef65863210a0591a7034e76c3a526bba1ca`이다.

## 동작 확인과 제품 빌드

- 별도 조작 검사에서 동일한 시험 영상을 일시정지하고 12초로 이동하자 C가 표시됐다. 4.25초로 되돌리자 A와 B가 함께 나타났다. 자막을 1초 늦추자 A만 표시됐고 지연을 해제하자 A와 B가 다시 표시됐다.
- 2배속으로 재생한 뒤 마지막 자막이 끝난 구간에서 11.4초로 되돌리자 C가 다시 나타났다. 0.5배속으로 바꿨다가 멈추고 4.25초로 이동해 홈으로 돌아오자, 갱신된 최근 영상 기록에 4.25초가 저장됐다. 이 검사는 재생기 조작 함수를 호출해 확인했다.
- 제품 0.6.1(빌드 번호 601)의 단위 테스트 57개가 통과했다. Android Lint는 오류와 경고 0건이고 디버그와 서명하지 않은 릴리스 빌드가 통과했다. 별도 사본에서 겹친 대사의 종료 시각을 잘못 계산하도록 바꿨을 때 새 자막 검사가 실패한 것도 확인했다.
- 사용 중인 Android 17 가상 기기 `Medium_Phone_API_37.0`에 제품 디버그 APK를 덮어 설치하고 앱을 열었다. 설치 전후 재생 기록 2개의 전체 열과 파일 읽기 권한 2개의 대상 및 권한이 일치했다. 설치본과 디버그 APK의 SHA-256은 `a39fec898e2e6dda472b2b95ec3df7cc533f884858420480507263019d04787b`, 릴리스 APK는 `cfc8857c5d10410ed87b042a865d23b4c025ce466397301b56a971d388d779a2`이다.
