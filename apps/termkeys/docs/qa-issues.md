# QA 이슈

확인되지 않은 환경 제약과 앱 결함을 구분합니다. 수정 후에는 최초 조건과 영향받는 동작을 새 빌드로 검사하고 후속 결과를 덧붙입니다.

## QA-001 보안 키보드 입력이 해제 후 다시 표시됨

- 상태: 0.1.0 방식 중단. 0.2.0에서 보안 입력 중 실제 이동과 다른 입력 영역 보존 재검증 통과. 0.2.1에서도 보안 입력 중 줄 이동 확인. 보안 입력 체크가 다시 생기는 원인은 미확정이며 보안 메뉴 자체를 수정한 것은 아님.
- 최초 우선순위: 높음. 0.1.0 당시 보안 입력 상태에서 핵심 기능을 시험할 수 없었음.
- 환경: 2026-11-16, macOS 27.2.1, Terminal 2.15(488.9), TermKeys 0.1.0.
- 최초 관찰: 사용자가 보안 키보드 입력 체크를 해제했다고 답했지만, 에이전트는 상태 갱신 주기 이후에도 `secure-input`을 표시함.
- 사용자 후속 보고: 해제해도 체크가 다시 생김.
- 조사: `defaults read com.apple.Terminal SecureKeyboardEntry`는 `0`. I/O Registry의 보안 입력 관련 PID는 1935였고, 해당 프로세스는 Terminal이었음. 이 비공식 진단 값만으로 원인을 확정하지 않음.
- 조사: Terminal 하위 프로세스의 이름과 TTY 입력 모드만 확인함. zsh와 Codex 실행 세션이 있었고, 확인한 4개 TTY는 echo와 canonical 모드가 모두 꺼져 있었음. 입력 내용과 명령어 인수는 읽지 않음. 이 결과를 특정 프로그램이 원인이라는 증거로 간주하지 않음.
- 당시 다음 확인: 기존 작업을 유지한 상태에서 새 Terminal 창에서도 해제 후 상태가 유지되는지 확인. 결과는 아래 후속 확인에 기록함.
- 보존 경계: Terminal과 하위 세션을 강제 종료하거나, 보안 설정을 강제로 바꾸거나, 설정 파일을 초기화하지 않음.

보안 입력이 활성인 동안 변환을 중지하는 것은 0.1.0의 설계였습니다. 당시 실제 키 이동을 확인하지 못해 핵심 기능 검증 완료로 판정하지 않았습니다. 0.2.0부터는 단축키를 직접 등록하는 방식으로 바꿨습니다.

### 후속 확인

- 새 Terminal 창에서도 사용자가 `secure-input`을 확인했습니다.
- 이후 TermKeys를 `off`한 상태에서 독립 프로세스가 공개 API `IsSecureEventInputEnabled`를 조회하니 `false`였습니다. 같은 시점의 I/O Registry에는 보안 입력 PID 항목이 없었습니다.
- TermKeys를 다시 `on`한 뒤 PID 4797이 `ready`를 표시했습니다.
- 앞선 활성 상태가 해제된 정확한 계기는 확인하지 못했습니다. 한 번의 상태 전환만으로 TermKeys가 원인이었거나 문제가 해결됐다고 판정하지 않습니다. 최초 실패 기록은 유지합니다.
- 후속 상태 확인에서 같은 PID 4797이 다시 `secure-input`을 표시했습니다. 사용자의 `abcdef` 입력 후 Command 좌우 이동 검사도 기대한 결과가 나오지 않았습니다. 실제 이동 검사는 실패로 기록합니다.
- 사용자가 Terminal을 완전히 종료하고 다시 실행하기로 했습니다. 요청에 따라 당시 TermKeys를 활성 상태로 유지했습니다. 이 시점에는 Terminal 재시작 후 검사를 기다렸으며 이슈는 미해결이었습니다.

### 0.2.0 단축키 등록 방식 실험

사용자 승인으로 기존 기록을 보존하고 `RegisterEventHotKey` 방식으로 교체했습니다. 새 앱의 손쉬운 사용 권한은 기존 항목을 제거하고 현재 앱을 다시 추가한 뒤 반영됐습니다. PID 18734에서 보안 입력 켜짐과 두 단축키 등록을 확인했습니다. 이 단계에서는 등록만으로 QA-001을 해결 처리하지 않고 같은 입력 조건의 실제 이동 검사 결과를 기다렸습니다.

후속 재검증에서 사용자가 보안 입력을 켠 채 두 번 모두 `XabcdefY`를 확인했습니다. 통지와 전송 요청도 각각 4회였습니다. 터미널 검색창과 다른 앱에서는 기존 동작이 유지됐고 통지 횟수는 증가하지 않았습니다. 현재 환경의 키 이동 불가 증상은 새 방식으로 해소된 것으로 기록합니다. 보안 체크 재활성 원인은 여전히 미확정이고 최초 실패 이력은 보존합니다. 빌드 식별값과 검증 범위는 [검증 기록](verification.md)에 있습니다.

### 0.2.1 후속 확인

보안 입력을 켠 상태에서 사용자가 `XabcdefY`를 확인했습니다. 0.2.1에서도 줄 이동은 성공했지만 메뉴 입력 제외 여부와 실제 응답 지연 조건은 QA-002와 QA-003의 미검증 항목으로 남깁니다.

## QA-002 메뉴 알림 등록 실패를 무시함

- 최초 보고: 2026-11-16 사용자 리뷰, P2. 0.2.0은 메뉴 열기와 닫기 알림 등록의 결과를 무시하고 감시 시작 성공을 반환함. 리뷰의 오류 주입에서 성공 반환을 확인했다고 보고됨.
- 영향: 메뉴가 열려 있는데도 입력 영역으로 판단해 단축키를 예약할 수 있음.
- 0.2.1 수정: 초점과 창 변경, 메뉴 열기와 닫기 네 알림을 모두 필수로 처리함. 하나라도 실패하면 이미 등록한 알림을 정리하고 실패를 반환해 단축키를 등록하지 않음.
- 상태: 수정 빌드의 실제 Agent 코드에서 메뉴 알림 각각의 실패와 복구, 부분 등록 정리 검사 통과. 실제 메뉴 조작 조건의 재검증 전까지 해결로 확정하지 않음.

후속 확인: 사용자는 0.2.1에서 메뉴에 이상이 없고 메뉴를 닫은 뒤 줄 이동도 성공했다고 보고했습니다. 다만 통지 횟수가 1회에서 6회로 증가해 메뉴 입력이 제외됐는지 합계로 확정하지 못했습니다. 메뉴만 분리한 검사는 사용자가 나중에 하기로 했으며, 이슈를 해결로 닫지 않습니다.

## QA-003 하위 접근성 객체의 대기 제한 누락

- 최초 보고: 2026-11-16 사용자 리뷰, P2. 0.2.0은 앱 객체에만 50ms 제한을 설정했고 입력 요소와 창의 조회에는 해당 제한이 적용되지 않음.
- 영향: 동기 조회가 지연되면 같은 실행 루프의 초점 변경 처리와 단축키 해제가 늦어질 수 있음.
- 0.2.1 수정: 각 속성 조회 직전에 실제 수신 객체에 50ms 제한을 설정하고 성공 여부를 검사함. 설정 실패나 조회 오류 시 즉시 중단함. 조회 후 앱이 바뀌었는지도 확인한 뒤 등록함.
- 경계: 제한은 호출별이며 전체 조회의 50ms 완료를 보장하지 않음. 정상 경로에 최대 네 번의 속성 조회가 있음.
- 상태: 수정 및 오류 주입 검사 통과. 입력 요소와 창의 지연 응답, 대기 제한 설정 실패 시 중단을 확인함. 실제 앱이 응답하지 않는 조건은 미검증으로 유지함.
