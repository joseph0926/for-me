# 검증 기록

## 0.4.3 문장 속 괄호 주소

사용자는 0.4.2에서 별도 줄에 표시한 세 샘플은 열렸지만 `MDN 지문 (주소)을 다시 보며`의 주소는 열리지 않았다고 보고했습니다. 당시 실행 중인 앱은 클릭 수신을 등록했고 마지막 결과는 클릭 위치에서 웹 주소를 확인하지 못했다는 것이었습니다. 상태에는 주소가 없어 그 결과를 특정 클릭과 연결할 수는 없습니다.

0.4.3 자동 검사에서는 보내 준 문장의 각 글자 위치를 검사했습니다. 주소 안에서는 어디를 눌러도 원래 MDN 주소와 끝의 `#microtasks`가 반환됐고, 공백과 바깥 괄호 및 조사에서는 주소가 반환되지 않았습니다. 한 줄에 주소가 두 개인 경우, 주소 안에 괄호나 한글이 있는 경우, 바깥 괄호가 닫히지 않은 경우를 포함해 전체 검사 326개가 통과했습니다. 해당 문장을 실제 터미널에서 클릭해 브라우저가 열린 결과는 미확인입니다.

## 0.4.2 같은 링크의 클릭 누락

사용자는 같은 화면에서 같은 주소를 눌러도 간헐적으로 열리지 않는다고 보고했습니다. 확인 당시 0.4.1은 보안 입력이 켜진 상태에서 클릭 수신을 등록한 상태였습니다. 실패 순간의 동작은 기록되지 않았습니다.

같은 MDN 주소의 88개 위치를 다섯 번씩 검사해 모두 같은 전체 주소를 얻었습니다. 별도의 모의 입력 검사에서 0.4.1은 포인터 위치가 고정된 클릭을 20번 모두 받았고, 놓는 위치가 1포인트 달라진 클릭은 20번 모두 취소했습니다. 1포인트 이동 통지가 포함돼도 결과는 같았습니다.

0.4.2에서는 두 위치가 같은 주소에 있고 시작점으로부터 2포인트 안에 있으면 클릭을 허용합니다. 수정 후 위 세 조건에서 각각 20번 모두 클릭으로 판정했습니다. 3포인트 이동 후 돌아온 입력과 가로세로 각각 2포인트 이동한 입력은 각각 20번 모두 제외했습니다. 이 결과는 모의 입력에 대한 결과이며 사용자가 겪은 실패 원인과 실제 브라우저 열기는 미확인입니다.

자동 검사 201개를 세 번 연속 통과했습니다. 주소 확인 실패, 드래그 취소, 두 위치의 주소 불일치, 열기 직전 주소 변경, macOS 열기 요청의 수락과 거절을 모의 입력으로 구분했습니다. 일반 클릭 후에는 마지막 결과가 유지됐고, 이전 형식의 상태 파일도 읽었습니다.

0.4.2 빌드 8을 설치한 뒤 실행 파일이 빌드 결과와 일치하고 서명이 유효한지 확인했습니다. 설치 직후 자동 실행은 켜졌고 손쉬운 사용 권한을 기다리는 상태였습니다. 이때 `termkeys status`는 이번 실행에서 받은 ⌘ 클릭이 없다고 표시했습니다.

## 0.4.1 괄호로 감싼 단독 주소

사용자는 제목 다음 줄에 괄호로 표시된 MDN 주소가 열리지 않았다고 보고했습니다. 원문의 들여쓰기와 줄바꿈을 보존한 검사에서 0.4.0은 주소 부분을 눌러도 목적지를 반환하지 않았습니다.

0.4.1(빌드 7)에서는 같은 문장의 주소 시작, 경로와 `#microtasks` 위치가 모두 원래의 전체 주소로 판별됐습니다. 제목, 들여쓰기와 바깥 괄호는 제외됐습니다. 주소 안에 괄호가 있는 경우와 문장 속 주소를 포함한 전체 자동 검사 169개가 통과했습니다. 실제 기본 터미널에서 이 MDN 주소를 다시 클릭한 결과는 미검증입니다.

## 0.4.0 링크 목적지와 단독 주소

2026-11-19, macOS 27.2.1. 사용자는 Mac 기본 터미널의 Command 더블 클릭에서도 문장 속 주소 뒤의 ‘까지만’이 함께 열렸다고 보고했습니다. 0.3.1의 주소 판별 코드에서 같은 문장을 클릭 대상으로 삼는 오류를 자동 검사로 재현했습니다.

0.4.0(빌드 6)에서 자동 검사 155개와 최적화 빌드, 서명 검사가 통과했습니다. 링크 요소와 해당 글자의 링크 속성이 제공한 웹 주소, 한글이 포함된 단독 주소, 여러 줄 사이의 주소, 본문 밖 요소와 파일 주소 거절, 조회 실패를 확인했습니다. 손쉬운 사용 응답과 브라우저 열기 요청은 검사에서 대체했습니다.

검사 프로세스는 실행 중인 Terminal을 확인했지만 손쉬운 사용 권한과 입력 전송 권한이 없었습니다. Terminal 2.15가 실제 출력의 링크 목적지를 제공하는지와 클릭 후 브라우저가 한 번 열리는지는 미검증입니다.

설치 후 사용자 실험에서 한 줄에 단독으로 쓴 주소(2번)는 열렸고, 문장 속 주소(3번)는 열리지 않았습니다. 마크다운 링크 이름(1번)은 눌러도 열리지 않았습니다. 터미널에 링크 이름과 목적지를 직접 출력하는 4번 실험의 결과는 아직 없습니다.

후속 실험에서 사용자는 기본 터미널의 셸에서 `printf`로 목적지를 지정한 링크(4번)를 출력하고 ‘문제 열기’를 Command 한 번 클릭했으나 열리지 않았습니다. Codex를 거치지 않아도 같은 현상이 나타났습니다. 이 클릭에서 손쉬운 사용 기능이 반환한 값은 수집하지 않아 실패 지점은 미확인입니다.

## 2026-11-16 설치와 명령어 검증

사용자 승인 후 `~/Applications/TermKeys.app`, `~/.local/bin/termkeys`에 설치하고 자동 실행을 등록했습니다. 설치된 바이너리의 SHA-256은 위 빌드와 일치했고 서명 검사가 통과했습니다. 현재 셸에서 `termkeys` 명령어를 찾을 수 있습니다.

- 최초 `on`: 실제 에이전트 PID 96067로 시작하고 `permission-required`를 표시했습니다.
- 사용자가 TermKeys의 손쉬운 사용 권한을 허용했습니다.
- `off` 두 번: 모두 성공하고 꺼짐 상태를 확인했습니다.
- `on` 두 번: 모두 성공하고 PID 96353을 유지했습니다. 중복 프로세스를 만들지 않았습니다.
- 이후 실제 로그인 세션에서 `status`: `secure-input`. 권한 대기를 벗어났으나 보안 키보드 입력이 활성 상태여서 변환을 중지했습니다.
- 샌드박스 안의 `status`는 프로세스 존재 확인이 제한되어 상태 미확인으로 표시됐습니다. 샌드박스 밖에서 위 상태를 확인했습니다.

권한 미허용 상태와 허용 후 상태 전환, 반복 켜기와 끄기는 확인했습니다. 실제 이동, 권한 회수, 보안 키보드 입력 해제 후 복구, 로그아웃 후 상태 유지, 업데이트와 파일 충돌 경로는 아직 미검증입니다. 자동 실행은 등록까지 확인했고 다음 로그인의 실행은 확인하지 않았습니다.

사용자는 보안 키보드 입력을 해제해도 체크가 다시 생긴다고 보고했습니다. 상태 갱신 이후에도 `secure-input`이 유지됐고, [QA-001](qa-issues.md#qa-001-보안-키보드-입력이-해제-후-다시-표시됨)에 최초 관찰과 조사 범위를 기록했습니다.

후속으로 `ready`가 한 번 관찰됐으나 같은 프로세스가 다시 `secure-input`으로 바뀌었습니다. 사용자의 실제 입력 검사에서 기대한 `XabcdefY`가 나오지 않았습니다. 실제 키 이동은 실패이며, 지원 완료로 처리하지 않습니다. 사용자가 Terminal을 종료 후 재실행하기로 했고, TermKeys는 요청대로 활성 상태를 유지합니다. 재시작 후 검증은 대기 중입니다.
