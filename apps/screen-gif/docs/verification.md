# 화면 녹화 GIF 생성기 검증 기록

실행한 검사와 결과를 날짜별로 남깁니다. 실제 녹화와 PC 동작은 아직 미검증입니다. 발견한 문제는 [QA 이슈](qa-issues.md)에서 관리합니다.

## 2026-11-14 1차 완료 확인

사용자가 끊김 수정, 저장 폴더 변경과 녹화 범위 테두리를 `pnpm tauri dev`로 확인하고 1차 완료로 판정했습니다. 저장된 GIF를 Windows GDI+로 읽은 값입니다.

| 파일 | 폴더 | 크기 | 프레임 | 길이 | 초당 프레임 | 용량 |
|---|---|---|---|---|---|---|
| `screen-gif-20261114-224459.gif` | `사진\screen-gif` | 2217×997 | 49 | 6.70초 | 7.3 | 3.34MB |
| `screen-gif-20261114-225454.gif` | `~/.screen-gif` | 1828×958 | 50 | 6.78초 | 7.4 | 2.85MB |

- 통과: 끊김 수정 뒤 초당 프레임이 1.2에서 7.3으로 늘었고 사용자가 좋아졌다고 확인했습니다(QA-002 완료).
- 통과: 저장 폴더 변경 뒤 녹화가 `~/.screen-gif`에 저장됐습니다.
- 사용자 확인: 녹화 범위 테두리. 테두리가 GIF에 나오지 않는지는 프레임을 열어 따로 확인하지 않았습니다.
- 미검증: 창을 눌러 녹화, 트레이 메뉴의 정지(QA-001의 남은 확인), 취소, 창 이동과 가림과 최소화, 화면 배율, 릴리스 빌드

## 2026-11-14 저장 폴더와 녹화 범위 테두리

사용자가 끊김이 나아졌다고 확인한 뒤 두 가지를 요청했습니다. 저장 폴더를 `~/.screen-gif`로 바꾸고, 녹화하는 동안 녹화 범위를 테두리로 보여 주되 결과에는 나오지 않게 했습니다. 테두리 창은 조작 막대와 같은 방식(`WDA_EXCLUDEFROMCAPTURE`)으로 녹화에서 빠지고, 클릭을 통과시키며, 창 녹화에서는 창을 따라갑니다.

- `cargo test --workspace` 18개 통과, `cargo clippy --workspace --all-targets` 경고 0개, `pnpm build` 통과, 앱은 별도 빌드 폴더에서 빌드 통과
- 미검증: 테두리가 화면에 보이고 GIF에는 나오지 않는지, 테두리가 클릭을 막지 않는지, 창을 옮길 때 따라가는지, `~/.screen-gif`에 저장되는지

## 2026-11-14 끊김 원인 측정과 수정

사용자가 첫 녹화 GIF가 버벅인다고 보고했습니다([QA-002](qa-issues.md#qa-002-화면이-많이-바뀌면-gif가-심하게-끊김)). 2077×1008 프레임 12장 중 1280×720 영역이 매 프레임 바뀌는 그린 화면으로 변환 시간을 쟀습니다. 앞의 두 장을 뺀 프레임당 평균입니다.

| 빌드 | 기본 모드 | 품질 모드 |
|---|---|---|
| 수정 전 디버그 | 1172ms | 6022ms |
| 수정 전 릴리스 | 118ms | 521ms |
| 수정 후 개발 빌드(인코더 최적화) | 86ms | 541ms |
| 수정 후 릴리스 | 70ms | 521ms |

- 수정 전 릴리스 기본 모드의 단계별 시간(12장 합): 바뀐 영역 찾기 22ms, 팔레트 만들기 581ms, 색 찾기 708ms, GIF 쓰기 109ms
- 색 찾기를 여러 코어로 나눈 뒤에도 같은 입력의 출력 해시가 같았습니다(기본 `2b8c622b17a21058`, 품질 `efe302e2d2108796`).
- `cargo test --workspace`: 18개 통과(인코더 10, 앱 8). 넓은 영역을 여러 스레드로 나눠 처리하는 테스트와 큐 테스트는 구현에 결함을 넣었을 때 실패하는 것을 확인하고 되돌렸습니다.
- `cargo clippy --workspace --all-targets` 경고 0개. 앱은 별도 빌드 폴더에서 빌드해 통과를 확인했습니다.
- 미검증: 수정 빌드로 같은 화면을 다시 녹화해 프레임 수가 늘었는지

## 2026-11-14 수정 빌드 첫 녹화

사용자가 QA-001을 고친 코드로 `pnpm tauri dev`를 실행해 드래그한 영역을 두 번 녹화했습니다. 환경은 아래 빌드 검증과 같은 PC입니다. 저장 결과는 `사진\screen-gif`에서 읽었고, 프레임은 Windows GDI+로 풀어 확인했습니다. 화면 내용이 담긴 프레임 파일은 확인 후 지웠습니다.

| 파일 | 크기 | 프레임 | 길이 | 용량 |
|---|---|---|---|---|
| `screen-gif-20261114-220933.gif` | 2077×1008 | 10 | 8.14초 | 1.70MB |
| `screen-gif-20261114-221022.gif` | 279×155 | 1 | 0.80초 | 2.9KB |

- 통과: 드래그한 영역이 녹화되고 정지 후 저장됨, 두 번째 녹화도 이어서 됨, 앱이 응답 상태를 유지함
- 통과: 첫 GIF의 가운데와 마지막 프레임을 열어 봤습니다. 가운데 프레임에 커서가 보이고, 두 프레임 모두 조작 막대와 노란 테두리는 보이지 않습니다. 조작 막대가 녹화 범위 안에 놓였는지는 기록이 없어 확인하지 못했습니다.
- 관찰: 화면이 바뀔 때만 프레임이 늘어 8초 동안 10장이 쓰였고, 바뀐 것이 없던 두 번째 녹화는 1장입니다.
- 관찰: 실행 로그에 `PostMessage failed ; is the messages queue full? Error code 0x80070578`이 두 번 나왔습니다. `wry` 0.57.2가 비동기 IPC 응답을 웹뷰 창으로 보내다 실패하면 디버그 빌드에서만 찍는 메시지입니다(`src/webview2/mod.rs`의 `dispatch_handler`). 녹화 시작 명령이 자신을 부른 선택 오버레이를, 정지 명령이 조작 막대를 닫아 응답 받을 창이 없어진 것으로 보이며, 녹화와 저장에는 영향이 없었습니다.
- 미검증: 창을 눌러 녹화, 트레이 메뉴의 정지, 취소, 창 이동과 가림과 최소화, 화면 배율, 노란 테두리가 실제 화면에 보였는지
- 남은 파일: 멈췄던 이전 실행이 강제 종료될 때까지 쓴 `.screen-gif-1794659667754.gif.part`(9.2MB)가 남아 있습니다. 끝맺음이 없는 미완성 GIF입니다.

## 2026-11-14 첫 실행 보고와 수정 빌드 확인

사용자가 `pnpm tauri dev`로 실행해 드래그로 영역을 고르자 녹화가 끝난 것처럼 보였다고 보고했습니다. 앱은 응답 없음 상태였고 0바이트 `.part` 파일이 남아 있었습니다. 원인과 수정은 [QA-001](qa-issues.md#qa-001-드래그로-영역을-고르면-조작-막대가-뜨지-않고-앱이-멈춤)에 있습니다.

같은 날 Vite 개발 서버가 `target/` 아래 잠긴 빌드 파일을 감시하다 `EBUSY` 경고를 냈습니다. 감시 대상에서 `target/`, `src-tauri/`, `encoder/`를 뺀 뒤, 임시 Vite 서버를 띄운 채 Rust를 빌드해 비교했습니다. 고치기 전 설정은 `EBUSY` 8줄, 고친 설정은 0줄이었습니다.

수정한 코드로 실행한 검사:

- `pnpm build`: 통과
- `cargo test --workspace`: 13개 통과
- `cargo clippy --workspace --all-targets`: 경고 0개
- 앱 빌드: 응답 없는 앱이 `target/debug/screen-gif.exe`를 잡고 있어, 별도 빌드 폴더에서 빌드해 통과를 확인하고 지웠습니다.

실행하지 못한 검사: 수정 빌드로 드래그 영역 녹화를 다시 해 보는 것. QA-001은 재검증 대기입니다.

## 2026-11-14 Tauri 시제품 빌드 검증

환경: Windows 11 Home(빌드 26300), AMD Ryzen 7 9700X, Rust 1.100.0, Node.js 24.21.0, pnpm 12.9.0, Visual Studio Community 2022 C++ 도구, WebView2 157.0.4341.57

`apps/screen-gif` 폴더에서 실행했습니다.

```bash
pnpm build
pnpm tauri build --debug --no-bundle
cargo test --workspace
cargo clippy --workspace --all-targets
cargo fmt --check
```

- 화면: 타입 검사와 빌드 통과
- 앱: 디버그 실행 파일 `target/debug/screen-gif.exe` 빌드 통과
- 테스트: 인코더 9개, 앱 4개(사각형 겹침 계산 2개, 크기가 바뀐 프레임 맞추기 2개) 통과
- clippy 경고 0개, 포맷 차이 없음

실행하지 못한 검사:

- 실제 녹화. 앱을 실행해 트레이 메뉴, 선택 오버레이, 조작 막대를 조작하려 했으나 컴퓨터 사용 권한 요청이 거절되어 진행하지 않았습니다. 실행 파일을 띄운 직후 프로세스가 살아 있는 것만 확인하고 종료했습니다.
- 아래 항목은 실제 녹화로 확인해야 합니다.
  - 드래그한 영역과 누른 창이 각각 그 범위만 녹화되는지
  - 조작 막대와 선택 오버레이가 GIF에 나오지 않는지, 커서는 나오는지
  - 노란 캡처 테두리가 화면과 GIF에 나오는지. 앱은 지원하는 운영체제에서 테두리를 끄도록 요청합니다.
  - 녹화 중 창을 옮기거나, 다른 창으로 가리거나, 최소화하거나, 크기를 바꿀 때의 결과
  - 화면 배율이 100%가 아닌 모니터에서 드래그한 영역과 GIF 범위가 맞는지
  - 정지하면 `사진\screen-gif`에 저장되고 탐색기가 그 파일을 선택해 여는지, 같은 이름의 파일을 덮어쓰지 않는지
  - 취소하면 임시 파일(`.part`)이 남지 않는지

## 2026-11-14 GIF 인코더 로컬 검증

환경: Windows 11 Home(빌드 26300), AMD Ryzen 7 9700X, Rust 1.100.0(`rust-toolchain.toml`로 고정)

`apps/screen-gif` 폴더에서 실행했습니다.

```bash
cargo test
cargo clippy --all-targets
cargo fmt --check
```

- 테스트: 9개 통과, 실패 0개
- clippy 경고 0개, 포맷 차이 없음

테스트는 다음 동작을 확인합니다.

- 색이 적은 프레임을 다시 풀었을 때 원본과 같습니다. 바뀐 사각형 안에 바뀌지 않은 픽셀이 섞인 경우도 포함합니다.
- 첫 프레임 이후에는 바뀐 사각형만 씁니다.
- 색 줄이기를 거쳐도 바뀌지 않은 픽셀은 앞 화면 그대로 보입니다.
- 표시 시간이 프레임 시각을 따르고, 같은 화면이 이어지면 앞 프레임의 표시 시간이 늘어납니다.
- 2/100초보다 짧게 이어지는 프레임은 다음 프레임으로 대체되고, 대체된 화면이 앞 화면과 같아도 전체 재생 시간이 유지됩니다.
- 버퍼 길이가 틀리거나 시각이 앞 프레임보다 이르면 오류를 돌려줍니다.

각 테스트가 잘못된 동작을 잡는지 확인하려고 구현에 결함을 하나씩 넣어 실행했습니다.

| 넣은 결함 | 실패한 테스트 |
|---|---|
| 바뀐 사각형 대신 항상 전체 프레임을 씀 | 첫 프레임 이후 바뀐 사각형만 쓰는지 |
| 같은 프레임을 합치지 않음 | 같은 화면이 이어질 때 표시 시간 |
| 최소 표시 시간을 무시함 | 짧은 프레임 대체 |
| 투명 색 칸을 예약하지 않음 | 색이 적은 프레임 재현. 처음에는 이 결함을 잡는 테스트가 없어, 바뀐 사각형 안에 바뀌지 않은 픽셀이 섞이도록 테스트를 고친 뒤 확인 |
| 앞 화면으로 돌아온 프레임을 쓰지 않음 | 대체된 화면의 재생 시간 유지 |

결함을 넣은 코드는 확인 후 원래대로 되돌렸습니다.

크기와 화질 측정은 [기술 조사](research.md#결정-gif와-자체-인코더)에 있습니다. 그린 프레임으로 잰 값이며 실제 화면 녹화로는 확인하지 않았습니다.
