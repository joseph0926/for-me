## 2026-11-19 macOS 반복 녹화와 선택 화면 닫기

- macOS 27.2.1에서 같은 QA-004 앱을 사용했습니다. 실행 파일 SHA-256은 `251bf5c6ea383fb39d7ef73329e50cf7fd659e4c3a984a2d659d7f60399b84b4`입니다.
- 사용자는 홀수 회차에 취소, 짝수 회차에 정지를 눌렀고 “6번은 모두 정상, 마지막 열고 닫을때 esc로 안닫힘”이라고 확인했습니다. 여섯 번째 뒤에도 메뉴에서 선택 화면이 다시 열렸습니다.
- 저장 폴더에서 13:18:38, 13:19:01, 13:19:23에 생성된 크기 0보다 큰 GIF 세 개를 확인했습니다. 검사 당시 임시 파일(`.part`)은 없었습니다. GIF 내용은 열지 않았습니다.
- 최초 리뷰는 한 번의 녹화 시작에서 창 생성 오류를 확인했습니다. 취소나 정지 이후 남은 창의 표시 상태와 다음 메뉴 동작을 연결하지 못했고, 그 결과를 수정 전 실제 앱에서 반복 검사하지 않았습니다. 선택 화면의 Esc 자동 검사도 브라우저 안에서 키 이벤트를 직접 보내 macOS가 어느 창에 키를 전달하는지 확인하지 못했습니다.

별도 진단 앱에서는 메뉴 조작을 생략하고 같은 선택 창을 여섯 번 열었습니다. 창은 매번 보였지만 macOS의 키 입력 대상이 되지 않아 진단 도구가 Esc 전송을 건너뛰었습니다. 앱 활성화 방법을 바꾼 실험에서 키 입력 대상이 된 창은 앱 내부로 보낸 Esc로 닫혔습니다. 활성화 성공은 반복되지 않았고, 사용자 키보드로 누른 Esc가 어느 창에 갔는지는 확인되지 않았습니다. QA-005는 미해결로 남겼습니다.

## 2026-11-15 macOS 첫 구현 빌드 검증

환경: macOS 27.2.1(빌드 26B131), Apple 칩(arm64), Retina 내장 화면 하나(2560×1664), Command Line Tools(Swift 6.4.2, macOS SDK 27.2), Xcode 없음, Rust 1.100.0(Homebrew rustup 1.29.3), Node.js 24.22.1, pnpm 12.9.0

바꾼 내용:

- 운영체제별 코드를 나눴습니다. 창과 모니터 찾기는 `src-tauri/src/targets/`, 화면 캡처는 `src-tauri/src/recording/` 아래 `win32.rs`와 `macos.rs`에 있습니다. Windows 코드는 위치만 옮겼고, 창 식별자 이름을 `hwnd`에서 `id`로 바꿨습니다.
- macOS 화면 캡처는 `screencapturekit` 11.1.2입니다. 영역 녹화는 모니터 캡처에 잘라 낼 범위를 지정하고, 이 앱의 창을 캡처 필터에서 뺍니다. 녹화 간격(0.1초)과 캡처 큐 깊이(3)는 기본값이 문서마다 달라 직접 지정했습니다. 창 목록은 CoreGraphics(`CGWindowListCopyWindowInfo`)에서 앞에 놓인 창부터 받습니다.
- 화면 기록 권한이 없으면 선택 오버레이에 안내를 보이고 권한을 요청합니다.
- Dock 아이콘을 숨기고(활성화 정책 Accessory), 투명 창을 위해 `macOSPrivateApi`를 켰습니다. 저장 뒤에는 Finder에서 파일을 보여 줍니다.
- `src-tauri/build.rs`가 Swift 런타임 검색 경로(`/usr/lib/swift`)와 Command Line Tools의 Swift 호환 라이브러리 경로를 더합니다. 없으면 각각 연결 실패(`swiftCompatibility56`)와 실행 직후 종료(`libswift_Concurrency.dylib`를 찾지 못함)가 났습니다.

검사:

- `cargo test --workspace` 22개 통과(인코더 10개, 앱 12개). 새로 넣은 macOS 테스트 4개(색 순서와 줄 여분 처리, 짧은 데이터 거절, Retina 좌표 변환, 모니터 거리)는 구현을 일부러 틀리게 바꾸면 각각 실패하는 것을 확인하고 되돌렸습니다.
- `cargo clippy --workspace --all-targets` 경고 0개, `cargo fmt --all --check` 통과, `pnpm build` 통과
- `pnpm tauri dev`로 개발 빌드를 실행해 프로세스가 시작 뒤에도 유지되는 것을 확인했습니다. Claude 앱 안에서 실행해 화면 기록 권한이 그 앱에 붙기 때문에 녹화 메뉴는 누르지 않았습니다.

실행하지 못한 검사:

- Windows 빌드. 이 맥에서 Windows 대상 검사(`cargo check --target x86_64-pc-windows-msvc`)는 Tauri가 Windows 리소스 컴파일러(`llvm-rc`)를 요구해 멈췄습니다. 옮긴 Windows 코드는 이전 커밋과 비교해 이름 바꾼 곳만 다른 것을 확인했습니다.

사용자가 QA-001을 고친 코드로 `pnpm tauri dev`를 실행해 드래그한 영역을 두 번 녹화했습니다. 환경은 아래 빌드 검증과 같은 PC입니다. 저장 결과는 `사진\screen-gif`에서 읽었고, 프레임은 Windows GDI+로 풀어 확인했습니다. 화면 내용이 담긴 프레임 파일은 확인 후 지웠습니다.

|---|---|---|---|---|
| `screen-gif-20261114-220933.gif` | 2077×1008 | 10 | 8.14초 | 1.70MB |

- 통과: 드래그한 영역이 녹화되고 정지 후 저장됨, 두 번째 녹화도 이어서 됨, 앱이 응답 상태를 유지함

- 미검증: 창을 눌러 녹화, 트레이 메뉴의 정지, 취소, 창 이동과 가림과 최소화, 화면 배율, 노란 테두리가 실제 화면에 보였는지
- 남은 파일: 멈췄던 이전 실행이 강제 종료될 때까지 쓴 `.screen-gif-1794659667754.gif.part`(9.2MB)가 남아 있습니다. 끝맺음이 없는 미완성 GIF입니다.

## 2026-11-14 첫 실행 보고와 수정 빌드 확인

사용자가 `pnpm tauri dev`로 실행해 드래그로 영역을 고르자 녹화가 끝난 것처럼 보였다고 보고했습니다. 앱은 응답 없음 상태였고 0바이트 `.part` 파일이 남아 있었습니다. 원인과 수정은 [QA-001](qa-issues.md#qa-001-드래그로-영역을-고르면-조작-막대가-뜨지-않고-앱이-멈춤)에 있습니다.

같은 날 Vite 개발 서버가 `target/` 아래 잠긴 빌드 파일을 감시하다 `EBUSY` 경고를 냈습니다. 감시 대상에서 `target/`, `src-tauri/`, `encoder/`를 뺀 뒤, 임시 Vite 서버를 띄운 채 Rust를 빌드해 비교했습니다. 고치기 전 설정은 `EBUSY` 8줄, 고친 설정은 0줄이었습니다.

수정한 코드로 실행한 검사:

- `pnpm build`: 통과
- `cargo test --workspace`: 13개 통과
- `cargo clippy --workspace --all-targets`: 경고 0개
- 앱 빌드: 응답 없는 앱이 `target/debug/screen-gif.exe`를 잡고 있어, 별도 빌드 폴더에서 빌드해 통과를 확인하고 지웠습니다.

실행하지 못한 검사: 수정 빌드로 드래그 영역 녹화를 다시 해 보는 것. QA-001은 재검증 대기입니다.

## 2026-11-14 GIF 인코더 로컬 검증

환경: Windows 11 Home(빌드 26300), AMD Ryzen 7 9700X, Rust 1.100.0(`rust-toolchain.toml`로 고정)

`apps/screen-gif` 폴더에서 실행했습니다.

```bash
cargo test
cargo clippy --all-targets
cargo fmt --check
```

- 테스트: 9개 통과, 실패 0개
- clippy 경고 0개, 포맷 차이 없음

테스트는 다음 동작을 확인합니다.

- 색이 적은 프레임을 다시 풀었을 때 원본과 같습니다. 바뀐 사각형 안에 바뀌지 않은 픽셀이 섞인 경우도 포함합니다.
- 첫 프레임 이후에는 바뀐 사각형만 씁니다.
- 색 줄이기를 거쳐도 바뀌지 않은 픽셀은 앞 화면 그대로 보입니다.
- 표시 시간이 프레임 시각을 따르고, 같은 화면이 이어지면 앞 프레임의 표시 시간이 늘어납니다.
- 2/100초보다 짧게 이어지는 프레임은 다음 프레임으로 대체되고, 대체된 화면이 앞 화면과 같아도 전체 재생 시간이 유지됩니다.
- 버퍼 길이가 틀리거나 시각이 앞 프레임보다 이르면 오류를 돌려줍니다.

각 테스트가 잘못된 동작을 잡는지 확인하려고 구현에 결함을 하나씩 넣어 실행했습니다.

| 넣은 결함 | 실패한 테스트 |
|---|---|
| 바뀐 사각형 대신 항상 전체 프레임을 씀 | 첫 프레임 이후 바뀐 사각형만 쓰는지 |
| 같은 프레임을 합치지 않음 | 같은 화면이 이어질 때 표시 시간 |
| 최소 표시 시간을 무시함 | 짧은 프레임 대체 |
| 투명 색 칸을 예약하지 않음 | 색이 적은 프레임 재현. 처음에는 이 결함을 잡는 테스트가 없어, 바뀐 사각형 안에 바뀌지 않은 픽셀이 섞이도록 테스트를 고친 뒤 확인 |
| 앞 화면으로 돌아온 프레임을 쓰지 않음 | 대체된 화면의 재생 시간 유지 |

결함을 넣은 코드는 확인 후 원래대로 되돌렸습니다.

크기와 화질 측정은 [기술 조사](research.md#결정-gif와-자체-인코더)에 있습니다. 그린 프레임으로 잰 값이며 실제 화면 녹화로는 확인하지 않았습니다.
