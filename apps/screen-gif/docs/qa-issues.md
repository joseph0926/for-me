# QA 이슈

화면 녹화 GIF 생성기를 직접 조작하다 발견한 문제의 현재 상태와 다음 조치를 관리합니다. 검사 결과는 [검증 기록](verification.md)에 남깁니다. 번호, 우선순위, 상태와 완료 기준은 [동영상 앱 QA 이슈의 처리 기준](../../video/docs/qa-issues.md#처리-기준)과 같게 씁니다. 이 앱에서는 APK 대신 실행 파일과 빌드 방법으로 빌드를 식별합니다.

## 등록 이슈

### QA-001 드래그로 영역을 고르면 조작 막대가 뜨지 않고 앱이 멈춤

- 상태: 재검증 대기
- 우선순위: 높음
- 발견일: 2026-11-14. 사용자가 직접 실행해 보고했습니다.
- 영향: 영역을 고른 직후 선택 오버레이가 사라지고 조작 막대가 나오지 않아 녹화를 멈추거나 저장할 수 없습니다. 사용자에게는 녹화가 끝난 것처럼 보입니다.
- 기대 동작: 영역을 고르면 녹화가 시작되고 대상 근처에 조작 막대가 뜹니다.
- 재현: `pnpm tauri dev`로 앱을 처음 실행 → 트레이 메뉴의 녹화 → 드래그로 영역 지정.
- 증거: 보고 직후 확인한 상태입니다. 앱 프로세스가 Windows에서 "응답 없음"이었고, `사진\screen-gif`에 0바이트 `.screen-gif-1794659667754.gif.part`가 남아 있었습니다.
- 원인: 녹화 시작 명령(`start_recording`)이 동기 명령 안에서 조작 막대 창을 만들었습니다. Tauri의 `WebviewWindowBuilder::new` 문서는 Windows에서 이렇게 하면 교착 상태가 된다고 적고 있고, 증거와 맞습니다. 실제 재현으로 원인을 확정하지는 않았습니다.
- 수정: 창을 만들고 닫는 명령을 async로 바꿨고, 트레이 메뉴 처리기의 창 작업도 별도 스레드로 넘겼습니다. 조작 막대를 띄우지 못하면 녹화를 취소합니다.
- 재검증: 수정한 코드의 빌드와 자동 검사는 통과했습니다.
- 재검증 결과(2026-11-14, `pnpm tauri dev` 디버그 빌드): 사용자가 원래 순서(처음 실행 → 트레이의 녹화 → 드래그)로 두 번 녹화했고, 두 번 모두 GIF가 저장됐으며 앱은 응답 상태를 유지했습니다. 결과는 [검증 기록](verification.md#2026-11-14-수정-빌드-첫-녹화)에 있습니다.
- 남은 확인: 창을 눌러 녹화 시작, 트레이 메뉴의 정지. 이 두 경로도 바꾼 코드를 지나므로 확인한 뒤 완료로 닫습니다.

### QA-002 화면이 많이 바뀌면 GIF가 심하게 끊김

- 상태: 완료. 개발 빌드(`pnpm tauri dev`)에서 사용자가 확인한 범위입니다.
- 우선순위: 높음
- 발견일: 2026-11-14. 사용자가 녹화 중 게임 클라이언트 창이 뜬 부분이 버벅인다고 보고했습니다.
- 영향: 움직임이 많은 화면을 녹화하면 대부분의 화면이 빠져 GIF가 끊겨 보입니다.
- 기대 동작: 화면이 계속 바뀌는 동안 녹화 간격(초당 10프레임)에 가깝게 프레임이 남습니다.
- 재현: `pnpm tauri dev` → 2077×1008 영역 녹화 중 넓은 영역이 계속 바뀌는 창을 띄움. 결과 GIF가 8.14초 동안 10프레임으로 초당 1.2프레임이었습니다([검증 기록](verification.md#2026-11-14-수정-빌드-첫-녹화)).
- 원인: 캡처 콜백 안에서 GIF 변환까지 했고, `windows-capture`의 프레임 버퍼가 1개라 변환하는 동안 들어온 화면을 받지 못했습니다. 1280×720이 매 프레임 바뀌는 2077×1008 프레임을 측정하니 변환에 디버그 빌드에서 1172ms, 릴리스 빌드에서 118ms가 걸렸습니다. 디버그 값이 보고된 초당 1.2프레임과 맞습니다.
- 수정:
  - 캡처 콜백은 프레임 복사만 하고, 변환은 별도 스레드가 맡습니다. 둘 사이 큐는 8프레임까지 담고, 가득 차면 가장 오래된 프레임을 버려 마지막 화면은 남깁니다.
  - 인코더가 색 찾기를 여러 코어로 나눠 합니다. 같은 입력의 출력 바이트가 수정 전과 같은 것을 해시로 확인했습니다.
  - 개발 빌드에서도 인코더와 GIF 관련 크레이트(`gif`, `color_quant`, `weezl`)를 최적화합니다.
  - 같은 측정에서 변환 시간이 개발 빌드 86ms, 릴리스 빌드 70ms가 됐습니다.
- 남은 제한: 품질 모드는 팔레트 학습에만 프레임당 약 490ms가 들어 실시간 변환으로는 초당 2프레임 정도입니다. 지금 녹화는 기본 모드만 쓰며, 품질 모드는 자르기 기능과 함께 저장할 때 변환하는 구조에서 다룹니다.
- 재검증: 2026-11-14 수정 빌드로 사용자가 다시 녹화하고 좋아졌다고 확인했습니다. 결과 GIF는 2217×997, 6.70초, 49프레임으로 초당 7.3프레임입니다. 수정 전 같은 크기대의 녹화는 초당 1.2프레임이었습니다. 화면이 바뀔 때만 프레임이 생기므로 이 평균만으로 버린 프레임이 있었는지는 알 수 없습니다([검증 기록](verification.md#2026-11-14-1차-완료-확인)).

### QA-003 macOS에서 드래그한 영역과 다른 곳이 녹화됨

- 상태: 재검증 대기
- 우선순위: 높음
- 발견일: 2026-11-15. 사용자가 macOS 개발 빌드(`pnpm tauri dev`)로 드래그 영역을 녹화해 보고했습니다.
- 영향: 드래그한 영역이 아닌 곳이 녹화되어, macOS에서 영역 녹화를 쓸 수 없습니다.
- 기대 동작: 드래그한 사각형과 같은 화면 영역이 같은 픽셀 크기로 녹화됩니다.
- 재현: macOS 27.2.1, 화면 1470×956 포인트(배율 2) → `pnpm tauri dev` → 메뉴 막대의 녹화 → 드래그로 영역 지정. 결과 GIF는 800×485 픽셀이었고, 드래그한 곳보다 화면 왼쪽 위 쪽이 담겼습니다.
- 증거: 오버레이를 띄운 채 잰 값입니다. 화면 쪽이 쓰는 배율이 2가 아니라 1이었고, 오버레이 창이 요청한 (0, 0)이 아니라 메뉴 막대 아래 (0, 33포인트)에 놓여 있었습니다.
- 원인:
  - macOS의 Tauri `monitor_from_point`는 포인트 좌표를 받는데(tao 0.37.2 `monitor::from_point`가 `CGDisplayBounds`와 비교), 물리 픽셀 커서 위치를 넘겨 모니터를 찾지 못했고 기본값 1을 썼습니다. 드래그 좌표와 크기가 절반으로 계산됐습니다.
  - macOS가 화면 전체에 놓은 오버레이 창을 메뉴 막대 아래로 옮겨, 오버레이 안 좌표를 모니터 왼쪽 위 기준으로 바꾸면 그만큼 위로 어긋났습니다.
- 수정: 선택 오버레이는 Tauri 창 API로 자기 창의 실제 위치와 배율을 읽고, 창이 옮겨지면 다시 읽습니다. 조작 막대와 녹화 범위 테두리의 배율은 macOS에서 모니터를 찾을 때 구한 배율(`targets::display_scale`)을 씁니다. Windows는 창이 모니터 왼쪽 위에 그대로 놓이므로 같은 값이 나오지만, Windows에서는 다시 확인하지 않았습니다.
- 남은 제한: 오버레이가 메뉴 막대를 덮지 못해 메뉴 막대 부분은 드래그로 고를 수 없습니다.
- 재검증: 수정 빌드의 자동 검사는 통과했습니다. 측정용 빌드에 사용자가 드래그한 영역 두 개가 배율 2 크기로 들어왔지만, 의도한 위치와 비교하지 않아 판정 근거로 쓰지 않습니다. 수정 빌드로 원래 재현 순서를 다시 녹화해 GIF의 영역을 확인해야 합니다.

### QA-004 macOS에서 녹화를 반복하면 조작 막대가 사라지고 다음 녹화도 열리지 않음

- 상태는 완료입니다. macOS 수정 빌드에서 사용자가 취소와 정지를 번갈아 여섯 번 확인했습니다. 최초 보고의 우선순위는 높음입니다.
- 2026-11-19 macOS 27.2.1의 0.1.0에서 사용자가 보고했습니다. 최초 실행 파일 SHA-256은 `0fea260781bc5753426247535353eabb3b984f89d35c1c7279f5def6410e780f`입니다. 취소를 두 번 눌러야 닫힌 경험은 별도의 확인 항목으로 둡니다.
- 같은 프로세스에서 앞선 두 번은 선택 화면이 닫히고 조작 막대와 테두리가 표시됐습니다. 세 번째인 12:19:32에는 선택 화면이 숨겨졌고 캡처가 시작됐습니다. 생성 순서상 조작 막대에 해당하는 화면은 약 18ms 뒤 표시되기 전에 닫혔습니다. 12:19:46에 캡처가 정지했고 이후 세 번 메뉴 동작이 기록됐지만 새 화면은 생성되지 않았습니다. 선택 화면은 계속 숨김 상태를 보고했습니다.
- 기존 코드는 선택 창이 남아 있으면 포커스만 요청했습니다. macOS에서는 숨은 창을 이 방법으로 표시할 수 없습니다. 조작 막대를 처음 닫은 요청과 취소 첫 클릭의 실제 전달 여부는 당시 기록에서 확인할 수 없었습니다.
- 수정 빌드는 선택 창, 조작 막대와 테두리를 재사용하고 필요한 창을 직접 표시합니다. 매번 현재 녹화에 맞춰 창 목록과 시간을 다시 표시하며, 비활성 상태인 조작 막대에서도 첫 클릭을 버튼에 전달하도록 설정했습니다.
- QA용 macOS 앱의 실행 파일 SHA-256은 `251bf5c6ea383fb39d7ef73329e50cf7fd659e4c3a984a2d659d7f60399b84b4`입니다. Rust 테스트 22개, 코드 형식 검사, Clippy, TypeScript 검사, 릴리스 빌드와 앱 서명 검사가 통과했습니다. 브라우저에서 네이티브 명령 응답을 대체해 선택 화면과 조작 막대를 각각 여섯 번 열고 닫으며 회차별 명령과 저장 오류 표시를 확인했습니다. 이 자동 검사에서는 실제 캡처와 macOS 창 전환을 실행하지 않았습니다.
- 후속 실기기 검사에서 홀수 회차의 취소 세 번과 짝수 회차의 정지 세 번이 모두 정상이라는 사용자 확인을 받았습니다. 여섯 번째 뒤에도 선택 화면이 다시 열렸습니다. 마지막 Esc 실패는 QA-005에 기록했습니다. Windows는 이번 검사 범위 밖입니다. [검증 기록](verification.md#2026-11-19-macos-반복-녹화와-선택-화면-닫기)

#### 사용자 확인 순서

1. 기존 앱은 메뉴 막대의 **종료**로 닫고 QA용 앱을 엽니다. 화면 기록 권한을 다시 요청하면 안내에 따라 허용하고 같은 QA용 앱을 다시 엽니다.
2. 같은 앱을 계속 실행한 채 여섯 번 녹화합니다. 매번 메뉴의 **녹화**를 눌렀을 때 선택 화면이 보이는지, 영역을 고르면 시간과 두 버튼이 있는 조작 막대가 뜨는지 확인합니다.
3. 홀수 번째에는 다른 앱의 창을 한 번 클릭한 뒤 조작 막대의 **취소**를 한 번만 누릅니다. 막대와 테두리가 사라지고 새 GIF가 생기지 않아야 합니다. 짝수 번째에는 **정지**를 한 번 눌러 Finder에 새 GIF가 표시되는지 확인합니다. 한 번은 메뉴 막대의 **정지**로 끝냅니다.
4. 여섯 번째 뒤에 **녹화**를 다시 눌러 선택 화면이 열리는지 확인하고 Esc로 닫습니다. 중간에 실패하면 시각, 몇 번째였는지, 마지막으로 누른 버튼과 남은 화면을 기록합니다. 이어서 조사할 수 있도록 앱은 실행해 둡니다.

#### 최초 리뷰에서 놓친 지점

최초 리뷰는 조작 막대 생성 함수가 오류를 반환하는 경로를 따라갔습니다. 이번 실행처럼 생성된 화면이 표시되기 전에 닫히는 경우와, 그 뒤 다음 녹화가 숨은 선택 창을 다시 만나는 경우까지 이어 보지 않았습니다. 당시 여러 차례 반복하는 실제 앱 검사도 수행하지 않았습니다. 이번에는 같은 앱에서 취소와 정지를 번갈아 실행한 뒤 메뉴에서 다시 녹화를 열어 두 회차 사이의 창 상태를 검사했습니다. 여섯 번 통과한 결과는 사용자 증상이 이 조건에서 사라졌음을 보여 줍니다. 수정 전 조작 막대를 처음 닫은 호출은 여전히 특정할 수 없습니다.

### QA-005 macOS에서 다시 연 선택 화면이 Esc로 닫히지 않음

- QA-004와 같은 수정 빌드에서 2026-11-19 사용자가 보고했습니다. 취소와 정지를 번갈아 여섯 번 사용한 뒤 메뉴에서 선택 화면을 다시 열고 Esc를 눌렀을 때 창이 남았습니다.
- 기대 동작은 영역을 고르기 전에 Esc 한 번으로 선택을 끝내고 다음 녹화를 열 수 있는 것입니다.
- 상태는 미해결입니다. 화면 녹화 없이 선택 창만 다시 여는 macOS 진단 앱에서, 창이 보여도 키 입력 대상이 되지 않는 경우를 여섯 번 관측했습니다. 앱을 활성화하는 실험에서 Esc가 전달된 경우에는 창이 닫혔지만, 같은 결과가 반복되지 않았습니다. 실험 코드는 QA 빌드에 반영하지 않았습니다.
- 사용자 조작 당시 macOS의 키 입력 대상과 선택 창의 Esc 수신 여부는 확인되지 않았습니다. 다음 재현 때는 메뉴에서 선택 화면을 연 직후 이 두 값과 취소 명령 도착 여부를 함께 확인합니다.
