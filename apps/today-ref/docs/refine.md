# 만들기 뒤 AI 슬롭 검사와 수정 루프

완성작이나 고객 제품 화면 하나를 "화면 보기, AI 슬롭 검사, 고치기, 기록, 다시 보기" 순서로 돌리는 절차입니다. 2026-11-26에 완성작 10개를 손으로 소급해 다듬으며 지적 133건을 찾고 120건을 고친 흐름을 옮겼습니다. 그날 지시서와 스크린숏 스크립트가 세션 밖에 있어 다시 돌릴 수 없었기 때문에, 화면을 보는 결정적인 단계는 명령(`taste.py refine`)으로, 판단하는 단계는 이 문서로 나눴습니다. 이 문서를 고칠 때는 [agent.md의 "규칙을 고칠 때"](agent.md#규칙을-고칠-때)를 따릅니다.

## 누가 무엇을 하나

| 단계 | 하는 곳 | 결과 |
|---|---|---|
| 빌드, 미리보기 서버, 산출물 폴더 | today-ref `pnpm refine <주제 id>` | 완성작 하나의 보고 폴더 |
| 상태별 스크린숏, 기계 검사, lint 측정, 지문 | tastepin `taste.py refine` | `report.json`, `report.md`, 스크린숏 |
| AI 슬롭 검사와 수정 | 하위 에이전트(아래 지시서) | 코드 수정, `findings.json` |
| 기록 | 상위 세션의 `taste.py record --from-json` | 판정 원장의 `ai-review` 줄 |
| 다시 보기와 멈춤 판단 | 상위 세션 | 보고 |

`taste.py refine`은 대상 저장소를 모릅니다. 주소와 상태 파일만 받기 때문에 today-ref 완성작과 고객 제품 화면이 같은 명령을 씁니다.

## 1. 입력

- **완성작:** 주제 id 하나. 상태 파일은 `works/<주제 id>/states.json`입니다. README의 "상태로 가는 방법"을 주소와 조작 순서로 옮긴 파일이라, README를 고치면 이 파일도 함께 고칩니다.
- **고객 제품 화면:** 개발 서버 주소와 상태 파일. 상태 파일은 대상 저장소에 이미 있으면 그것을 쓰고, 없으면 세션 스크래치에 만듭니다. 대상 저장소에 새로 커밋할지는 사용자에게 묻습니다.

상태 파일 형식은 아래와 같습니다. `viewports`를 빼면 1440x900과 375x812 두 개를 씁니다. 상태마다 새 페이지에서 `path`를 연 뒤 `steps`를 차례로 실행하고, 상태끼리는 이어지지 않습니다.

```json
{
  "viewports": [{"name": "desktop", "width": 1440, "height": 900}, {"name": "phone", "width": 375, "height": 812}],
  "states": [
    {"id": "home", "label": "첫 화면", "path": "/"},
    {"id": "reveal", "label": "무료 팩 받기 뒤 카드 공개", "path": "/", "steps": [
      {"click": {"role": "button", "name": "무료 선수 팩 받기"}},
      {"wait": 2600}
    ]}
  ]
}
```

- `steps`는 `{"click": 대상}`, `{"hover": 대상}`, `{"fill": 대상, "value": "문자열"}`, `{"press": "Escape"}`, `{"wait": 밀리초}`, `{"scroll": 픽셀}`입니다.
- 대상은 `{"role": ..., "name": ..., "exact": false}`, `{"text": ...}`, `{"selector": ...}` 중 하나입니다. 같은 대상이 여럿이면 첫 번째를 씁니다.
- hover와 선택, 열린 시트, 알림처럼 첫 화면에 없는 상태를 넣습니다. 2026-11-26 지적 중 hover가 선택처럼 보이는 것(9건)과 열린 시트, 알림의 문제는 첫 화면만 봐서는 보이지 않았습니다.

## 2. 실행

완성작:

```sh
cd apps/today-ref
pnpm refine <주제 id>
```

고객 제품 화면(개발 서버를 먼저 띄웁니다):

```sh
python3 -B ~/dev/p/tools/taste/taste.py refine <개발 서버 주소> --states <상태 파일> --out <보고 폴더>
```

- 완성작의 보고 폴더는 `works/<주제 id>/.refine/<실행 시각>/`입니다(git에서 뺌). `--out <폴더>`로 바꿀 수 있고, 빌드를 이미 했으면 `--no-build`를 붙입니다. 껍데기에서 멈추면(빌드 실패, 서버를 띄우지 못함) 종료 코드 3이고 보고가 만들어지지 않으므로, 빌드부터 고칩니다.
- 고객 저장소의 보고 폴더는 세션 스크래치나 그 저장소가 git에서 빼는 폴더에 둡니다. 스크린숏은 커밋하지 않습니다.
- 종료 코드 0은 검사를 마쳤고 실패가 없다는 뜻이고, 1은 고칠 기계 검사 실패가 있다는 뜻입니다. 2는 브라우저를 띄우지 못한 것이므로 루프를 멈추고 그대로 보고합니다.
- lint는 이 명령 안에서 늘 측정만 합니다. 완성을 막지 않고 고침 기준도 아닙니다. 루프 밖(`/tastepin` 적용)에서는 지금처럼 사용자가 요청할 때만 돌립니다(2026-11-26 사용자 결정).

## 3. report.json 읽기

- `checks`의 `fail`은 기계 검사(콘솔 오류, 가로 넘침, 마우스로 누른 뒤 남는 초점, 상태 단계 실패)뿐입니다. 모두 고칩니다. 상태 단계 실패는 화면 결함일 수도 있고 상태 파일이 틀렸을 수도 있으니, 어느 쪽인지 먼저 확인합니다.
- `lint_checks`와 `symptom_candidates`는 하위 에이전트가 볼 곳을 알려 주는 단서입니다. 측정값이 규칙 범위를 넘으면 지적으로 옮기고, 그렇지 않으면 무시해도 됩니다.
- `fingerprint`는 보여 주기만 합니다. 서체, 모서리 분포, 버튼 벌 수, 곡선, 강조 색상각을 다른 완성작과 비교해 보고에 적습니다. 지문이 다른 완성작이나 tastepin 화면 전체 값과 같아도 이 루프에서는 고치지 않습니다. 정체성은 4단계에서 정합니다.
- `button_sets`와 `radius`의 종류 수는 아래 "개수 기준"의 입력입니다.

## 4. AI 슬롭 검사 지시서 (하위 에이전트용 원본)

상위 세션은 아래 블록을 복사하고 `<...>`를 채워 하위 에이전트에 넘깁니다. 완성작 여러 개를 동시에 돌리면 완성작마다 하위 에이전트 하나와 포트 하나를 씁니다.

````text
# AI 슬롭 검사와 수정: <대상 이름>

맡은 일: <완성작 works/<주제 id> | 고객 저장소 경로와 화면>의 AI 슬롭(AI가 만든 티)을 찾아 고치고, 지적 목록을 돌려준다.

## 먼저 읽을 것
- 검사 보고: <보고 폴더>/report.md, report.json, 스크린숏
- 대상의 범위와 결정: <완성작이면 README.md와 topics/<주제 id>/topic.json의 selection.items[].part | 고객 저장소면 그 저장소의 AGENTS.md, 범위 문서, 디자인 토큰>
- 취향 출력: <완성작 폴더에서 받아 둔 apply-context 출력 파일>. 다시 실행하지 않는다
- 이전 바퀴의 지적: <이전 findings.json 경로 | 없음>

## 찾는 것
화면에서 실제로 보이거나 코드로 확인한 것만 적는다. 추측으로 채우지 않는다.
- 흔한 구성: 마케팅 히어로, 통계 띠, 카드 모자이크, 가운데 질문형 빈 화면, 큰 제목 위 작은 머리말
- 장식: 근거 없는 배지와 칩, 색 면을 깐 알약, 왼쪽 강조 막대, 줄마다 같은 아이콘, 장식용 고정폭 숫자, 한글의 넓은 자간, 글래스와 반투명 흐림
- 같은 것을 다르게: 같은 기능이나 값을 화면마다 다른 이름, 아이콘, 색, 모서리, 버튼 모양, 숫자 형식으로 보여 주는 것
- 상태 혼동: hover가 선택이나 켜짐처럼 보이는 것, 누를 수 없는 글자에 행동 색이나 밑줄, 끌 수 없는 손잡이, 마우스로 누른 뒤 남는 초점
- 되풀이: 설명, 스펙, 배지, 제목이 이미 보이는 값을 다시 말하는 것, 같은 일을 하는 컨트롤 두 개
- 군더더기: 요청이나 part에 없는 필터, 탭, 검색, 즐겨찾기, 눌러도 아무 일이 없는 버튼, 내부 처리 방식이나 사용법을 알리는 안내문
- 그림: 실사 생성 인물 얼굴, 생성 이미지의 흔한 구도, 서로 다른 항목에 같은 사진
- 움직임: 드로어와 시트의 스프링, 들어오기만 하고 나갈 때 움직이지 않는 것, 같은 종류 전환의 길이와 곡선이 제각각인 것

## 개수 기준 (고정값을 강제하지 않는다)
- 일관성은 개수로 잰다. 같은 역할의 버튼은 주 버튼 한 벌과 보조 버튼 한 벌 정도로, 모서리 값의 종류는 몇 개 안쪽으로 줄인다. report.json의 button_sets와 radius 종류 수를 고치기 전과 뒤에 적는다.
- 어느 값으로 맞출지는 대상이 이미 정한 것에서 고른다. 순서는 대상의 토큰, README나 범위 문서에 적은 결정, 지문에서 가장 많이 쓰는 값이다. 다른 완성작이나 이전 다듬기에서 고친 값(예: 6px, 높이 44px, 누름 0.95배)을 그대로 옮기지 않는다. 2026-11-26 소급에서 같은 값을 모든 완성작에 넣어 표면이 하나로 모였다.
- 규칙의 범위(예: 모서리는 컨테이너 0~6px, 버튼과 입력 4~8px)를 넘는 것만 슬롭으로 고치고, 범위 안의 값은 대상의 값을 둔다.

## 고칠 범위
- 구조, 동작, 컴포넌트 값, 모션, 문구, 컨트롤 구성
- 지우는 것(장식, 되풀이 문구, 쓸모없는 컨트롤)은 해도 된다. 새 기능은 더하지 않는다

## 지킬 것 (보호 범위)
- 대상의 색과 서체 토큰, 제목 표현, README나 범위 문서에 사용자 결정으로 적은 것
- 완성작이면 고를 때 적은 part의 화면 구조. 취향 값이나 규칙과 부딪치면 이쪽을 따르고 findings의 note에 적는다
- 새 이미지를 만들거나 내려받지 않는다. 그림 자체가 문제면 fixed: false로 남긴다
- 맡은 폴더 밖 파일, git 쓰기, taste.py record와 apply-context, 패키지 설치는 하지 않는다. 정해 준 포트만 쓴다
- 기존 주석 말투(한국어, 왜 그렇게 하는지)를 따르고 가운데점 문자는 쓰지 않는다

- 완성작이면 README의 "tastepin 다듬기에서 고친 것" 절을 갱신하고(남긴 것도 한 줄씩), 바뀐 동작에 맞춰 "상태로 가는 방법"과 states.json을 함께 고친다
````

## 5. findings.json 형식

```json
[{"text": "한 문장 관찰", "where": "화면이나 컴포넌트", "fixed": true, "note": "고친 방법이나 남긴 이유", "symptoms": ["증상 id"]}]
```

- `text`는 스크린숏 없이 읽히게 어느 화면의 무엇이 어떻게 보이는지 쓰는 관찰입니다. 사용자가 말한 것처럼 쓰지 않습니다.
- `fixed: false`는 고칠 수 없거나 고치지 않기로 한 것입니다(그림 자체의 문제, part와 부딪침, 사용자 결정). `note`에 이유를 적습니다.
- `symptoms`는 선택이지만 되도록 붙입니다. `report.json`의 `symptom_candidates`와 `tastepin/data/symptoms.json`의 id를 씁니다. 사전에 없는 id는 기록할 때 오류가 납니다. 2026-11-26 기록 133건 중 95건이 증상 없이 남아 어떤 규칙의 근거인지 셀 수 없었습니다.

## 6. 기록

```sh
python3 -B ~/dev/p/tools/taste/taste.py record --from-json <보고 폴더>/findings.json --origin ai-review --surface claude --session "$CLAUDE_CODE_SESSION_ID" --dry-run
```

- 먼저 `--dry-run`으로 쓸 내용을 보고, 문제가 없으면 `--dry-run`을 빼고 다시 실행합니다. 항목 하나라도 형식이 틀리면 아무것도 쓰지 않으니, 고쳐서 다시 실행합니다.
- `ai-review` 줄은 AI의 지적이라 사용자가 tastepin 대시보드에서 보관하기 전까지 취향 근거가 되지 않습니다. 판정 원장에 사용자 문장이 아닌 것을 `ai-review` 없이 남기지 않습니다.
- 원장(`~/dev/p/tools/taste/state/`)이 없는 사본(클라우드 세션, 원장이 없는 머신)에서는 `--dry-run`까지만 하고, `findings.json`을 보고에 남겨 원장이 있는 머신에서 기록하게 합니다.
- 완성작이면 고친 내용을 [agent.md 6단계](agent.md#6-tastepin으로-다듬기)대로 기록 도구에 `change`로도 남깁니다.

## 7. 다시 실행과 멈춤

고친 뒤 2단계의 명령을 같은 상태 파일로 다시 실행하고, 하위 에이전트에 이전 `findings.json`을 함께 넘겨 다시 검사합니다. 다시 검사할 때는 이전 지적이 사라졌는지와, 고치면서 새로 생긴 것만 찾습니다. 같은 지적을 다른 말로 다시 적지 않습니다.

다음 중 하나면 멈춥니다.

- 기계 검사 `fail`이 0이고, 이번 바퀴의 새 지적이 모두 `fixed: false`입니다.
- 두 바퀴를 돌았습니다. 남은 `fail`과 지적은 고치지 않고 보고합니다.
- 브라우저를 띄우지 못했습니다(종료 코드 2).

바퀴 수를 늘리지 않는 이유: 2026-11-26 소급에서 고칠 수 있는 지적은 한 바퀴에 90%(133건 중 120건)가 고쳐졌고, 남은 것은 그림, part와 부딪친 것, 사용자 결정처럼 더 돌아도 바뀌지 않는 것이었습니다.

## 8. 보고

사용자에게 아래를 짧게 보고합니다.

- 돈 바퀴 수와 멈춘 이유
- 기계 검사 `fail` 수(처음과 끝), 지적 수와 고친 수, 남긴 것과 이유
- button_sets와 모서리 종류 수의 전과 후, 지문이 다른 완성작이나 tastepin 화면 전체 값과 겹치는 곳(고치지 않고 알리기만 함)
- 기록한 `ai-review` 건수, 또는 `--dry-run`까지만 한 이유. 대시보드에서 보관하거나 무시할 수 있다는 안내
- 확인하지 못한 것: 움직임의 체감, 실제 휴대폰과 터치, Safari, 상태 파일에 넣지 않은 상태
