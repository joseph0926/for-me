# 만들기 뒤 AI 슬롭 검사와 수정 루프

완성작이나 고객 제품 화면 하나를 "화면 보기, AI 슬롭 검사, 고치기, 기록, 다시 보기" 순서로 돌리는 절차입니다. 2026-11-26에 완성작 10개를 손으로 소급해 다듬으며 지적 133건을 찾고 120건을 고친 흐름을 옮겼습니다. 그날 지시서와 스크린숏 스크립트가 세션 밖에 있어 다시 돌릴 수 없었기 때문에, 화면을 보는 결정적인 단계는 명령(`taste.py refine`)으로, 판단하는 단계는 이 문서로 나눴습니다. 이 문서를 고칠 때는 [agent.md의 "규칙을 고칠 때"](agent.md#규칙을-고칠-때)를 따릅니다.

## 누가 무엇을 하나

| 단계 | 하는 곳 | 결과 |
|---|---|---|
| 빌드, 미리보기 서버, 산출물 폴더 | today-ref `pnpm refine <주제 id>` | 완성작 하나의 보고 폴더 |
| 상태별 스크린숏, 기계 검사, lint 측정, 지문 | tastepin `taste.py refine` | `report.json`, `report.md`, 스크린숏 |
| AI 슬롭 검사와 수정 | 하위 에이전트(아래 지시서) | 코드 수정, `findings.json` |
| 기록 | 상위 세션의 `taste.py record --from-json` | 판정 원장의 `ai-review` 줄 |
| 다시 보기와 멈춤 판단 | 상위 세션 | 보고 |

`taste.py refine`은 대상 저장소를 모릅니다. 주소와 상태 파일만 받기 때문에 today-ref 완성작과 고객 제품 화면이 같은 명령을 씁니다.

## 1. 입력

- **완성작:** 주제 id 하나. 상태 파일은 `works/<주제 id>/states.json`입니다. README의 "상태로 가는 방법"을 주소와 조작 순서로 옮긴 파일이라, README를 고치면 이 파일도 함께 고칩니다.
- **고객 제품 화면:** 개발 서버 주소와 상태 파일. 상태 파일은 대상 저장소에 이미 있으면 그것을 쓰고, 없으면 세션 스크래치에 만듭니다. 대상 저장소에 새로 커밋할지는 사용자에게 묻습니다.

상태 파일 형식은 아래와 같습니다. `viewports`를 빼면 1440x900과 375x812 두 개를 씁니다. 상태마다 새 페이지에서 `path`를 연 뒤 `steps`를 차례로 실행하고, 상태끼리는 이어지지 않습니다.

```json
{
  "viewports": [{"name": "desktop", "width": 1440, "height": 900}, {"name": "phone", "width": 375, "height": 812}],
  "states": [
    {"id": "home", "label": "첫 화면", "path": "/"},
    {"id": "reveal", "label": "무료 팩 받기 뒤 카드 공개", "path": "/", "steps": [
      {"click": {"role": "button", "name": "무료 선수 팩 받기"}},
      {"wait": 2600}
    ]}
  ]
}
```

- `steps`는 `{"click": 대상}`, `{"hover": 대상}`, `{"fill": 대상, "value": "문자열"}`, `{"press": "Escape"}`, `{"wait": 밀리초}`, `{"scroll": 픽셀}`, `{"expect": 대상}`(보여야 함), `{"expect": 대상, "absent": true}`(보이지 않아야 함)입니다. `expect`와 상태의 `guard: true`는 고객 제품의 기능 계약에 쓰며 [9절](#9-고객-제품)에 씁니다.
- 대상은 `{"role": ..., "name": ..., "exact": false}`, `{"text": ...}`, `{"selector": ...}` 중 하나입니다. 같은 대상이 여럿이면 첫 번째를 씁니다.
- hover와 선택, 열린 시트, 알림처럼 첫 화면에 없는 상태를 넣습니다. 2026-11-26 지적 중 hover가 선택처럼 보이는 것(9건)과 열린 시트, 알림의 문제는 첫 화면만 봐서는 보이지 않았습니다.

## 2. 실행

완성작:

```sh
cd apps/today-ref
pnpm refine <주제 id>
```

고객 제품 화면(개발 서버를 먼저 띄웁니다):

```sh
python3 -B ~/dev/p/tools/taste/taste.py refine <개발 서버 주소> --states <상태 파일> --out <보고 폴더>
```

- 완성작의 보고 폴더는 `works/<주제 id>/.refine/<실행 시각>/`입니다(git에서 뺌). `--out <폴더>`로 바꿀 수 있고, 빌드를 이미 했으면 `--no-build`를 붙입니다. 껍데기에서 멈추면(빌드 실패, 서버를 띄우지 못함) 종료 코드 3이고 보고가 만들어지지 않으므로, 빌드부터 고칩니다.
- 고객 저장소의 보고 폴더는 세션 스크래치나 그 저장소가 git에서 빼는 폴더에 둡니다. 스크린숏은 커밋하지 않습니다.
- 종료 코드 0은 검사를 마쳤고 실패가 없다는 뜻이고, 1은 고칠 기계 검사 실패가 있다는 뜻입니다. 2는 브라우저를 띄우지 못한 것이므로 루프를 멈추고 그대로 보고합니다.
- lint는 이 명령 안에서 늘 측정만 합니다. 완성을 막지 않고 고침 기준도 아닙니다. 루프 밖(`/tastepin` 적용)에서는 지금처럼 사용자가 요청할 때만 돌립니다(2026-11-26 사용자 결정).

## 3. report.json 읽기

- `checks`의 `fail`은 기계 검사(콘솔 오류, 가로 넘침, 마우스로 누른 뒤 남는 초점, 상태 단계 실패)뿐입니다. 모두 고칩니다. 상태 단계 실패는 화면 결함일 수도 있고 상태 파일이 틀렸을 수도 있으니, 어느 쪽인지 먼저 확인합니다.
- `lint_checks`와 `symptom_candidates`는 하위 에이전트가 볼 곳을 알려 주는 단서입니다. 측정값이 규칙 범위를 넘으면 지적으로 옮기고, 그렇지 않으면 무시해도 됩니다.
- `fingerprint`는 보여 주기만 합니다. 서체, 모서리 분포, 버튼 벌 수, 곡선, 강조 색상각을 다른 완성작과 비교해 보고에 적습니다. 지문이 다른 완성작이나 tastepin 화면 전체 값과 같아도 이 루프에서는 고치지 않습니다. 정체성은 4단계에서 정합니다.
- `button_sets`와 `radius`의 종류 수는 아래 "개수 기준"의 입력입니다.

## 4. AI 슬롭 검사 지시서 (하위 에이전트용 원본)

상위 세션은 아래 블록을 복사하고 `<...>`를 채워 하위 에이전트에 넘깁니다. 완성작 여러 개를 동시에 돌리면 완성작마다 하위 에이전트 하나와 포트 하나를 씁니다.

````text
# AI 슬롭 검사와 수정: <대상 이름>

맡은 일: <완성작 works/<주제 id> | 고객 저장소 경로와 화면>의 AI 슬롭(AI가 만든 티)을 찾아 고치고, 지적 목록을 돌려준다.

## 먼저 읽을 것
- 검사 보고: <보고 폴더>/report.md, report.json, 스크린숏
- 대상의 범위와 결정: <완성작이면 README.md와 topics/<주제 id>/topic.json의 selection.items[].part | 고객 저장소면 그 저장소의 AGENTS.md, 범위 문서, 디자인 토큰>
- 실제 제품 근거: <topics/<주제 id>/topic.json의 references(points, evidence)와 captures/<주제 id>/의 캡처 | 동작 수집 주제의 같은 것 | 없음>
- 취향 출력: <완성작 폴더에서 받아 둔 apply-context 출력 파일>. 다시 실행하지 않는다
- 이전 바퀴의 지적: <이전 findings.json 경로 | 없음>

## 지적의 종류 (지적마다 하나를 고른다)
당신의 눈도 사용자의 눈도 정답이 아니다. 지적마다 무엇으로 확인되는지를 적고, 확인되는 만큼만 고친다.
- fact: 고장과 불일치. 서로 다른 항목의 같은 사진, 잘리거나 겹친 글자, 깨진 테두리, 같은 역할인데 화면마다 다른 버튼이나 이름처럼 값이나 표시가 서로 어긋나거나 작동하지 않는 것이고, 화면이나 코드에서 누구나 다시 확인할 수 있는 것. proof에 스크린숏 파일과 위치, 또는 파일과 줄을 적는다. 고친다
  - 있어도 되는지에 대한 판단은 fact가 아니라 taste다. 중복으로 보이는 컨트롤, 되풀이로 보이는 문구, 불필요해 보이는 요소가 여기에 든다
  - 고치는 방법이 여럿이면 화면을 가장 적게 바꾸는 방법을 쓴다. 요소를 지워야만 고쳐지는데 그 요소가 실제 제품 근거의 캡처에 보이면 지우지 않고 fixed: false, note에 "보류: 지우기"로 남긴다
- reference: 구조와 동작이 실제 제품 근거와 다른 것. proof에 레퍼런스 id와 그 evidence, 본 캡처 파일을 적는다. 근거가 state나 still이고 고를 때 적은 part에 든 것이면 고친다. 근거가 read나 secondhand뿐이거나 part에 없으면 고치지 않고 fixed: false, note에 "보류: 근거 제시"로 남긴다
- taste: 그 밖의 모양, 크기, 여백, 색, 분위기에 대한 의견. 취향 출력의 확정 규칙이 정한 범위를 넘은 것만 고치고 proof에 그 규칙 이름을 적는다. 규칙이 없으면 고치지 않고 fixed: false, note에 "의견"으로 남긴다. 제목을 키우자, 여백을 줄이자 같은 제안이 여기에 든다
  - 규칙이 있어도 고치기 전에 실제 제품 근거의 캡처에서 그 부분을 직접 본다. 실제 제품이 규칙과 반대로 하고 있으면(큰 모서리, 통계 줄, 사진 위 배지, 구분선 등) 고치지 않고 fixed: false, note에 "보류: 규칙과 근거가 다름"으로 남기고 proof에 규칙 이름과 캡처 파일을 함께 적는다. 취향 규칙은 다른 화면에서 나온 선택이라 이 화면의 실제 제품보다 앞서지 않는다
- proof를 적을 수 없으면 fact나 reference로 올리지 않는다. 좋아 보이는 화면에서 taste를 채우려고 애쓰지 않는다

## 찾는 것
화면에서 실제로 보이거나 코드로 확인한 것만 적는다. 추측으로 채우지 않는다. 아래는 볼 곳의 목록이고, 목록에 있다는 것만으로 고칠 근거가 되지 않는다.
- 흔한 구성: 마케팅 히어로, 통계 띠, 카드 모자이크, 가운데 질문형 빈 화면, 큰 제목 위 작은 머리말
- 장식: 근거 없는 배지와 칩, 색 면을 깐 알약, 왼쪽 강조 막대, 줄마다 같은 아이콘, 장식용 고정폭 숫자, 한글의 넓은 자간, 글래스와 반투명 흐림
- 같은 것을 다르게: 같은 기능이나 값을 화면마다 다른 이름, 아이콘, 색, 모서리, 버튼 모양, 숫자 형식으로 보여 주는 것
- 상태 혼동: hover가 선택이나 켜짐처럼 보이는 것, 누를 수 없는 글자에 행동 색이나 밑줄, 끌 수 없는 손잡이, 마우스로 누른 뒤 남는 초점
- 되풀이: 설명, 스펙, 배지, 제목이 이미 보이는 값을 다시 말하는 것, 같은 일을 하는 컨트롤 두 개
- 군더더기: 요청이나 part에 없는 필터, 탭, 검색, 즐겨찾기, 눌러도 아무 일이 없는 버튼, 내부 처리 방식이나 사용법을 알리는 안내문. 고객 저장소면 필터, 탭, 검색, 즐겨찾기는 실제 기능일 수 있으므로 군더더기로 보지 않고, 의심되면 보류로 적는다
- 그림: 실사 생성 인물 얼굴, 생성 이미지의 흔한 구도, 서로 다른 항목에 같은 사진
- 움직임: 드로어와 시트의 스프링, 들어오기만 하고 나갈 때 움직이지 않는 것, 같은 종류 전환의 길이와 곡선이 제각각인 것

## 개수 기준 (고정값을 강제하지 않는다)
- 일관성은 개수로 잰다. 같은 역할의 버튼은 주 버튼 한 벌과 보조 버튼 한 벌 정도로, 모서리 값의 종류는 몇 개 안쪽으로 줄인다. report.json의 button_sets와 radius 종류 수를 고치기 전과 뒤에 적는다.
- 어느 값으로 맞출지는 대상이 이미 정한 것에서 고른다. 순서는 대상의 토큰, README나 범위 문서에 적은 결정, 지문에서 가장 많이 쓰는 값이다. 다른 완성작이나 이전 다듬기에서 고친 값(예: 6px, 높이 44px, 누름 0.95배)을 그대로 옮기지 않는다. 2026-11-26 소급에서 같은 값을 모든 완성작에 넣어 표면이 하나로 모였다.
- 규칙의 범위(예: 모서리는 컨테이너 0~6px, 버튼과 입력 4~8px)를 넘는 것만 슬롭으로 고치고, 범위 안의 값은 대상의 값을 둔다.

## 고칠 범위
- "지적의 종류"가 고쳐도 된다고 한 지적만 고친다. 아래는 그 안에서 손댈 수 있는 곳이다
- 구조, 동작, 컴포넌트 값, 모션, 문구, 컨트롤 구성
- 완성작이면 지우는 것(장식, 되풀이 문구, 쓸모없는 컨트롤)은 해도 된다. 새 기능은 더하지 않는다
- 고객 저장소면 지우지 않는다. 지울 것으로 보이는 요소는 `fixed: false`, note에 "보류: 지우기"와 이유를 적어 돌려준다. 바꾸는 것은 모양, 값, 문구까지다
- 고객 저장소면 `guard: true` 상태의 화면은 고치지 않는다. 지킬 상태가 깨질 수정이면 보류로 적는다

## 지킬 것 (보호 범위)
- 대상의 색과 서체 토큰, 제목 표현, README나 범위 문서에 사용자 결정으로 적은 것
- 완성작이면 고를 때 적은 part의 화면 구조. 취향 값이나 규칙과 부딪치면 이쪽을 따르고 findings의 note에 적는다
- 새 이미지를 만들거나 내려받지 않는다. 그림 자체가 문제면 fixed: false로 남긴다
- 맡은 폴더 밖 파일, git 쓰기, taste.py record와 apply-context, 패키지 설치는 하지 않는다. 정해 준 포트만 쓴다
- 기존 주석 말투(한국어, 왜 그렇게 하는지)를 따르고 가운데점 문자는 쓰지 않는다

2. 최종 답변(300단어 이내): 종류별 지적 수와 고친 수, button_sets와 모서리 종류 수의 전과 후, 남긴 것과 이유, 바꾼 파일
````

## 5. findings.json 형식

```json
[{"text": "한 문장 관찰", "where": "화면이나 컴포넌트", "basis": "fact", "proof": "home-desktop.png 결과 카드 1번과 3번", "fixed": true, "note": "고친 방법이나 남긴 이유", "symptoms": ["증상 id"]}]
```

- `text`는 스크린숏 없이 읽히게 어느 화면의 무엇이 어떻게 보이는지 쓰는 관찰입니다. 사용자가 말한 것처럼 쓰지 않습니다.
- `basis`는 `fact`, `reference`, `taste` 중 하나이고 뜻은 지시서의 "지적의 종류"입니다. `proof`는 그 지적을 다른 사람이 다시 확인할 곳입니다. 규칙 없는 `taste`만 `proof`를 비워 둘 수 있습니다. 기준을 이렇게 나눈 이유는 [scope.md의 "판단의 기준과 멈추는 조건"](scope.md#판단의-기준과-멈추는-조건)에 있습니다.
- 상위 세션은 `fact` 지적의 `proof`를 직접 열어 확인합니다. 확인되지 않는 지적은 `taste`로 내리고, 이미 고친 것이면 보고의 "확인되지 않은 수정"에 적습니다.
- `fixed: false`는 고칠 수 없거나 고치지 않기로 한 것입니다(그림 자체의 문제, part와 부딪침, 사용자 결정, 근거 제시로 보류한 것, 의견). `note`에 이유를 적습니다.
- `basis`와 `proof`는 `taste.py record`가 읽지 않는 항목이라 원장에는 남지 않고 보고 폴더의 `findings.json`에만 있습니다.
- `symptoms`는 선택이지만 되도록 붙입니다. `report.json`의 `symptom_candidates`와 `tastepin/data/symptoms.json`의 id를 씁니다. 사전에 없는 id는 기록할 때 오류가 납니다. 2026-11-26 기록 133건 중 95건이 증상 없이 남아 어떤 규칙의 근거인지 셀 수 없었습니다.

## 6. 기록

```sh
python3 -B ~/dev/p/tools/taste/taste.py record --from-json <보고 폴더>/findings.json --origin ai-review --surface claude --session "$CLAUDE_CODE_SESSION_ID" --dry-run
```

- 먼저 `--dry-run`으로 쓸 내용을 보고, 문제가 없으면 `--dry-run`을 빼고 다시 실행합니다. 항목 하나라도 형식이 틀리면 아무것도 쓰지 않으니, 고쳐서 다시 실행합니다.
- `ai-review` 줄은 AI의 지적이라 사용자가 tastepin 대시보드에서 보관하기 전까지 취향 근거가 되지 않습니다. 판정 원장에 사용자 문장이 아닌 것을 `ai-review` 없이 남기지 않습니다.
- AI 지적은 개인 Mac에서만 원장에 들어갑니다(진입점의 `TASTEPIN_AI_REVIEW_MACHINES`, 2026-11-26). 다른 머신과 클라우드 세션에서 `--dry-run` 없이 실행하면 원장 대신 `~/dev/p/tools/taste/state/pending/<머신>-<시각>.json` 새 파일로 남고, 개인 Mac에서 `taste.py record --import-pending`으로 넣은 뒤 그 파일을 지웁니다. 실행마다 새 파일이라 원장의 pull 충돌이 나지 않습니다. tools 사본조차 없는 곳에서는 `--dry-run`까지만 하고 `findings.json`을 보고에 남깁니다.
- 완성작이면 고친 내용을 [agent.md 6단계](agent.md#6-tastepin으로-다듬기)대로 기록 도구에 `change`로도 남깁니다.

## 7. 다시 실행과 멈춤

고친 뒤 2단계의 명령을 같은 상태 파일로 다시 실행하고, 하위 에이전트에 이전 `findings.json`을 함께 넘겨 다시 검사합니다. 다시 검사할 때는 이전 지적이 사라졌는지와, 고치면서 새로 생긴 것만 찾습니다. 같은 지적을 다른 말로 다시 적지 않습니다.

다음 중 하나면 멈춥니다.

- 기계 검사 `fail`이 0이고, 이번 바퀴의 새 지적이 모두 `fixed: false`입니다.
- 두 바퀴를 돌았습니다. 남은 `fail`과 지적은 고치지 않고 보고합니다.
- 브라우저를 띄우지 못했습니다(종료 코드 2).

바퀴 수를 늘리지 않는 이유: 2026-11-26 소급에서 고칠 수 있는 지적은 한 바퀴에 90%(133건 중 120건)가 고쳐졌고, 남은 것은 그림, part와 부딪친 것, 사용자 결정처럼 더 돌아도 바뀌지 않는 것이었습니다.

루프가 멈춘 것은 AI가 혼자 고칠 수 있는 것이 끝났다는 뜻이고, 화면이 완성됐다는 뜻이 아닙니다. 완성은 세 가지가 모두 맞을 때입니다.

- `fact` 지적과 기계 검사 `fail`이 남지 않았습니다. 사용자가 좋다고 한 화면에서도 남아 있으면 고칩니다.
- `reference` 지적 중 보류한 것을 근거와 함께 사용자에게 보여 줬고, 정해졌습니다.
- 규칙 없는 `taste` 의견을 보여 줬고, 사용자의 이견이 없습니다.

사용자가 아직 답하지 않았으면 진행을 멈추지 않고, 보고와 기록에 "사용자 확인 전"으로 남깁니다. AI 지적이 0개가 됐다는 것만으로, 또는 사용자의 "좋다" 한마디만으로 완성이라고 적지 않습니다.

## 8. 보고

사용자에게 아래를 짧게 보고합니다.

- 돈 바퀴 수와 멈춘 이유
- 기계 검사 `fail` 수(처음과 끝), 종류별(`fact`, `reference`, `taste`) 지적 수와 고친 수, 남긴 것과 이유, 확인되지 않은 수정
- 바꾼 파일 수와 줄 수. 지적에 없는 수정이 있으면 따로 적습니다
- 사용자가 정할 것: 보류한 `reference` 지적과 "규칙과 근거가 다름"으로 보류한 지적마다 실제 제품이 쓰는 방식과 취향 규칙이 말하는 방식을 레퍼런스 id, `evidence`와 함께 놓고 고르게 합니다. 규칙 없는 `taste` 의견은 중요한 것 세 개까지만 보여 주고, 나머지는 개수만 적습니다
- button_sets와 모서리 종류 수의 전과 후, 지문이 다른 완성작이나 tastepin 화면 전체 값과 겹치는 곳(고치지 않고 알리기만 함)
- 기록한 `ai-review` 건수와 원장에 들어갔는지 대기 폴더로 갔는지, 또는 `--dry-run`까지만 한 이유. 대시보드에서 보관하거나 무시할 수 있다는 안내
- 확인하지 못한 것: 움직임의 체감, 실제 휴대폰과 터치, Safari, 상태 파일에 넣지 않은 상태

## 9. 고객 제품

고객의 실제 제품 저장소에서 이 루프를 돌 때는 위 절차에 아래를 더합니다. 상황(B 부분 개선, C 부분 새로 만들기, D 전면 재설계)의 판별은 [use.md의 상황 판별](use.md#상황-판별)입니다. 완성작에서는 군더더기가 데모의 장식이지만, 고객 제품에서는 같은 필터나 탭이 사용자가 쓰는 기능입니다. 그래서 슬롭 수정이 기존 기능을 지우지 않게 하는 것이 이 절의 목적입니다.

### 지우기는 보류

- 4절 지시서의 "지우는 것은 해도 된다"와 "요청에 없는 필터, 탭, 검색은 군더더기"는 완성작에만 적용합니다. 고객 제품에서는 지우지 않고, 하위 에이전트가 `fixed: false`와 "보류: 지우기"로 돌려준 지적을 모아 한 번에 보여 주고 사용자가 고르게 합니다. [use.md 3단계](use.md#3-대상-화면에-맞추기)의 보류 행과 같은 방식입니다.
- 지시서의 "대상의 범위와 결정"에는 대상 저장소의 AGENTS.md(없으면 README)의 "UI 결정" 절과 토큰 파일을 넣습니다.

### 지킬 상태

바꾸는 화면 밖에서 깨지면 안 되는 상태를 `states.json`에 `guard: true`로 표시합니다.

- 고르는 법: 바꾸는 컴포넌트를 import하는 다른 화면(코드 검색으로 찾음)과, 바꾸는 부분이 있는 같은 페이지의 나머지입니다. 공유 컴포넌트나 토큰을 고치면 상태 파일에 없는 화면이 깨지므로, 검색으로 찾은 화면을 빠짐없이 넣습니다.
- 상태마다 그 화면에 있어야 할 것을 `expect` 단계로 적습니다. 예: 보관함의 검색칸과 정렬 버튼이 보여야 한다. `expect`는 대상이 2초 안에 보이지 않으면 그 상태의 `state-failed`가 되고, `"absent": true`는 보이지 않아야 통과합니다(예: 빈 목록 상태에서 목록 행).
- 로그인이 필요한 화면은 `--storage-state <파일>`로 로그인 상태를 넘깁니다. 파일은 사용자가 로그인한 브라우저에서 저장하게 하고, 비밀번호를 대신 입력하지 않습니다. 로그인 화면으로 돌아가면 `login-redirect` fail이 되므로, 그때는 화면 결함이 아니라 로그인 상태가 없는 것입니다. 이 파일은 비밀이라 세션 스크래치에 두고 커밋하지 않습니다.

```json
{"id": "library", "label": "보관함 목록", "path": "/library", "guard": true, "steps": [
  {"expect": {"role": "searchbox"}},
  {"expect": {"role": "button", "name": "정렬"}}
]}
```

### 판정 기준

- 지킬 상태는 `expect` 통과와 새 fail 0이면 통과입니다. 고치기 전에 한 번 돌려 둔 보고보다 fail이 늘지 않아야 합니다.
- 픽셀 차이는 판정에 쓰지 않고 보고만 합니다. 시계, 난수, 실제 API 때문에 같은 화면도 스크린숏이 바뀌어, 차이를 fail로 걸면 거짓 실패가 쌓입니다.
- 개발 모드의 경고가 콘솔 오류로 잡히면 대상 저장소의 결함인지 개발 모드 잡음인지 구분해 보고하고, 잡음이면 고치지 않습니다.

### 대상 저장소에 남기는 것

다음 작업이 이어 받을 수 있게 세 가지를 대상 저장소에 둡니다.

1. 기존 토큰 파일. 새 파일을 만들지 않고 이미 있는 토큰을 씁니다. `apply-context`는 이 토큰을 찾으면 그 값을 넣지 않습니다.
2. `states.json`(지킬 상태와 `expect` 포함). 위치는 대상 저장소의 관례를 따르고, 없으면 저장소 루트의 `states.json`으로 제안합니다.
3. AGENTS.md(없으면 README)의 "UI 결정" 절. 칸은 정체성(서체, 바탕과 강조색, 기준 모서리, 모션, 제목 표현과 그 근거), 보호 목록(바꾸지 않을 화면, 조작, 컴포넌트), 사용자 결정(사용자가 정하거나 뺀 색, 서체, 기능과 날짜)입니다. 정체성 칸은 [topic.ts](../topic.ts)의 `Identity`와 같게 둡니다.

- 커밋할지는 저장소마다 처음 한 번 묻고, 답을 그 저장소의 "UI 결정" 절에 적어 다시 묻지 않습니다. 커밋하지 않기로 하면 세 가지를 세션 스크래치에 두고 보고에 위치를 적습니다.
- 스크린숏, 보고 폴더와 `.refine/`, 로그인 상태 파일은 커밋하지 않습니다.

### D: 기능 유지, 전면 재설계

1. 라우트, 기존 e2e 테스트와 README에서 사용자가 하는 일을 모아 행동 목록 초안을 `states.json`(상태마다 `expect`)으로 만듭니다. AI가 화면을 돌아다니며 뽑은 목록을 그대로 확정하지 않습니다. 틀린 목록이 정답이 되기 때문입니다.
2. 이 상태 파일로 옛 UI에서 먼저 `taste.py refine`을 돌려 모두 통과시킵니다. 옛 UI에서 실패하는 행은 목록이 틀린 것이므로 고칩니다. 이 보고가 전후 비교의 기준입니다.
3. 행동 목록과 정체성 후보를 한 메시지로 보여 주고 **한 번 멈춥니다**. 후보는 기존 정체성을 유지하는 안 하나와 새 안을 포함하고, 안마다 다른 축과 근거를 한 줄로 적습니다. 진행 중 멈추는 곳은 여기 하나입니다.
4. 새 UI는 별도 라우트나 플래그 뒤에 두어 옛 UI와 함께 살립니다. store, API와 라우트의 동작은 건드리지 않고 보기 층만 바꿉니다. 화면 하나씩, 그 화면에 맞는 완성작이 없으면 [agent.md](agent.md) 1~7로 주제를 열어(주제 파일에 `target`) 이식합니다.
5. 화면마다 같은 상태 파일로 새 UI를 `taste.py refine`하고, 위 판정 기준으로 봅니다. 옛 UI에서 통과하고 새 UI에서 실패한 상태 단계가 잃어버린 기능입니다. 버튼 이름이 바뀌어 `expect`를 고쳐야 하면 옛 이름과 새 이름의 대응표를 보고에 적습니다.
6. 전과 후 보고 두 벌을 끝 보고로 줍니다. 옛 UI를 새 UI로 바꿔 끼우는 전환은 사용자가 합니다.
