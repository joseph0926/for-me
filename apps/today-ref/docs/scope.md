# 범위

## 2026-11-18 처음 범위

사용자 요청과 후속 답변은 [사용과 개발 기록](../../journal/README.md)의 `today-ref` 요청에 원문으로 있습니다.

- 시작: 사용자가 대화에서 "오늘의 레퍼런스"라고 말할 때. 정해진 시각의 자동 실행은 하지 않습니다.
- 주제: 하루에 웹이나 앱 하나. 웹과 앱을 번갈아 고르고 같은 종류의 제품을 반복하지 않습니다.
- 수집: 실제 제품과 사용자가 정한 레퍼런스 사이트의 무료 공개 범위. 캡처는 로컬에만 두고 저장소에는 링크와 직접 쓴 설명만 둡니다.
- 선택: 하나로 결정하거나 여러 개를 조합합니다. 조합에서 가져올 부분이 비어 있으면 AI가 나눠 제안하고 사용자가 확정합니다.
- 완성작: 주제마다 독립 프로젝트. 서버 없이 가짜 데이터로 주요 동작이 실제로 움직이는 수준. 앱 주제는 휴대폰 크기 틀 안에 그립니다.
- 저장: 사용자가 완성이라고 하면 상태를 완성으로 바꿉니다. 커밋은 사용자가 합니다.

### 완료 기준

- 갤러리에서 주제를 고르고, 레퍼런스 캡처를 크게 보고, 하나 또는 여러 개를 골라 선택 문장을 복사할 수 있습니다.
- 잘못된 주제 파일이 있어도 나머지 주제가 갤러리와 검사 명령에 나옵니다.
- 첫 주제를 실제로 수집해 사용자가 레퍼런스의 질을 받아들이는지 확인합니다. 보관과 자동화를 넓히는 일은 그 뒤에 정합니다. Viewgrain에서 보관할 자료가 받아들여지기 전에 보관 기능부터 넓혔던 [폐기 기록](../../../docs/retired-viewgrain.md)의 교훈입니다.

## 2026-11-18 변경: AI가 고르기

사용자가 "당신이 판단하고 고르는걸 메인으로 가져갑시다"라고 정했습니다. 같은 날 AI가 사용자 역할로 세 주제를 돌린 방식을 기본으로 삼습니다.

- 선택: AI가 레퍼런스를 비교해 하나로 결정하거나 조합하고, 가져올 부분까지 정합니다. 사용자 확인을 기다리지 않습니다.
- 피드백: AI가 완성작을 직접 써 보고 결함을 한 번 고칩니다.
- 저장: AI의 확인이 끝나면 완성으로 저장하고 보고합니다. 사용자가 아직 보지 않았다는 사실은 기록에 남깁니다.
- 사용자는 선택 대기 중에 갤러리에서 선택 문장을 복사할 수 있습니다. AI가 선택을 확정하면 갤러리는 그 결과를 보여 줍니다. 제작 중이거나 완성된 뒤에도 사용자는 대화로 레퍼런스를 다시 지정하거나 피드백할 수 있고, AI는 그것을 따릅니다.
- 위의 처음 범위 중 선택과 저장 항목은 이 변경으로 대체됩니다.

## 2026-11-27 방향: 동작 단위 수집과 근거 등급

사용자가 tastepin과 오늘의레퍼런스의 문제 정의, 수집과 소비 방향을 다시 잡으라고 요청했습니다. 원문과 성공 기준 다섯 개는 [사용과 개발 기록](../../journal/README.md)의 `today-ref` 요청에 있습니다. 전문가 역할의 하위 에이전트 다섯(제품 책임자, 디자인 디렉터, 레퍼런스 리서처, AI 에이전트 엔지니어, 유지보수 설계자)이 두 도구의 기록을 읽고 진단한 뒤 서로 반박했습니다. 아래 결정은 그 표결을 받아 AI가 정한 것이고, 사용자가 확인하기 전입니다.

### 문제 정의

- 사용자가 하는 일의 대부분이 결정이 아니라 나르기입니다. 스크린숏을 붙이고, 지적을 판정 문장으로 바꾸고, 도구를 하나씩 부릅니다.
- 실제 수요(다른 제품의 삭제와 수량 입력 화면)에는 레퍼런스가 간 적이 없습니다. 수집은 화면 단위만 있었고 `target`을 적은 주제는 없었습니다.
- tastepin 시편의 수집은 문서만 읽었습니다. 그래서 사용자가 실제 화면 근거가 없는 대안(`qtyremove.zero=trash`, `clearall.place=head`)을 실제 제품의 방식처럼 골랐습니다.
- AI 티는 값보다 구조(다른 업종의 템플릿)와 비어 있는 상태(부족, 오류, 빈 화면)에서 나옵니다. 이 둘은 취향 값이 아니라 실제 제품 레퍼런스로만 막을 수 있습니다.
- 만든 것이 쓴 것보다 빨리 늘었습니다. `identity`와 `target`을 채운 주제는 11개 중 0개이고, 다듬기 루프의 AI 지적 단계는 실제 완성작에서 끝까지 돈 적이 없습니다.

### 판단의 기준과 멈추는 조건

같은 날 AI의 맨눈 심사를 사용자의 지난 판정과 두 번 대조했습니다([검증 기록](verification.md)). 정지 화면으로 볼 수 있는 판정 5건 중 AI는 1~2건만 짚었고, 사용자가 좋다고 한 화면과 개성이 없다고 한 화면을 구별하지 못했습니다. 사용자의 지난 판정을 줘도 맞는 수는 늘지 않았고, 전에 나온 불만을 다른 화면에까지 적용했습니다. 한편 AI만 짚은 지적 중에는 화면에서 바로 확인되는 것도 있었습니다. 사용자는 "저도 1명의 개인이라 제 판단이 완벽하지 않을수있습니다"라고 정했습니다.

그래서 AI와 사용자 어느 쪽도 정답으로 두지 않고, 판단의 종류마다 기준을 나눕니다.

| 판단 | 기준 | 사용자와 AI가 다를 때 |
|---|---|---|
| 고장과 불일치(같은 사진의 재사용, 잘린 글자, 깨진 테두리, 한 화면 안에서 제각각인 같은 역할의 버튼) | 화면이나 코드에서 확인되는 사실 | 누가 말했든 확인되면 고칩니다. 사용자가 좋다고 한 화면에서도 고칩니다 |
| 구조와 동작(이 업종에서 이 화면과 이 동작이 어떻게 생겼는가) | 실제 제품 화면 근거. `evidence`가 `state`나 `still`인 레퍼런스 | 근거를 나란히 보여 주고 정합니다. 근거가 `read`나 `secondhand`뿐이면 그 사실을 함께 보여 줍니다 |
| 취향(실제 제품이 여러 방식을 다 쓸 때 어느 쪽이 좋은가) | 사용자의 선택 | 사용자가 정합니다. 정답이 아니라 그 자리의 선호로 기록하고, 뒤에 바꿀 수 있습니다. 다른 화면에서 나온 취향 규칙이 이 화면의 실제 제품 근거와 다르면 규칙대로 고치지 않고 둘을 나란히 보여 줍니다 |

- 멈추는 조건은 첫째 줄이 0건이고, 둘째 줄이 근거와 어긋나지 않고, 셋째 줄에 사용자의 이견이 없을 때입니다. AI 지적이 0개가 되는 것도, 사용자의 "좋다" 한마디도 혼자서는 멈추는 조건이 아닙니다.
- AI가 묻지 않고 고칠 수 있는 것은 첫째 줄뿐입니다. 제목을 키우자, 여백을 줄이자 같은 제안은 첫째 줄이 아니고, 근거나 사용자 선택 없이 적용하지 않습니다. 확인되지 않으면 첫째 줄로 올리지 않습니다.
- 사용자에게는 느낌을 묻기보다 실제 제품이 쓰는 방식 두세 개를 근거와 함께 놓고 고르게 합니다.
- 사용자의 판정을 다른 화면의 규칙으로 넓힐 때는 그 화면에서도 맞는지 근거로 확인합니다. 한 화면의 불만을 모든 화면에 적용하면 그 화면에서 좋았던 것까지 깎입니다.
- 재지 않은 것: AI가 자기 지적을 첫째 줄과 나머지로 스스로 가를 수 있는지.

### 호출

같은 날 사용자가 스킬 명시 호출을 선호한다며 모든 쓰임을 `/today-ref-use`의 인자로 부르게 해 달라고 요청했습니다. 첫 단어가 할 일을 정하는 [호출 표](invoke.md)를 두었고, 스킬은 그 표만 읽어 절차 문서로 넘깁니다. 자연어로 부르던 문장은 그대로 받습니다.

하지 않기로 한 것: 스킬 자동 호출 확대, 관찰 색인 같은 새 저장 형식, 사용자 캡처를 첫 경로로 두기, 완성작 여러 개에 한 값을 일괄로 넣는 소급 다듬기.
