# 완성작을 실제 화면에 쓰는 절차

다른 앱이나 저장소의 화면을 만들 때 사용자가 "오늘의 레퍼런스 대시보드 참고해서"처럼 완성작을 지정하면 이 절차를 따릅니다. 새 주제를 모으는 절차는 [agent.md](agent.md)입니다. 이 절차는 `apps/today-ref`의 파일을 고치지 않습니다. 완성작을 실행할 때 생기는 빌드 캐시는 예외입니다. 이 문서를 고칠 때는 먼저 [agent.md의 "규칙을 고칠 때"](agent.md#규칙을-고칠-때)를 따릅니다.

## 상황 판별

"오늘의 레퍼런스로 보관함 개선해줘", "오늘의 레퍼런스로 정산 페이지 처음부터 만들어줘", "오늘의 레퍼런스로 이 앱 기능은 두고 다시 만들어줘"처럼 대상과 동사만 말해도 이 절차로 받습니다. 새 명령이나 스킬을 두지 않고 이 한 문장을 진입으로 씁니다(2026-11-26 사용자 승인). 작업 위치와 동사로 상황을 하나 고르고, 시작할 때 "B로 판단: 보관함 개선, 맞는 완성작 없음, 새 주제부터"처럼 한 줄로 알립니다. 사용자가 다른 상황이라고 고치면 그 말을 따릅니다. 판별은 이 표로 하고 따로 분류하는 코드는 두지 않습니다.

| 상황 | 위치와 동사 | 진행 | 사람이 고르는 곳 |
|---|---|---|---|
| A 새 제품 | 코드가 없는 새 저장소나 for-me에서 "새로 시작", "새 제품" | 사용자가 준 주제로 [agent.md](agent.md) 1~7을 돌리고, 완성작을 새 저장소의 시작점으로 꺼냅니다. 가상 이름과 가짜 데이터는 꺼낸 뒤 대상 제품의 것으로 바꿀 자리로 보고합니다 | 없음. 끝 보고의 정체성 후보 두 개 중에서 한 문장으로 바꿀 수 있습니다(agent.md 7단계) |
| B 부분 개선 | 기존 제품 저장소에서 "개선", "고쳐", "다듬어" | 아래 1~5단계(이식) | 3단계의 보류 행 |
| C 부분 새로 만들기 | 기존 제품 저장소에서 "처음부터", "새로 만들어" | 아래 1~5단계. 옮기는 방식은 그 부분의 교체입니다. 기존 부분이 있으면 먼저 그 상태를 `states.json`으로 적어 빠뜨리지 않을 상태를 고정합니다 | 3단계의 보류 행 |
| D 전면 재설계 | 기존 제품 저장소에서 "기능은 두고", "전부 다시", "전면" | [refine.md의 "고객 제품"](refine.md#9-고객-제품)의 D 절차 | 처음 한 번(행동 목록과 정체성 후보) |

- 동사가 애매하면 범위가 작은 쪽(B)으로 판단하고 한 줄 알림에 그 사실을 적습니다. D는 바꾸는 범위가 커서, 동사가 분명하지 않으면 D로 판단하지 않습니다.
- B와 C에서 tastepin 정체성 고르기는 하지 않습니다. 대상 저장소의 토큰과 사용자 결정이 정체성입니다. 정체성을 새로 고르는 상황은 A와 D뿐입니다.
- B, C, D의 대상 저장소에 남기는 것(기존 토큰 파일, `states.json`, "UI 결정" 절)과 커밋 여부를 묻는 규칙은 [refine.md의 "고객 제품"](refine.md#9-고객-제품)을 따릅니다.

## 활용 유형

요청에 맞는 유형을 하나 고르고, 보고와 기록에 그 유형을 적습니다.

| 유형 | 요청 예 | 결과물 |
|---|---|---|
| 이식 | "보관함을 동영상 레퍼런스 참고해서 고쳐줘" | 3단계의 표와 대상 화면의 변경 |
| 검토 | "today-ref-use로 위계 검토" | 대상 화면에서 잰 값과 완성작 값을 대조한 진단, 3단계의 표. 화면은 사용자가 고치라고 한 뒤에 바꿉니다 |
| 시편 | "레퍼런스를 tastepin 시편으로 쪼개 줘" | tastepin Lab 시편. 완성작이 고른 방식을 한 값으로, 같은 주제의 다른 레퍼런스 방식과 새 대안을 비교 값으로 둡니다 |

- 세 유형 모두 1, 2단계로 완성작을 찾고 읽습니다.
- 시편은 tastepin 저장소의 시편 규칙을 따릅니다. 이미 있는 시편과 질문이 겹치는 부분은 새로 만들지 않고 보고에 적습니다. 사용자가 판정하면 완성작이 고른 방식이 몇 개 중 몇 개 채택됐는지를 `use` 기록 아래 `followup`으로 남깁니다. 이 수는 완성작이 사용자 취향과 얼마나 맞는지 보여 주는 근거입니다.

## 1. 완성작 찾기

1. `topics/*/topic.json`의 `title`, `platform`, `status`, `selection.items[].part`를 읽고 사용자가 말한 주제를 찾습니다. 제목, 주제 id, 제품 이름이나 패턴(예: "지도 마커 묶음")으로 지정할 수 있습니다.
2. 후보가 여럿이면 제목과 날짜로 고를 수 있게 보여 주고 묻습니다. 사용자가 완성작을 이름으로 지정했는데 후보가 없으면 있는 완성작 목록을 보여 주고 멈춥니다.
   - **맞는 완성작이 없을 때:** 사용자가 완성작을 지정하지 않고 대상만 말했는데(상황 판별의 A~D) 그 부분에 맞는 완성작이 없으면, 멈추지 않고 그 부분을 주제로 [agent.md](agent.md) 1~7을 돌린 뒤 이 절차의 2단계로 돌아옵니다. 주제는 사용자가 준 주제로 다루고, 주제 파일에 `target`을 적습니다(agent.md 1단계). 한 줄 알림에 새 주제부터 시작한다는 사실을 적습니다.
3. `status`가 `done`이 아니면 아직 완성 전이라는 사실을 알리고, 그래도 쓸지 묻습니다.

## 2. 읽는 순서

1. `topic.json`의 `selection.items[].part`: 레퍼런스마다 가져온 부분.
2. `works/<주제 id>/README.md`: 고른 이유, 가져온 것과 가져오지 않은 것, 사진 출처, 부분마다 그 상태로 가는 방법.
3. 필요한 부분의 소스: README와 `src/`의 파일 이름으로 해당 부분만 찾아 읽습니다. 전체를 먼저 읽지 않습니다.
4. 상태 변화나 움직임을 옮길 때는 완성작을 실행해 확인합니다. `apps/today-ref`에서 `pnpm --filter work-<주제 id> dev`로 띄우고, README에 적힌 방법으로 그 상태까지 간 뒤 확인이 끝나면 끕니다. 정지 화면이나 코드만으로 동작을 추측하지 않습니다.

`captures/`의 원래 제품 캡처는 완성작이 원본과 어떻게 다른지 확인할 때만 보고, 대상 저장소로 옮기지 않습니다.

## 3. 대상 화면에 맞추기

먼저 대상 화면의 범위를 대상 저장소의 문서(범위, 화면 설계 문서 등)와 코드에서 확인합니다. 그다음 완성작의 부분마다 대상 화면의 자리를 정해 아래 표를 만듭니다.

| 완성작의 부분 | 대상 화면의 자리 | 옮기는 방식 | 완성작 값 | 대상 값 | 확인 방법 |
|---|---|---|---|---|---|
| 예: 숙소 예약의 결과 수와 적용한 조건 칩 | 동영상 앱 보관함의 제목 옆 개수와 검색칸 아래 | 걸러진 수를 제목 옆에 붙이고 검색어를 빼기 칩으로 보여 주는 흐름만 옮기고, 컴포넌트와 색은 대상 저장소 것을 씀 | 칩 높이 32px | 대상 저장소의 칩 | 코드 |
| 예: 동영상 재생 화면의 조작 겹침 | 재생 화면 | 어둡게 덮는 비율과 사라지는 시간을 옮김 | 50%, 3초 뒤 숨김 | 50%, 3초 | 실행 |
| 예: 숙소 예약의 지도와 목록 연동 | 없음 | 옮기지 않음 | | | |

- 사용자가 부분을 지정했으면 그 부분만 표에 넣습니다. 지정하지 않았으면 `part`마다 대상 화면에 이미 있는 요소 중 맞는 자리가 있는 것만 고르고, 자리가 없는 부분은 "없음, 옮기지 않음"으로 적습니다.
- "확인 방법"은 `실행` 또는 `코드`입니다. 움직임이나 상태 변화를 옮기는 행은 완성작을 실행해 값을 확인하고 `실행`으로 적습니다. 실행하지 못했으면 `코드로만 확인`으로 적고 그 이유를 보고합니다.
- 표를 짧게 보여 주고 진행합니다. 다만 대상 범위에 없는 기능, 화면이나 데이터(예: 검색만 있는 화면에 정렬이나 필터 추가)를 새로 들이는 행이 있으면 그 행은 보류하고 사용자에게 묻습니다. 대상 화면의 기존 주요 조작(예: 카드를 누르면 바로 재생)을 바꾸는 행도 범위 안 기능이더라도 보류하고 사용자에게 묻습니다. 나머지 행은 계속합니다.
- 보류한 행은 한 번에 모아 보여 주고, 여러 개를 한꺼번에 고르거나 순서를 정할 수 있게 묻습니다.
- 대상 저장소의 디자인 규칙, 토큰과 컴포넌트가 완성작보다 우선합니다. 대상 저장소에 해당 값이 없을 때만 완성작의 값(간격, 비율, 움직임 시간 등)을 씁니다. 대상 폴더에서 `apply-context --via workflow`를 직접 실행합니다(2026-11-26 사용자 결정). 전달 기록이 대상 폴더를 `project`로 남기고, 폴더에서 찾은 토큰(색과 서체, 그리고 모서리와 간격)의 값을 넣지 않기 때문에 대상 폴더에서 실행합니다. tastepin의 구조와 동작 값(제품 시편, 컴포넌트 값, 모션)은 완성작보다 우선하지만, 범위가 있는 값은 대상 저장소의 값이 범위 안이면 그대로 둡니다. 대상 화면의 색, 서체와 제목 표현은 대상 저장소의 것을 유지하고, tastepin의 화면 전체 값(바탕색, 강조색, 서체, 제목)으로 바꾸지 않습니다. 2026-11-24 Screen Note 0.4.0에서 tastepin 기본값이 기존 개성을 지워 되돌렸습니다.

  ```sh
  cd <대상 폴더>
  python3 -B ~/dev/p/tools/taste/taste.py apply-context --surface claude --via workflow --session "$CLAUDE_CODE_SESSION_ID" --request "<대상 화면과 주요 컴포넌트>"
  ```

  `taste.py`가 없는 사본에서는 tastepin 스킬 문서의 대체 경로(대상 저장소의 `.taste/AGENT.md`)를 따르고, 그것도 없으면 취향 없이 진행했다고 보고합니다.
- 완성작의 색, 서체, 가상 제품 이름과 가짜 데이터는 가져오지 않습니다.
- 스택이 같으면(React, Tailwind) 필요한 부분의 코드를 대상 저장소의 규칙에 맞게 고쳐 옮길 수 있습니다. 스택이 다르면(예: Kotlin Compose, SwiftUI) 코드는 옮기지 않고 구조, 값과 상태 변화를 옮깁니다.
- 완성작의 Unsplash 사진을 옮기면 완성작 README의 출처를 함께 옮깁니다.
- 완성작에 없는 상태(빈 목록, 오류, 로딩, 권한 거절 등)는 대상 화면의 요구에서 새로 정합니다. 완성작에 없다는 이유로 빼지 않습니다.

## 4. 확인

- 대상 저장소의 검증 기준을 따릅니다.
- 확인 방법이 `실행`인 행은 완성작에서 확인한 상태와 같은 상태(같은 필터, 같은 선택, 같은 재생 위치)를 대상 화면에서 만들어 값과 화면을 비교합니다. 플랫폼이 달라 한 화면에 나란히 띄울 수 없으면 각각의 화면을 따로 확보해 비교합니다.
- 다르게 만든 점은 이유를 함께 보고합니다. `코드로만 확인`한 행은 보고에 따로 모읍니다.
- 이식한 화면은 완성작과 같은 [AI 슬롭 검사와 수정 루프](refine.md)를 돕니다. 대상 저장소의 개발 서버 주소와 상태 파일로 `taste.py refine`을 실행하고, 지시서의 보호 범위에는 대상 저장소의 토큰과 결정을 넣습니다. 완성작에서 고친 값(모서리, 버튼 모양, 누름 크기)을 대상 화면에 그대로 맞추지 않고, 대상 화면 안에서 같은 역할의 모양이 몇 벌인지만 줄입니다. 고객의 실제 제품 화면도 같은 검사를 받아야 데모에서만 슬롭이 없는 상태를 피할 수 있습니다(2026-11-26 결정). 검토 유형에서는 고치지 않고 `findings.json`과 보고만 돌려줍니다.

## 5. 기록

- 대상 저장소에 기록 절차가 있으면 그 절차로 요청, 변경과 검증을 남깁니다.
- 4단계 확인이 끝나면 [기록 도구](../../journal/docs/agent.md)에 앱 id `today-ref`로 `use` 기록을 하나 남깁니다. `authority`는 `interpretation`이고, 본문에 어떤 완성작의 어떤 부분을 어느 저장소의 어느 화면에 썼는지 적습니다. 기록 도구의 `parentId`는 같은 앱 안에서만 이어지므로, 대상 앱의 기록이 있으면 `source`에 그 앱 id와 기록 id를 적어 잇습니다. 이 기록은 오늘의레퍼런스가 실제로 쓰이는지 판단하는 근거입니다.
- `details`는 아래 세 줄로 씁니다. 새 주제 수집 기록(`details`가 `수집`)과 이 기록을 이 줄로 구분합니다.

  ```text
  활용: 이식
  부분: <주제 id> r1, r6
  코드로만 확인: r6
  ```

  `활용`은 이식, 검토, 시편 중 하나입니다. `코드로만 확인`에는 3단계 표에서 `코드로만 확인`으로 남은 레퍼런스 id를 적고, 없으면 `없음`으로 적습니다. 나중에 그 부분을 실행해 확인하면 `followup`으로 확인한 결과를 남기고 `record.update`로 이 줄에서 뺍니다.
- 같은 세션에서 옮긴 부분을 되돌리거나 다시 고쳤으면 세션을 마치기 전에 `use` 기록 아래 `followup`으로 남깁니다. 사용자 원문이 있으면 `authority: user`, AI가 판단한 것이면 `interpretation`입니다.
- 사용자가 결과 화면을 판정하면 대상 앱의 기록 절차에 남깁니다. 그 판정이 오늘의레퍼런스 완성작이나 옮긴 부분에 대한 것이면(예: "이 레퍼런스는 이 앱에 안 맞는다", "상세 보기를 따로 버튼으로 빼 주세요") 같은 원문을 위 `use` 기록 아래 `followup`(`authority: user`)으로도 남깁니다.

### 회고

다른 세션에서 나중에 되돌린 부분은 위 규칙으로 잡히지 않습니다. 그래서 오늘의레퍼런스 규칙을 고칠 때마다 [agent.md의 "규칙을 고칠 때"](agent.md#규칙을-고칠-때) 1단계로 회고를 돌립니다. 회고에서는 `read`로 `details`가 `활용:`으로 시작하는 `use` 기록을 고르고, 대상 앱 기록 중 `source`나 `parentId`로 그 활용과 이어진 변경과 후속 기록을 모아 읽습니다. 이미 어느 `followup`의 `source`에 들어간 기록 id는 건너뜁니다. 되돌림이나 수정을 찾으면 그 기록 id를 `source`에 적어 `use` 기록 아래 `followup`(`authority: interpretation`)으로 남깁니다.
