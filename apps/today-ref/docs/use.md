# 완성작을 실제 화면에 쓰는 절차

다른 앱이나 저장소의 화면을 만들 때 사용자가 "오늘의 레퍼런스 대시보드 참고해서"처럼 완성작을 지정하면 이 절차를 따릅니다. 새 주제를 모으는 절차는 [agent.md](agent.md)입니다. 이 절차는 `apps/today-ref`의 파일을 고치지 않습니다. 완성작을 실행할 때 생기는 빌드 캐시는 예외입니다.

## 1. 완성작 찾기

1. `topics/*/topic.json`의 `title`, `platform`, `status`, `selection.items[].part`를 읽고 사용자가 말한 주제를 찾습니다. 제목, 주제 id, 제품 이름이나 패턴(예: "지도 마커 묶음")으로 지정할 수 있습니다.
2. 후보가 여럿이면 제목과 날짜로 고를 수 있게 보여 주고 묻습니다. 후보가 없으면 있는 완성작 목록을 보여 주고 멈춥니다.
3. `status`가 `done`이 아니면 아직 완성 전이라는 사실을 알리고, 그래도 쓸지 묻습니다.

## 2. 읽는 순서

1. `topic.json`의 `selection.items[].part`: 레퍼런스마다 가져온 부분.
2. `works/<주제 id>/README.md`: 고른 이유, 가져온 것과 가져오지 않은 것, 사진 출처.
3. 필요한 부분의 소스: README와 `src/`의 파일 이름으로 해당 부분만 찾아 읽습니다. 전체를 먼저 읽지 않습니다.
4. 상태 변화나 움직임을 옮길 때는 완성작을 실행해 확인합니다. `apps/today-ref`에서 `pnpm --filter work-<주제 id> dev`로 띄우고, 확인이 끝나면 끕니다. 정지 화면만으로 동작을 추측하지 않습니다.

`captures/`의 원래 제품 캡처는 완성작이 원본과 어떻게 다른지 확인할 때만 보고, 대상 저장소로 옮기지 않습니다.

## 3. 대상 화면에 맞추기

먼저 대상 화면의 범위를 대상 저장소의 문서(범위, 화면 설계 문서 등)와 코드에서 확인합니다. 그다음 완성작의 부분마다 대상 화면의 자리를 정해 아래 표를 만듭니다.

| 완성작의 부분 | 대상 화면의 자리 | 옮기는 방식 |
|---|---|---|
| 예: 숙소 예약의 결과 수와 적용한 조건 칩 | 동영상 앱 보관함의 제목 옆 개수와 검색칸 아래 | 걸러진 수를 제목 옆에 붙이고 검색어를 빼기 칩으로 보여 주는 흐름만 옮기고, 컴포넌트와 색은 대상 저장소 것을 씀 |
| 예: 숙소 예약의 지도와 목록 연동 | 없음 | 옮기지 않음 |

- 사용자가 부분을 지정했으면 그 부분만 표에 넣습니다. 지정하지 않았으면 `part`마다 대상 화면에 이미 있는 요소 중 맞는 자리가 있는 것만 고르고, 자리가 없는 부분은 "없음, 옮기지 않음"으로 적습니다.
- 표를 짧게 보여 주고 진행합니다. 다만 대상 범위에 없는 기능, 화면이나 데이터(예: 검색만 있는 화면에 정렬이나 필터 추가)를 새로 들이는 행이 있으면 그 행은 보류하고 사용자에게 묻습니다. 나머지 행은 계속합니다.
- 대상 저장소의 디자인 규칙, 토큰과 컴포넌트가 완성작보다 우선합니다. 대상 저장소에 해당 값이 없을 때만 완성작의 값(간격, 비율, 움직임 시간 등)을 씁니다. 사용자가 이번 작업에 tastepin을 불렀다면 그 기본값도 완성작보다 우선합니다. tastepin은 사용자가 부르는 스킬이라 AI가 대신 부르지 않습니다.
- 완성작의 색, 서체, 가상 제품 이름과 가짜 데이터는 가져오지 않습니다.
- 스택이 같으면(React, Tailwind) 필요한 부분의 코드를 대상 저장소의 규칙에 맞게 고쳐 옮길 수 있습니다. 스택이 다르면(예: Kotlin Compose, SwiftUI) 코드는 옮기지 않고 구조, 값과 상태 변화를 옮깁니다.
- 완성작의 Unsplash 사진을 옮기면 완성작 README의 출처를 함께 옮깁니다.
- 완성작에 없는 상태(빈 목록, 오류, 로딩, 권한 거절 등)는 대상 화면의 요구에서 새로 정합니다. 완성작에 없다는 이유로 빼지 않습니다.

## 4. 확인

- 대상 저장소의 검증 기준을 따릅니다.
- 가져온 부분은 완성작과 같은 상태(같은 필터, 같은 선택)로 나란히 띄워 비교하고, 다르게 만든 점은 이유를 함께 보고합니다.

## 5. 기록

- 대상 저장소에 기록 절차가 있으면 그 절차로 요청, 변경과 검증을 남깁니다.
- 4단계 확인이 끝나면 [기록 도구](../../journal/docs/agent.md)에 앱 id `today-ref`로 `use` 기록을 하나 남깁니다. `authority`는 `interpretation`이고, 본문에 어떤 완성작의 어떤 부분을 어느 저장소의 어느 화면에 썼는지 적습니다. 기록 도구의 `parentId`는 같은 앱 안에서만 이어지므로, 대상 앱의 기록이 있으면 `source`에 그 앱 id와 기록 id를 적어 잇습니다. 이 기록은 오늘의레퍼런스가 실제로 쓰이는지 판단하는 근거입니다.
- 사용자가 결과 화면을 판정하면 대상 앱의 기록 절차에 남깁니다. 그 판정이 오늘의레퍼런스 완성작에 대한 것이면(예: "이 레퍼런스는 이 앱에 안 맞는다") 같은 원문을 위 `use` 기록 아래 `followup`(`authority: user`)으로도 남깁니다.
