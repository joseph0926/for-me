# 음악 앱 검증 기록

재생 엔진 선택과 앱 동작을 확인한 기록입니다. 기술 선택의 근거는 [기술 조사](research.md)에 있습니다.

## 2026-11-28 Media3 가상 기기 최소 실험

사용자가 권장안(Media3)으로 정하되 그 권장안이 최선인지 검증이 필요하다고 했고, 가상 기기를 활용하라고 했습니다. 저장소 밖 임시 폴더에 최소 앱을 만들어 실험했고, 끝난 뒤 가상 기기에서 지웠습니다. 앱 코드는 저장소에 남기지 않았습니다.

### 환경

- 가상 기기: `Pixel_6_Pro_API_34`, Android 14(API 34). 이 Mac에 Android 17 이미지가 없어 Android 17의 백그라운드 제한은 시험하지 않았습니다.
- 앱: Media3 1.11.1의 `ExoPlayer`와 `MediaSessionService`, 화면은 `MediaController`로 연결. compileSdk와 targetSdk 36, AGP 8.13.2, Kotlin 2.2.21(장면과 같은 값). 확장 디코더 없이 기기 디코더만 사용.
- 음원: ffmpeg 9.0.2로 440Hz 사인파 10초를 만들어 정확히 5초에서 두 곡으로 자른 뒤 형식마다 인코딩했습니다. AAC는 ffmpeg와 macOS `afconvert` 두 가지로 만들었습니다. `afconvert` 파일에는 iTunes 파일처럼 `iTunSMPB` 태그가 있습니다.
- 판정: 재생기 안에 출력 소리를 WAV로 함께 쓰는 처리기(`TeeAudioProcessor`)를 넣어, 곡마다 실제로 낸 표본 수와 사인파 위상을 기대값(곡마다 정확히 5초, 두 번째 곡은 5초 지점 위상)과 비교했습니다. 가상 기기의 스피커 출력은 듣지 않았습니다.

### 형식과 곡 사이 끊김

길이차는 곡마다 기대보다 더 낸 표본 수입니다. 첫 곡의 길이차가 0이면 두 곡이 끊김 없이 이어진 것입니다. 두 번째(마지막) 곡의 길이차는 재생 목록 끝에 붙는 무음이라 듣는 데는 영향이 없습니다.

| 형식 | 디코더 | 첫 곡 길이차 | 마지막 곡 길이차 | 판정 |
|---|---|---|---|---|
| FLAC 16비트 44.1kHz | `c2.android.flac.decoder` | 0 | 0 | 끊김 없음 |
| FLAC 24비트 96kHz | `c2.android.flac.decoder` | 0 | 0 | 끊김 없음(출력은 16비트로 변환) |
| WAV 16비트 | 없음(PCM) | 0 | 0 | 끊김 없음 |
| MP3(LAME 192kbps) | `c2.android.mp3.decoder` | 0 | +731 | 곡 사이 끊김 없음. 마지막 곡 끝 패딩이 남음 |
| AAC(`afconvert`, `iTunSMPB` 있음) | `c2.android.aac.decoder` | 0 | +620 | 곡 사이 끊김 없음. 마지막 곡 끝 패딩이 남음 |
| AAC(ffmpeg, 끝 패딩 정보 없음) | `c2.android.aac.decoder` | +684 | +684 | 곡 사이 15.5ms 틈 |
| Opus(Ogg, libopus 128kbps) | `c2.android.opus.decoder` | +648 | +648 | 곡 사이 13.5ms 틈 |
| ALAC(M4A) | 없음 | 출력 없음 | 출력 없음 | 재생 실패 |

- MP3는 두 곡의 시작 위상이 똑같이 27.9표본 어긋났습니다. 곡 사이에서는 이어지므로 끊김은 아닙니다.
- ALAC는 트랙이 "지원 안 함"으로 판정돼 오디오가 선택되지 않았습니다. 그런데도 재생기는 오류 없이 재생 중, 다음 곡, 끝 상태를 차례로 거쳤습니다. 앱이 `Tracks`에서 오디오가 선택되지 않은 경우를 직접 잡아 알리지 않으면 사용자는 소리 없는 재생만 보게 됩니다.
- Media3 1.12.0-rc01의 릴리스 노트에는 Opus 끝 패딩 제거와 마지막 곡 끝 패딩 제거가 있습니다. 하지만 1.12.0-rc01은 compileSdk 37을 요구하고, 이 Mac에는 Android 37 SDK 플랫폼이 없어 빌드하지 못했습니다. 고쳐졌는지는 미검증입니다.

### 화면 밖 재생

120초 FLAC을 재생하다가 홈으로 나가고 화면을 껐습니다(`mWakefulness=Asleep`).

- 화면을 끈 직후 재생 위치는 5.9초, 30초 뒤에는 36.0초였고 상태는 계속 `PLAYING`이었습니다.
- 서비스는 `isForeground=true`, 유형 `mediaPlayback`(`types=00000002`)으로 실행 중이었습니다. 알림은 `category=transport`인 미디어 알림 하나였습니다. 알림은 따로 만들지 않았고 Media3가 자동으로 만들었습니다.
- 재생기가 낸 소리는 파일 크기로 46.9초 분량으로, 실행부터 종료까지의 시간과 맞았습니다.
- 오류, 버퍼 부족(underrun) 기록은 없었습니다.

### 실행하지 못한 검사

- Android 17(API 37) 가상 기기와 `adb shell cmd audio set-enable-hardening throw`를 켠 화면 밖 재생
- Media3 1.12.0-rc01의 Opus와 마지막 곡 끝 패딩 처리
- FFmpeg 확장 디코더로 ALAC 재생
- libVLC와의 같은 조건 비교
- 실제 휴대폰의 디코더(제조사 디코더는 가상 기기의 `c2.android.*`와 다를 수 있습니다), 이어폰 분리, 최근 앱에서 지우기, 일시정지 10분 뒤 동작, 재부팅 뒤 이어듣기
- 사용자의 실제 음악 파일 형식

## 2026-11-28 Android 17 가상 기기의 백그라운드 오디오 강제 검사

[기술 조사](research.md#검증-결과와-남은-조건)의 Media3 확정 조건 1을 Windows에서 검사했습니다. 이 PC에는 Android 37 SDK 플랫폼과 가상 기기 이미지가 이미 있었습니다. 저장소 밖 임시 폴더에 최소 앱을 만들었고, 끝난 뒤 가상 기기에서 지우고 강제 설정을 되돌렸습니다. 앱 코드는 저장소에 남기지 않았습니다.

### 환경

- 가상 기기: `Medium_Phone_API_37.0`, Android 17(API 37), `google/sdk_gphone64_x86_64/emu64xa:17/CE2A.260420.051.A2/16418371`. 창 없이 실행했습니다.
- 앱 A: Media3 1.11.1, compileSdk와 targetSdk 36, AGP 8.13.2, Kotlin 2.2.21, Build-Tools 36.0.0(장면과 같은 값).
- 앱 B: Media3 1.12.0-rc01, compileSdk와 targetSdk 37, Build-Tools 37.0.0. AGP 8.13.2로 빌드됐고 "compile SDK 36.1까지만 시험했다"는 경고가 나왔습니다.
- 구조: 권장안대로 `ExoPlayer`와 `MediaSession`을 `MediaSessionService` 안에 두고, 화면은 `MediaController`로 연결했습니다. 대조군(`mode=bare`)은 서비스 없이 화면이 직접 `ExoPlayer`를 들고 재생합니다. 두 구조 모두 오디오 포커스를 재생기에 맡겼습니다.
- 음원: Python으로 만든 440Hz 사인파 120초 WAV(모노, 16비트, 44.1kHz)를 앱 전용 외부 폴더에 넣었습니다.
- 강제 설정: `adb shell cmd audio set-hardening throw`. 공식 문서의 `set-enable-hardening`은 이 이미지에 없고, `cmd audio help`에 나온 이름은 `set-hardening <1|enable|0|disable|throw>`와 `clear-hardening`입니다.
- 알림 권한은 `pm grant`로 미리 줬습니다.

### 순서

앱 실행 → 5초 뒤 홈 → 3초 뒤 화면 끄기(`mWakefulness=Asleep`) → 20초 뒤 `cmd media_session dispatch pause` → 12초 뒤 `dispatch play` → 15초 뒤 확인. 위치는 앱이 5초마다 logcat에 남긴 값, 서비스 상태는 `dumpsys activity services`, 위반은 logcat과 `dumpsys audio`의 `AudioHardening` 기록으로 봤습니다.

### 결과

| 실행 | 화면 밖 재생 | 일시정지와 재개 | 포그라운드 서비스 | 새 위반 기록 |
|---|---|---|---|---|
| 앱 A 세션 구조, 1회차 | 화면을 끈 뒤 30초 동안 위치 39.4초 → 79.4초 | 미실행(아래 참고) | `isForeground=true`, `types=0x00000002`, 미디어 세션 알림 | 0 |
| 앱 A 세션 구조, 2회차 | 위치 계속 증가 | 일시정지 중 27.9초에서 멈춤, 재개 뒤 43.0초까지 증가 | 일시정지 중과 재개 뒤 모두 유지 | 1(아래 참고) |
| 앱 A 세션 구조, 3회차(먼저 강제 종료) | 위치 계속 증가 | 일시정지 중 27.6초에서 멈춤, 재개 뒤 증가 | 유지 | 0 |
| 앱 B 세션 구조 | 위치 계속 증가 | 일시정지 중 28.0초에서 멈춤, 재개 뒤 증가 | 유지 | 0 |
| 앱 A 대조군, `throw` | 홈 6초 뒤 막힘 | 해당 없음 | 서비스 없음 | 1, `level: partial`. 재생기가 `ERROR_CODE_AUDIO_TRACK_WRITE_FAILED`(AudioTrack 쓰기 -4)로 멈춤 |
| 앱 A 대조군, `enable` | 홈 5초 뒤 막힘 | 해당 없음 | 서비스 없음 | 1, `level: partial`. 재생기는 오류 없이 `playing=true`로 위치를 계속 늘림 |

- 1회차의 일시정지는 `input keyevent KEYCODE_MEDIA_PAUSE`로 보냈는데 반영되지 않아 위치가 계속 늘었습니다. 2회차부터 `cmd media_session dispatch`를 썼습니다. 화면이 꺼진 상태에서 `input keyevent` 미디어 키가 왜 세션에 가지 않았는지는 확인하지 않았습니다.
- 2회차의 위반 1건(03:22:55.605)은 새 실행이 시작되기(03:22:56.473) 전, 1회차가 재생 중일 때 `am start -S`로 강제 종료한 순간에 남았습니다. 먼저 강제 종료한 3회차와 앱 B에서는 새 기록이 없었습니다.
- 대조군이 막히는 것으로 이 검사가 위반을 잡는다는 것을 확인했습니다. 기본 강제 모드에서는 소리가 막혀도 재생기 상태가 그대로이므로, 앱의 재생 상태만으로는 이 실패를 알 수 없습니다.
- `dispatch stop` 뒤 5초가 지나도 서비스는 포그라운드였습니다. Media3는 멈춘 뒤 10분이 지나야 포그라운드에서 내려온다고 문서에 적혀 있으며, 10분 뒤 동작은 기다리지 않았습니다.

### 실행하지 못한 검사

- Media3 1.12.0-rc01의 Opus 곡 사이 처리: Windows에 Opus 음원을 만들 ffmpeg가 없습니다.
- 실제 휴대폰의 Android 17, 화면 밖에서 시작한 재생(알림이나 블루투스 버튼으로 서비스가 내려간 뒤 재개), 일시정지 10분 뒤 동작, 재부팅 뒤 이어듣기
- 강제 설정 없이 targetSdk 37만으로 적용되는 기본 규칙(강제 설정이 대상 SDK와 관계없이 같은 조건을 적용하므로 따로 돌리지 않았습니다)

### 검사 중 생긴 일

- 첫 빌드에서 앱의 `buildToolsVersion`을 정하지 않아 AGP가 Android SDK에 Build-Tools 35.0.0을 자동으로 설치했습니다(`%LOCALAPPDATA%\Android\Sdk\build-tools\35.0.0`). 이후 빌드는 설치돼 있던 36.0.0과 37.0.0으로 지정했습니다. 35.0.0을 지울지는 사용자 결정 대기입니다.
- 후속(2026-11-28): 사용자 결정으로 Build-Tools 35.0.0을 휴지통으로 옮겼습니다.

## 2026-11-28 Media3 1.12의 Opus 곡 사이 측정

[기술 조사](research.md#검증-결과와-남은-조건)의 Media3 확정 조건 3을 Windows에서 검사했습니다. 사용자 승인으로 Opus 음원을 만들 ffmpeg(winget `Gyan.FFmpeg` 9.1, `libopus` 포함)를 설치했습니다. 다른 세션이 켜 둔 `Medium_Phone_API_37.0` 가상 기기는 건드리지 않고, 같은 Android 17 이미지로 실험 전용 가상 기기를 임시 폴더에 만들어 쓴 뒤 지웠습니다. 실험 앱은 저장소 밖 임시 폴더에 만들었고 끝난 뒤 지웠습니다.

### 환경

- 가상 기기: Android 17(API 37) `google_apis_playstore` x86_64 이미지, 기기 정의 `medium_phone`. 디코더는 기기 디코더(`c2.android.opus.decoder`)만 씁니다.
- 앱 A: Media3 1.11.1, compileSdk와 targetSdk 36. 앱 B: Media3 1.12.0-rc01, compileSdk와 targetSdk 37. 구조는 [Android 17 강제 검사](#2026-11-28-android-17-가상-기기의-백그라운드-오디오-강제-검사)와 같고, 재생기 출력을 WAV로 함께 쓰는 처리기(`TeeAudioProcessor`)를 넣었습니다.
- 음원: ffmpeg로 440Hz 사인파 10초(48kHz 모노)를 만들고 정확히 240,000번째 표본에서 둘로 잘랐습니다. 대조군은 16비트 WAV 두 곡, 실험군은 libopus 128kbps Ogg Opus 두 곡입니다(ffmpeg 9.1, `Lavc63.24.100 libopus`). Opus 파일의 앞부분 건너뛰기 값(pre-skip)은 312표본입니다.
- 판정: 곡마다 기대 길이는 240,000표본입니다. 둘째 곡만 재생한 출력 길이와 두 곡 연속 재생의 출력 길이를 재서, (연속 길이 − 240,000 − 둘째 곡 단독 길이)를 첫 곡 뒤 틈으로 봅니다. 위상 비교 없이 길이만으로 틈을 구합니다. 각 조건을 두 번씩 돌렸습니다.

### 결과

| 형식 | Media3 | 둘째 곡 단독 | 두 곡 연속 | 첫 곡 뒤 틈 | 마지막 곡 끝 패딩 |
|---|---|---|---|---|---|
| WAV(대조) | 1.11.1 | 240,000 | 480,000 | 0 | 0 |
| WAV(대조) | 1.12.0-rc01 | 240,000 | 480,000 | 0 | 0 |
| Ogg Opus | 1.11.1 | 240,648 | 481,296 | +648(13.5ms) | +648 |
| Ogg Opus | 1.12.0-rc01 | 240,000 | 480,000 | 0 | 0 |

- 두 회차의 값이 모두 같았습니다.
- 1.11.1의 Opus 값은 Mac의 Android 14 실험(+648, +648)과 같습니다. 인코더 버전(ffmpeg 9.0.2와 9.1)과 Android 버전이 달라도 재현됐습니다.
- 1.12.0-rc01의 두 곡 연속 출력을 이상적인 사인파와 비교했습니다. 경계 주변 2,000표본의 상대 오차는 0.91%로, 각 곡 가운데 구간(0.61%, 0.69%)과 같은 수준이었습니다. 648표본이 밀리면 이 오차가 100%에 가까워지므로, 경계에서 파형이 이어진 것으로 판단했습니다.
- 출력 WAV는 곡이 바뀔 때 여러 파일로 나뉘었습니다(1.12 연속 재생: 240,000, 648, 239,352). 처리기가 다시 설정될 때 새 파일을 여는 것으로 보이며, 판정은 파일 길이의 합으로 했습니다.

### 실행하지 못한 검사

- 실제 휴대폰의 Opus 디코더(제조사 디코더가 가상 기기와 다를 수 있습니다)
- WebM Opus, 다른 비트레이트와 스테레오 Opus
- Media3 1.12 안정판(아직 시험판 rc01만 있습니다)

## 2026-11-28 사용자 음악 파일의 형식 확인

[기술 조사](research.md#검증-결과와-남은-조건)의 Media3 확정 조건 2를 Windows에서 확인했습니다. 사용자가 휴대폰 음악을 PC의 폴더 하나로 옮겨 주었고, ffprobe와 ffmpeg(9.1)로 형식과 헤더만 읽었습니다. 파일은 수정하지 않았습니다. 가상 기기나 휴대폰에서 이 파일들을 재생하지는 않았습니다.

### 결과

- 12곡 모두 MP3입니다. 44.1kHz 스테레오이고, 11곡은 가변 비트레이트(평균 약 115~125kbps, `Xing` 헤더), 1곡은 고정 128kbps(`Info` 헤더)입니다. 인코더는 ffmpeg의 libmp3lame(`Lavc59.37` 11곡, `Lavc56.60` 1곡)입니다.
- 12곡 모두 첫 프레임에 LAME 형식의 인코더 지연(576표본)과 끝 패딩 값이 있습니다. Media3가 곡 사이를 잇는 데 쓰는 정보입니다.
- 12곡 모두 ID3 태그에 500x500 PNG 앨범 아트가 들어 있습니다.
- 태그 내용은 동영상 사이트에서 받은 파일의 형태입니다. 제목에는 "가수 - 곡명 | 공연 날짜" 같은 영상 제목이, 아티스트에는 올린 채널 이름이 있고, 앨범은 제목과 같습니다. 12곡 모두 아티스트가 실제 가수가 아니라 올린 채널 이름이고, 9곡이 같은 채널입니다. 파일 이름은 대부분 곡명만 있어 태그 제목보다 짧습니다.
- 1곡은 헤더가 적은 길이(5분 10초)보다 실제 소리가 짧습니다(끝까지 풀었을 때 3분 12초). ffmpeg는 "filesize and duration do not match" 경고를 냈습니다. 받는 도중 잘린 파일로 보입니다. 나머지 11곡은 헤더 길이와 실제 길이가 0.02초 안에서 같았습니다.

### 판정

- 조건 2: 이 폴더의 형식은 MP3 하나이고, MP3는 [Android 14 실험](#2026-11-28-media3-가상-기기-최소-실험)에서 기기 디코더로 곡 사이 끊김 없이 재생됐습니다. FFmpeg 확장은 필요하지 않습니다. 파일 형식 기준의 판정이며, 이 파일들 자체의 재생은 확인하지 않았습니다.
- 조건 3: Opus가 없어 해당하지 않습니다. Media3 1.12와 compileSdk 37은 필요하지 않습니다.

### 앱 설계에 주는 점(AI 해석)

- 아티스트와 앨범 태그로 묶는 보관함은 이 음악에서 거의 쓸모가 없습니다. 곡 목록과 재생 목록이 중심이 되고, 표시 이름은 태그 제목과 파일 이름 중 무엇을 쓸지 정해야 합니다.
- 헤더 길이가 틀린 파일이 실제로 있습니다. 진행 막대, 남은 시간, 저장한 재생 위치가 실제 끝보다 뒤를 가리킬 수 있으므로, 재생이 헤더 길이보다 일찍 끝나는 경우와 저장 위치가 실제 길이를 넘는 경우를 검사에 넣습니다.

### 검사 중 찾아 고친 결함

- **잘린 곡이 헤더 길이까지 소리 없이 머묾(최초 실패):** 처음부터 재생한 `부디`가 실제 끝(3:12) 뒤에도 재생 중 상태로 위치만 늘다가 헤더 길이(5:10)에서야 다음 곡으로 넘어갔습니다. 3:05로 옮긴 경우도 5:10까지 머물렀습니다. 파일에는 7,369프레임(192.5초)만 있습니다. Media3 1.11.1은 Xing 헤더의 길이를 믿고, 재생 위치가 그 길이에 닿아야 곡을 끝냅니다(`ExoPlayerImplInternal`의 `playingPeriodDurationUs <= positionUs`). 앱에서 MP3 추출기를 감싸, 파일 끝까지 읽었는데 마지막 표본이 헤더 길이보다 1초 넘게 앞이면 길이를 읽은 만큼으로 다시 알리게 했습니다. 고친 빌드로 같은 조건에서 3:12에 넘어감을 확인했고, 잘린 사본과 온전한 사본으로 만든 단위 검사를 더했습니다.
  - 남은 한계: 재생을 시작한 직후에는 남은 시간이 헤더 길이로 보이다가, 파일을 끝까지 읽은 뒤에 바뀝니다. 잘린 곡 안에서 위치를 옮기면 헤더의 위치표를 따르므로 표시 위치와 실제 소리가 어긋납니다.
- **지운 곡의 안내가 보이지 않음(최초 실패):** 대기열에서 지운 곡을 누르자 다음 곡으로 넘어갔지만 안내가 없었습니다. 안내 칸이 재생 화면과 대기열 밑에 깔렸고, 서비스가 곧바로 다음 곡으로 넘겨 화면이 오류 상태를 받지 못했습니다. 안내 칸을 모든 화면 위로 옮기고 이유를 세션 오류(`MediaSession.sendError`)로 보내게 했습니다. 고친 빌드에서 "재생할 수 없는 곡입니다: 아라리. 파일이 옮겨지거나 지워졌을 수 있습니다."가 보이고 다음 곡이 재생됐습니다.
- **같은 곡이 두 번 보임(최초 실패):** 파일 선택기로 추가한 곡이 음악 권한을 허용한 뒤 음악 목록의 같은 곡과 함께 두 줄로 보였습니다. 다운로드 문서 주소(`msf:23`)는 `MediaStore.getMediaUri`가 "Provider for this Uri is not supported"로 거절해, `msf:` 뒤 번호를 MediaStore 번호로 옮겨 같은 파일인지 판단하게 했습니다. 고친 빌드에서 권한이 있으면 한 줄, 없으면 직접 추가한 곡만 보였습니다. `msf:` 형식은 공식 문서에 없는 관찰값입니다.

### 그 밖의 발견

- 다른 앱이 `Download` 폴더에 넣은 음악도 미디어 분석을 마치면 `READ_MEDIA_AUDIO`만으로 목록에 나왔습니다. 분석 전에는 음악 여부가 비어 있어(`is_music=NULL`) 목록에 나오지 않았습니다. 휴대폰에서 받은 직후의 파일이 바로 보이는지는 확인하지 않았습니다.
- 새 재생 목록의 이름 칸은 눌러야 키보드가 열립니다. 이름 칸에 처음부터 초점을 두지 않았습니다.
- 첫 빌드에서 Gradle이 Media3 세션이 요구하는 `androidx.lifecycle:lifecycle-service:2.9.4`를 내려받았습니다. 채택한 Media3의 하위 의존성입니다.
