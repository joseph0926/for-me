## 등록 이슈

아래 열 건은 2026-11-23 코드 리뷰(코드 품질 기록 `2026-11-23-for-me-screen-note-review`)에서 나왔다. 리뷰는 커밋 `c7eaa58`의 소스를 읽기만 했고 앱을 실행하지 않았다. 수정은 같은 날 그 커밋 위의 커밋하지 않은 변경이며, 재검증에 쓴 "브라우저 빌드"는 수정한 코드를 `corepack pnpm build`로 만든 화면을 Chromium에서 연 것이다. 수정한 코드로 Tauri 앱은 만들지 않았다.

### QA-001 색을 한 번 고르면 되돌리기 기록이 여러 건 쌓임

- 상태: 완료. macOS 앱에서 확인한 범위다.
- 우선순위: 보통
- 발견일: 2026-11-23, 코드 리뷰. 사례 ID `2026-11-23-for-me-screen-note-review-color-undo`.
- 영향: 색을 한 번 바꾼 뒤 되돌리기를 누르면 고르는 도중의 중간 색으로 한 단계씩만 돌아간다. 그 앞의 이동이나 자르기를 되돌리려면 이 기록을 모두 지나야 한다.
- 기대 동작: README의 "되돌리기로 마지막 편집을 취소"대로, 색 고르기 한 번은 되돌리기 한 번으로 고르기 전 색이 된다.
- 재현: 정적 검토만 했다. 표시를 선택하고 색상 선택 창에서 색을 끌어 고르면 색이 바뀔 때마다 편집 기록이 추가되는 구조였다. 실제 운영체제 색상 선택 창에서 쌓이는 건수는 재지 않았다.
- 증거: 수정 전 `src/Editor.tsx`의 `MarkSettings onColor`와 선택한 펜 획의 `PenSettings onChange`가 색 입력의 변경마다 `storeMark`를 불렀다.
- 원인: 색 입력은 고르는 동안 변경 이벤트를 계속 보내는데(확인한 사실은 React가 `input` 이벤트마다 `onChange`를 부른다는 것, 운영체제 창이 보내는 빈도는 추정) 변경마다 편집 기록을 한 건씩 만들었다.
- 다음 조치: macOS 앱에서 색상 선택 창으로 색을 끌어 고른 뒤 되돌리기 한 번으로 원래 색이 되는지 확인한다.
- 수정: `src/document.ts`의 `recolorMark`가 같은 표시의 연속된 색 변경을 편집 기록 한 건으로 묶는다. 다른 편집이 사이에 끼면 새 기록이 된다.
- 재검증: 2026-11-23, 브라우저 빌드. 색 입력에 변경 여섯 번을 보낸 뒤 되돌리기 한 번으로 원래 색 `#ee5319`가 됐고 표시는 남았다. 새 자동 검사는 묶기를 끄면 실패했다. 운영체제 색상 선택 창은 미확인이다.
- 앱 재검증: 2026-11-23, 수정 빌드 macOS 앱(실행 파일 SHA-256 `6b8f871c460fb5b8881a06e35fe7678c9e0c27f1c355845f2af1662c283c30ab`), Apple M2, macOS 27.2.1(26B131). 통과. 가리기를 선택하고 채우기 색 칸의 견본 팝오버에서 "Show Colors..."로 macOS 색상 창을 연 뒤 색상 휠을 두 번 끌었다. 끄는 동안 가리기 색이 붉은색, 보라색, 청록색, 올리브색으로 계속 바뀌었고, 되돌리기 한 번으로 고르기 전 어두운 회색이 됐으며 표시는 남았다. 선택한 펜 획의 선 색도 같은 방법으로 노랑, 초록, 청록, 보라로 바뀐 뒤 되돌리기 한 번으로 원래 주황색이 됐고 획은 남았다. 견본 팝오버의 칸을 끌어 고르는 경로와 메모 글자색은 따로 보지 않았다.

### QA-002 이미지 파일을 창에 끌어다 놓으면 편집 화면이 사라질 수 있음

- 상태: 재검증 대기. macOS의 파일 놓기는 통과했고 링크 놓기와 Windows가 남았다.
- 우선순위: 높음(사실이면 복사하지 않은 편집을 잃는다)
- 발견일: 2026-11-23, 코드 리뷰. 사례 ID `2026-11-23-for-me-screen-note-review-webview-default-loss`.
- 영향: 웹뷰가 놓은 파일로 이동하면 편집 화면과 편집 내용이 사라진다. 저장 기능이 없어 복구할 수 없다.
- 기대 동작: 놓은 이미지를 편집기가 열고, 편집 중이면 교체 확인을 띄운다. 이미지가 아닌 파일은 열기 실패 안내를 보인다.
- 재현: 미확인. 정적 검토만 했고 수정 전 앱에 파일을 놓아 보지 않았다. `src-tauri/tauri.conf.json`의 `dragDropEnabled: false`로 Tauri가 놓기를 가로채지 않는데 화면 코드에 놓기 처리가 없었다는 사실에서 추론했다.
- 증거: 수정 전 `src`에 `dragover`와 `drop` 처리가 없었다.
- 원인: 추정. 처리기가 없으면 WKWebView와 WebView2는 놓은 파일의 주소로 이동한다.
- 다음 조치: macOS 앱에서 표시를 그린 뒤 Finder의 PNG를 창에 놓아 교체 확인이 뜨는지, 이미지가 아닌 파일과 링크를 놓아도 화면이 유지되는지 확인한다. Windows도 같은 순서로 확인한다.
- 수정: `src/main.tsx`가 `dragover`와 `drop`의 기본 동작을 막고 놓은 파일을 기존 열기 경로로 넘긴다. 글 입력란에 글을 놓는 경우만 웹뷰에 맡긴다.
- 재검증: 2026-11-23, 브라우저 빌드. 합성한 놓기 이벤트로 PNG가 열렸고, 편집 중에는 교체 확인이, 글 파일에는 열기 실패 안내가 나왔으며 기존 문서는 유지됐다. 운영체제에서 실제로 끌어다 놓는 동작과 Tauri 앱은 미확인이다.
- 앱 재검증: 2026-11-23, 수정 빌드 macOS 앱(실행 파일 SHA-256 `6b8f871c460fb5b8881a06e35fe7678c9e0c27f1c355845f2af1662c283c30ab`), Apple M2, macOS 27.2.1(26B131). Finder의 파일을 마우스로 끌어 창에 놓았다. 편집이 없는 첫 화면에 PNG(1536 × 1024)를 놓으면 확인 없이 열렸다. 가리기와 강조를 그린 뒤 다른 PNG를 놓으면 "현재 편집을 닫고 coast-b.png 파일을 열까요?"가 떴고, 계속 편집을 누르자 표시가 그대로 남았다. 글 파일(`.txt`)을 놓으면 "이미지를 열 수 없습니다. PNG, JPEG, WebP 파일을 다시 선택하세요."가 나오고 편집 화면과 표시가 유지됐다. 같은 날 6000 × 4000 JPEG를 첫 화면에 놓는 첫 시도는 아무 변화나 안내 없이 끝났고 두 번째 시도에서 열렸다([QA-012](#qa-012-첫-화면에-놓은-파일이-한-번-열리지-않음)). 링크 놓기, 교체 확인의 새 이미지 열기와 Windows는 미확인이다. 수정 전 앱이 없어 수정 전에 화면이 사라지는지는 여전히 재현하지 않았다.

### QA-003 강조 상자 안쪽을 누르면 그 아래 표시를 고를 수 없음

- 상태: 완료. 브라우저 빌드에서 확인한 범위다.
- 우선순위: 보통
- 발견일: 2026-11-23, 코드 리뷰. 사례 ID `2026-11-23-for-me-screen-note-review-highlight-hit`.
- 영향: 메모나 가리기를 만든 뒤 그 둘레에 강조를 그리면 안쪽 표시를 눌러도 강조가 선택돼 글 수정, 색, 크기 설정에 접근할 수 없다. 강조를 옮기면 우회할 수 있다.
- 기대 동작: 사용자가 2026-11-23에 수정이 필요하다고 정했다. 강조는 테두리를 누르면 선택되고, 안쪽을 누르면 그 아래 표시가 먼저, 아래에 표시가 없으면 강조가 선택된다.
- 재현: 정적 검토. 수정 전 `hitMark`는 강조의 영역 전체를 맞은 것으로 보고 나중에 만든 표시를 우선했다. 기존 테스트도 이 동작을 기대했다.
- 증거: 수정 전 `src/document.ts`의 `hitMark`, `tests/document.test.mjs`의 겹친 표시 검사.
- 원인: 테두리만 그리는 표시와 채워진 표시에 같은 판정을 썼다.
- 다음 조치: 해당 없음
- 수정: `hitMark`가 강조의 테두리 안쪽을 가장 낮은 순위로 둔다. 기존 테스트의 기대값은 테두리 지점으로 바꿨고 새 검사를 더했다.
- 재검증: 2026-11-23, 브라우저 빌드. 메모를 만들고 둘러싸는 강조를 그린 뒤 마우스로 메모를 누르면 메모가, 안쪽 빈 곳과 테두리를 누르면 강조가 선택됐다. 새 자동 검사는 판정을 되돌리면 실패했다.
- 앱 재검증: 2026-11-23, 수정 빌드 macOS 앱(실행 파일 SHA-256 `6b8f871c460fb5b8881a06e35fe7678c9e0c27f1c355845f2af1662c283c30ab`), Apple M2, macOS 27.2.1(26B131). 통과. 메모를 둘러싸는 강조를 그린 뒤 선택 도구로 메모 글자를 누르면 메모 설정(글자색, 크기, 굵게, 글 수정)이, 강조 안쪽 빈 곳과 왼쪽 테두리를 누르면 강조 설정(테두리 색)이 나왔다.

### QA-004 복사한 뒤 원본 크기 캔버스의 메모리가 남음

- 상태: 재검증 대기
- 우선순위: 보통
- 발견일: 2026-11-23, 코드 리뷰. 사례 ID `2026-11-23-for-me-screen-note-review-copy-canvas-release`.
- 영향: 큰 사진을 복사한 뒤 메모리가 높은 상태로 남는다. [0.2.0 측정](verification.md#020-실행-시간과-cpu-메모리-사용량)에서 6000 × 4000 사진의 PNG 생성 2.5~4.5초 뒤에도 사진만 연 상태보다 약 320MiB 많았다.
- 기대 동작: 복사가 끝나면 대기 중 메모리가 사진만 연 수준에 가깝게 돌아오고, 반복 복사에도 쌓이지 않는다.
- 재현: 위 측정값. 반복 복사에 따른 누적은 측정하지 않았다.
- 증거: 수정 전 `src/copy.ts`는 `toCanvas`가 돌려준 원본 해상도 캔버스를 `toBlob` 뒤에 비우지 않았다. Konva 10.10.0의 `toCanvas`도 돌려준 캔버스를 비우지 않는다.
- 원인: 추정. 캔버스의 픽셀 저장소가 가비지 수집 때까지 남는다.
- 다음 조치: 검증 기록에 계획한 대로 같은 큰 사진을 여러 번 복사하며 대기 중 메모리를 수정 전과 비교한다.
- 수정: PNG를 만든 뒤 캔버스의 너비와 높이를 0으로 바꾼다.
- 재검증: 2026-11-23, 브라우저 빌드. 복사 뒤 캔버스가 800 × 600에서 0 × 0이 된 것만 확인했다. 메모리가 줄었는지는 미측정이다.
- 앱 재검증: 2026-11-23, 수정 빌드 macOS 앱(실행 파일 SHA-256 `6b8f871c460fb5b8881a06e35fe7678c9e0c27f1c355845f2af1662c283c30ab`), Apple M2, 메모리 16GB, macOS 27.2.1(26B131). 판정 보류, 상태는 재검증 대기로 둔다. 6000 × 4000 JPEG를 열고 15초 간격으로 이미지 복사를 다섯 번 눌렀다. 대기 메모리는 사진만 연 상태 130.7MiB, 각 복사 8~14초 뒤 257.6~266.1MiB로 다섯 번 사이에 늘지 않았다. 사진만 연 상태보다는 약 127~135MiB 높게 남아 기대 동작의 "사진만 연 수준에 가깝게"에는 이르지 않았고, 늘어난 양은 대부분 WebKit 화면 처리 프로세스(71MiB에서 182MiB)였다. 사용자가 측정 시간이 길다며 중단해 문서를 닫은 뒤의 회수는 측정하지 않았다. 0.2.0 측정과 기기(Apple M4 Pro, 48GB), 표본 간격(0.25초와 약 25ms), 사진 여는 방법(실제 끌어 놓기와 자동 파일 입력), 클립보드 전송 포함 여부가 달라 수정 전 값(복사 뒤 약 320MiB 증가)과 직접 비교할 수 없다. 남은 양이 캔버스인지 WebKit의 다른 캐시인지는 확인하지 않았다.

### QA-005 복사 실패를 모두 클립보드 접근 문제로 안내함

- 상태: 완료. PNG 생성 실패를 모의한 범위다.
- 우선순위: 보통
- 발견일: 2026-11-23, 코드 리뷰. 사례 ID `2026-11-23-for-me-screen-note-review-copy-failure-message`.
- 영향: 이미지가 너무 커서 PNG를 만들지 못한 경우에도 클립보드 접근을 확인하라고 안내해, 사용자가 같은 실패를 반복한다.
- 기대 동작: 실패 원인에 맞는 다음 행동을 안내한다.
- 재현: 정적 검토. 웹뷰의 캔버스 한도를 넘는 실제 이미지로는 재현하지 않았다.
- 증거: 수정 전 `src/Editor.tsx`의 `copy`가 모든 실패를 한 문구로 처리했다.
- 원인: PNG 생성 실패와 클립보드 거절을 같은 예외 경로로 받았다.
