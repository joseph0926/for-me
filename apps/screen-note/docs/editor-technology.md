# 개인용 이미지 편집기 기술 결정

2026-11-23에 첫 버전은 **Tauri 2, React, TypeScript, Konva**로 만들기로 했다. macOS와 Windows를 지원 목표로 두고 편집 화면을 공유한다. 사용자는 성능 차이가 크다면 두 운영체제에 맞는 기술을 따로 쓰는 쪽을 선호했다.

## 기술별 역할

| 기술 | 맡는 일 |
|---|---|
| Tauri 2와 Rust | 데스크톱 창을 띄우고 운영체제의 파일 열기, 저장, 클립보드에 연결한다. |
| React와 TypeScript | 메모, 자르기, 가리기, 강조 도구와 선택 상태를 관리한다. 한글 메모는 텍스트 입력창에서 편집한다. |
| Konva와 react-konva | 캔버스에 원본 이미지와 표시를 그린다. 원본과 편집 중인 표시를 분리해 메모를 옮길 때마다 원본 전체를 다시 그리는 일을 줄인다. |

사용자가 이미지 파일을 열거나 붙여 넣은 시점부터 편집을 시작한다. 메모의 위치와 자르기 범위는 원본 이미지 좌표로 보관하고, 복사하거나 저장할 때 표시를 원래 해상도로 합성한다. [첫 화면과 사용 사례](scope.md)

## Mac에서 직접 비교한 결과

Apple M4 Pro, 메모리 48GB, macOS 27.2.1에서 시험했다. 메모리에 준비한 같은 합성 이미지에 불투명한 검은 사각형 20개를 그리고, 결과를 메모리 안의 PNG로 만드는 시간을 쟀다. 입력은 흰 바탕에 색 막대가 반복되는 이미지였다.

- Mac 전용 경로는 Swift 최적화 빌드에서 Core Graphics로 그리고 Image I/O로 PNG를 만들었다.
- 웹 경로는 Mac용 Tauri가 사용하는 WKWebView에서 2D Canvas로 그리고 `toBlob`으로 PNG를 만들었다. 이 경로에는 React와 Konva를 올리지 않았다.
- 해상도마다 한 번 예열하고 두 경로의 실행 순서를 번갈아 7회 측정했다. 예열 때 두 PNG를 다시 열어 해상도별 출력 픽셀이 일치하는지 확인했다.

| 이미지 크기 | Mac 전용 중앙값 | 웹 중앙값 | 중앙값 차이 |
|---|---:|---:|---:|
| 2560 × 1600 | 20.5ms | 24ms | 3.5ms |
| 6000 × 4000 | 124.7ms | 141ms | 16.3ms |

아래는 실행 순서대로 적은 측정값이다. 단위는 밀리초이고 Mac 전용 값은 소수 둘째 자리까지 표시했다.

| 이미지 크기 | Mac 전용 7회 | 웹 7회 |
|---|---|---|
| 2560 × 1600 | 20.50, 20.27, 20.50, 20.27, 20.77, 20.35, 20.92 | 25, 23, 24, 24, 24, 24, 24 |
| 6000 × 4000 | 129.91, 120.53, 122.33, 126.16, 124.68, 120.85, 124.91 | 141, 137, 135, 134, 145, 143, 145 |

두 해상도 모두 Mac 전용 경로가 빨랐다. 큰 이미지에서도 한 번 내보낼 때 차이는 약 0.016초여서 이 결과만으로 두 편집기를 따로 개발할 이득은 작다고 판단했다. 이 수치는 단색 영역이 많은 이미지의 합성과 PNG 생성에 한정된다. 실제 사진 열기, 한글 입력, 드래그, 클립보드 전송, 디스크 저장, 최대 메모리 사용량과 Windows 성능은 미측정이다.

## 공개 자료에서 확인한 점

- Tauri는 macOS에서 WKWebView를, Windows에서 Edge 기반 WebView2를 사용한다. 같은 편집 코드도 실제 성능은 각 운영체제에서 확인해야 한다. [Tauri 웹 엔진 문서](https://v2.tauri.app/reference/webview-versions/)
- react-konva 공식 시험에서 데스크톱 Chromium으로 크기 변경 입력 24회를 처리했을 때, 갱신 방식을 바꾼 두 구현의 중앙값은 도형 100개에서 188.7ms와 22.9ms, 도형 하나에서 1.1ms와 1.7ms였다. 이 시험은 루트에 편집 상태를 둔 경우의 입력과 상태 반영 시간을 비교했다. 사용자 화면에 프레임이 표시되는 시간은 별도로 측정해야 한다. [측정 조건과 결과](https://github.com/konvajs/react-konva/blob/master/benchmarks/README.md)

## 운영체제별 구현으로 바꿀 기준

같은 운영체제와 기기에서 같은 스크린샷과 고해상도 사진으로 반복한다. 파일을 연 뒤 첫 메모를 입력할 수 있을 때까지의 시간, 메모 이동과 자르기 중 느린 프레임의 시간, 결과가 실제로 붙여넣기 가능해질 때까지의 시간, 최대 메모리 사용량을 기록한다. 드래그는 평균 외에 느린 쪽 5%의 경계값도 본다. 60Hz 화면에서 한 프레임의 시간은 약 16.7ms, 120Hz에서는 약 8.3ms다.

공통 구현에서 자주 하는 작업의 지연이 반복되면 원본 재그리기와 불필요한 이미지 복사부터 점검한다. 그래도 문제가 남고, 같은 기기에서 같은 해상도와 편집 결과를 내는 전용 시제품이 그 지연을 해소하면 해당 운영체제의 구현을 분리한다.

- **macOS 후보**는 Swift, AppKit, Core Graphics, Image I/O다. 큰 이미지는 표시 크기에 맞춰 읽고, 원본 해상도로 내보낼 때의 비용을 따로 측정한다. [Apple 이미지 처리 지침](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/CoreImaging/ci_performance/ci_performance.html)
- **Windows 후보**는 C#, WinUI 3, Win2D다. Win2D는 Direct2D로 이미지와 도형을 그리며, GPU가 한 번에 담을 수 있는 크기를 넘는 이미지를 타일로 나눠 다룰 수 있다. [Microsoft Win2D 문서](https://learn.microsoft.com/en-us/windows/apps/develop/win2d/)
